# 배포 전략 Rolling Blue-Green Canary

### 3줄 요약
- 배포 전략 Rolling Blue-Green Canary는 새 버전을 사용자 트래픽에 노출하는 속도와 실패 시 되돌리는 방식을 결정하는 기준을 다룬다.
- 핵심은 도구 사용법보다 배포 실패, 장애 탐지, 영향 완화, 복구 가능성을 한 흐름으로 보는 것이다.
- Rolling Deployment, Blue-Green Deployment, Canary와 점진적 트래픽 전환을 기준으로 Spring 백엔드 운영 판단을 구체화한다.

### 핵심 정리
- 배포 전략은 새 버전을 얼마나 빨리 내보낼지가 아니라 실패를 얼마나 작게 만들지의 문제다.
- 애플리케이션 rollback과 DB 변경 rollback은 같은 난이도가 아니다.
- 점진 배포는 지표가 좋을 때만 다음 단계로 가야 한다.
- 배포 전략 Rolling Blue-Green Canary의 문서는 정상 경로와 실패 경로를 함께 설명해야 한다.
- 배포 전략 Rolling Blue-Green Canary에서 좋은 예시는 실제 설정, 확인 명령, 장애 신호, rollback 또는 restore 판단을 포함한다.
- 개인 프로젝트에서는 재현성과 최소 복구 절차가 중요하고, 기업 운영에서는 권한, 감사, 알림, 리허설이 추가된다.

### 헷갈리는 지점
- 배포 전략을 도구 목록으로만 외우면 운영 판단이 빠진다.
	- 핵심은 명령을 실행하는 것이 아니라 그 명령이 어떤 실패를 줄이는지 아는 것이다.
- 배포 전략 Rolling Blue-Green Canary는 인프라 담당자만의 일이 아니다.
	- 백엔드 개발자는 요청 경로, 설정 값, 로그, 지표, 최근 배포를 설명해야 한다.
- 작은 서비스에는 운영 기준이 필요 없다고 생각하기 쉽다.
	- 작은 서비스일수록 자동화가 적어 장애 중 사람이 기억에 의존하기 쉽다.

### 확인 질문
- 배포 전략 Rolling Blue-Green Canary에서 가장 먼저 확인할 운영 신호는 무엇인가?
	- health check, 최근 배포, 오류율, latency, 로그, rollback 가능성이다.
- 배포 전략 Rolling Blue-Green Canary가 도구 사용법과 다른 점은 무엇인가?
	- 실패했을 때 영향 범위를 줄이고 복구할 수 있는 판단 기준을 제공한다는 점이다.
- 인프라 담당자와 협업할 때 무엇을 제공해야 하는가?
	- 서비스명, 환경, 버전, 시간대, 오류 샘플, 지표, 이미 시도한 조치를 제공해야 한다.
