>- Canary와 점진적 트래픽 전환과 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Canary와 점진적 트래픽 전환은 배포 전략 Rolling Blue-Green Canary 안에서 새 버전을 사용자 트래픽에 노출하는 속도와 실패 시 되돌리는 방식을 결정하는 기준을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Canary와 점진적 트래픽 전환은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Canary와 점진적 트래픽 전환 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Canary와 점진적 트래픽 전환에서는 트래픽 전환 속도보다 실패 반경을 작게 유지하는 것이 우선이다.
- Canary와 점진적 트래픽 전환은 애플리케이션 버전과 데이터 호환성을 같이 봐야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Canary와 점진적 트래픽 전환은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```bash
VERSION=2026.06.30-1
./deploy.sh --version "$VERSION" --strategy rolling
curl -fsS https://api.example.com/actuator/health/readiness
./smoke-test.sh --base-url https://api.example.com
./observe-window.sh --minutes 10 --watch error-rate,latency-p95
./deploy.sh --rollback --to previous-version
```

이 예시는 Canary와 점진적 트래픽 전환의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- 새 버전이 readiness를 통과하기 전 기존 버전을 제거하지 않는다.
- 배포 전후 error rate, latency p95, 핵심 API smoke test를 비교한다.
- DB migration은 이전 버전과 새 버전이 동시에 동작할 수 있는지 확인한다.
- Canary와 점진적 트래픽 전환 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Canary와 점진적 트래픽 전환 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 배포 직후 특정 endpoint만 5xx가 증가한다.
- rollback 후에도 DB schema 변경 때문에 이전 버전이 실패한다.
- canary 비율을 올렸을 때 latency만 천천히 악화된다.
- Canary와 점진적 트래픽 전환 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Canary와 점진적 트래픽 전환 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Canary와 점진적 트래픽 전환 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Canary와 점진적 트래픽 전환이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Canary와 점진적 트래픽 전환 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Canary와 점진적 트래픽 전환이 적용된 서비스명, 환경, 버전, 적용 시간
- Canary와 점진적 트래픽 전환 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Canary와 점진적 트래픽 전환과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Canary와 점진적 트래픽 전환에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
curl -fsS https://api.example.com/actuator/health/readiness
./scripts/error-rate.sh --window 10m
./deploy.sh --rollback
```

Canary와 점진적 트래픽 전환을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- rollback 버튼을 누르기 전에 데이터 변경 여부부터 확인한다.
- canary는 트래픽 비율보다 관측 창과 중단 조건이 중요하다.
- Canary와 점진적 트래픽 전환 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Canary와 점진적 트래픽 전환이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 배포 실패를 새 배포로 덮어쓴다.
- DB destructive change와 애플리케이션 배포를 한 번에 묶는다.
- Canary와 점진적 트래픽 전환의 성공 여부를 담당자 감각으로만 판단한다.
- Canary와 점진적 트래픽 전환과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Canary와 점진적 트래픽 전환이 줄이려는 대표 장애는 무엇인가?
	- 배포 직후 특정 endpoint만 5xx가 증가한다.
- Canary와 점진적 트래픽 전환을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Canary와 점진적 트래픽 전환에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.

## 리뷰 체크포인트

- Canary와 점진적 트래픽 전환 변경은 배포 전 검증 항목에 들어가 있는가?
- Canary와 점진적 트래픽 전환 실패 시 사용자가 보는 증상과 운영자가 보는 지표가 연결되는가?
- Canary와 점진적 트래픽 전환 담당자, 승인자, rollback 판단자가 문서에 남아 있는가?
- Canary와 점진적 트래픽 전환 관련 명령은 읽기 명령과 변경 명령이 구분되어 있는가?
- Canary와 점진적 트래픽 전환 결과를 장애 회고에서 재사용할 수 있는 형태로 남길 수 있는가?

## 운영 메모

Canary와 점진적 트래픽 전환은 한 번 설정하고 끝나는 항목이 아니다. 배포 방식, 트래픽 규모, 팀 권한, 장애 경험이 바뀌면 같은 설정도 위험도가 달라진다.

Canary와 점진적 트래픽 전환 문서를 업데이트할 때는 마지막 장애나 마지막 배포 실패에서 실제로 헷갈렸던 지점을 우선 반영한다.
