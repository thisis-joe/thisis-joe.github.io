# Logging Metrics Tracing

### 3줄 요약
- Logging Metrics Tracing는 장애와 성능 문제를 로그, 메트릭, 트레이스로 연결해 설명하는 체계를 다룬다.
- 핵심은 도구 사용법보다 배포 실패, 장애 탐지, 영향 완화, 복구 가능성을 한 흐름으로 보는 것이다.
- Structured Logging과 Correlation ID, Metrics Counter Gauge Histogram, Distributed Tracing과 Span를 기준으로 Spring 백엔드 운영 판단을 구체화한다.

### 핵심 정리
- 로그는 사건의 문맥, 메트릭은 추세, 트레이스는 경로를 보여준다.
- 관측 신호가 연결되지 않으면 장애 원인은 추측으로 남는다.
- Spring Actuator와 Micrometer는 애플리케이션 내부 상태를 운영 지표로 노출하는 기본 통로다.
- Logging Metrics Tracing의 문서는 정상 경로와 실패 경로를 함께 설명해야 한다.
- Logging Metrics Tracing에서 좋은 예시는 실제 설정, 확인 명령, 장애 신호, rollback 또는 restore 판단을 포함한다.
- 개인 프로젝트에서는 재현성과 최소 복구 절차가 중요하고, 기업 운영에서는 권한, 감사, 알림, 리허설이 추가된다.

### 헷갈리는 지점
- 관측성 운영을 도구 목록으로만 외우면 운영 판단이 빠진다.
	- 핵심은 명령을 실행하는 것이 아니라 그 명령이 어떤 실패를 줄이는지 아는 것이다.
- Logging Metrics Tracing는 인프라 담당자만의 일이 아니다.
	- 백엔드 개발자는 요청 경로, 설정 값, 로그, 지표, 최근 배포를 설명해야 한다.
- 작은 서비스에는 운영 기준이 필요 없다고 생각하기 쉽다.
	- 작은 서비스일수록 자동화가 적어 장애 중 사람이 기억에 의존하기 쉽다.

### 확인 질문
- Logging Metrics Tracing에서 가장 먼저 확인할 운영 신호는 무엇인가?
	- health check, 최근 배포, 오류율, latency, 로그, rollback 가능성이다.
- Logging Metrics Tracing가 도구 사용법과 다른 점은 무엇인가?
	- 실패했을 때 영향 범위를 줄이고 복구할 수 있는 판단 기준을 제공한다는 점이다.
- 인프라 담당자와 협업할 때 무엇을 제공해야 하는가?
	- 서비스명, 환경, 버전, 시간대, 오류 샘플, 지표, 이미 시도한 조치를 제공해야 한다.
