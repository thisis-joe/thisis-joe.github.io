# Cloud Infra VM VPC LB Object Storage

### 3줄 요약
- 클라우드 인프라는 리소스를 만드는 일이 아니라 백엔드 요청이 어디를 지나고 어디서 실패할 수 있는지 이해하는 일이다.
- VM, VPC, Load Balancer, Object Storage는 각각 실행 위치, 네트워크 경계, 트래픽 분산, 파일 제공 책임을 가진다.
- Managed Service는 운영 부담을 줄이지만 연결 제한, 비용, 장애 조치, 권한, 서비스 한계를 반드시 확인해야 한다.

### 핵심 정리
- VM Instance 운영은 OS, runtime, process, log, disk, patch, access key까지 애플리케이션 실행 책임을 포함한다.
- VPC, Subnet, Security Group은 요청이 공개망에서 애플리케이션과 DB까지 도달하는 경로를 결정한다.
- Load Balancer는 정상 target만 트래픽을 받게 하며, Health Check는 Spring 애플리케이션의 준비 상태와 맞아야 한다.
- Object Storage는 정적 파일과 사용자 업로드를 VM disk 밖에 두는 장치이며, 권한과 cache 정책이 함께 필요하다.
- Managed Service는 직접 운영을 줄이는 대신 quota, 장애 조치 방식, 유지보수 창, 비용 모델을 받아들이는 선택이다.
- 백엔드 개발자는 인프라를 직접 만들지 않아도 endpoint, port, timeout, 파일 경로, 연결 수, 장애 신호를 설명해야 한다.

### 헷갈리는 지점
- Managed Service를 쓰면 운영 책임이 사라진다고 오해하기 쉽다.
	- patch나 장애 조치 일부는 맡길 수 있지만 설정, 권한, 연결 수, 비용, 데이터 모델 책임은 남는다.
- VM이 살아 있으면 서비스도 정상이라고 착각하기 쉽다.
	- 프로세스, 포트, 로그, 디스크, 의존 서비스 연결까지 확인해야 요청을 처리할 수 있다.
- Object Storage는 단순 파일 저장소라고 보기 쉽다.
	- 공개/비공개 권한, signed URL, cache, lifecycle, CORS가 사용자 경험과 보안에 직접 영향을 준다.

### 확인 질문
- Security Group은 백엔드 장애 분석에서 무엇을 설명하는가?
	- 어떤 source가 어떤 port/protocol로 어떤 target에 도달할 수 있는지를 설명한다.
- Load Balancer Health Check가 애플리케이션 준비 상태와 맞지 않으면 어떤 일이 생기는가?
	- 요청을 처리할 수 없는 target이 트래픽을 받거나 정상 target이 제외될 수 있다.
- Managed Service 선택 전 확인해야 할 운영 기준은 무엇인가?
	- 연결 제한, 장애 조치 방식, 백업/복구, 유지보수 창, 비용, 권한, 서비스 한계다.
