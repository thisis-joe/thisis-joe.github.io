>- Reverse Proxy와 Upstream는 Spring 백엔드 운영에서 어떤 실패를 줄이는가?
>- Reverse Proxy와 Upstream를 적용하기 전후에 어떤 신호를 확인해야 하는가?
>- Reverse Proxy와 Upstream와 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Reverse Proxy와 Upstream는 Nginx Reverse Proxy Static TLS 안에서 외부 HTTP 요청을 Spring 애플리케이션으로 전달하고 TLS, 정적 파일, timeout, 로그를 관리하는 경계를 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Reverse Proxy와 Upstream는 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Reverse Proxy와 Upstream 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Reverse Proxy와 Upstream에서는 프록시가 남기는 로그가 장애 분석의 첫 번째 경계가 된다.
- Reverse Proxy와 Upstream 설정은 Spring timeout, 업로드 크기, CDN 캐시 정책과 같이 맞춰야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Reverse Proxy와 Upstream는 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```nginx
upstream spring_api {
    server 127.0.0.1:8080 max_fails=3 fail_timeout=10s;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    location / {
        proxy_pass http://spring_api;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
        client_max_body_size 10m;
    }
}
```

이 예시는 Reverse Proxy와 Upstream의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- X-Forwarded-For, X-Forwarded-Proto, Host header 전달을 확인한다.
- proxy_connect_timeout과 proxy_read_timeout을 API 성격별로 정한다.
- 정적 파일은 hash asset과 HTML entry의 cache policy를 분리한다.
- Reverse Proxy와 Upstream 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Reverse Proxy와 Upstream 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- Nginx access log에는 499, 502, 504가 늘지만 Spring log에는 요청이 없다.
- 큰 파일 업로드에서 413이 발생한다.
- 인증서 만료 직전 알림이 없거나 reload 절차가 없다.
- Reverse Proxy와 Upstream 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Reverse Proxy와 Upstream 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Reverse Proxy와 Upstream 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Reverse Proxy와 Upstream가 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Reverse Proxy와 Upstream 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Reverse Proxy와 Upstream가 적용된 서비스명, 환경, 버전, 적용 시간
- Reverse Proxy와 Upstream 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Reverse Proxy와 Upstream와 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Reverse Proxy와 Upstream에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
nginx -t
tail -f /var/log/nginx/api.access.log
curl -I https://api.example.com/actuator/health
```

Reverse Proxy와 Upstream를 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- 프록시 장애는 Nginx log, upstream 상태, Spring health 순서로 본다.
- 캐시 문제는 응답 header와 실제 파일명 hash를 같이 확인한다.
- Reverse Proxy와 Upstream 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Reverse Proxy와 Upstream가 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- timeout을 크게만 늘려 Spring thread 점유를 키운다.
- TLS 갱신 후 nginx -t 없이 reload 한다.
- Reverse Proxy와 Upstream의 성공 여부를 담당자 감각으로만 판단한다.
- Reverse Proxy와 Upstream와 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Reverse Proxy와 Upstream가 줄이려는 대표 장애는 무엇인가?
	- Nginx access log에는 499, 502, 504가 늘지만 Spring log에는 요청이 없다.
- Reverse Proxy와 Upstream를 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Reverse Proxy와 Upstream에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
