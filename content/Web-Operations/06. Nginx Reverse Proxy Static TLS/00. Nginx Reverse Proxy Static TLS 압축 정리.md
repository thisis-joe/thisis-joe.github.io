# Nginx Reverse Proxy Static TLS

### 3줄 요약
- Nginx Reverse Proxy Static TLS는 외부 HTTP 요청을 Spring 애플리케이션으로 전달하고 TLS, 정적 파일, timeout, 로그를 관리하는 경계를 다룬다.
- 핵심은 도구 사용법보다 배포 실패, 장애 탐지, 영향 완화, 복구 가능성을 한 흐름으로 보는 것이다.
- Reverse Proxy와 Upstream, Static Serving과 Cache Header, TLS Termination과 인증서를 기준으로 Spring 백엔드 운영 판단을 구체화한다.

### 핵심 정리
- Nginx는 단순 포트 전달기가 아니라 요청 경계와 장애 증거를 남기는 계층이다.
- 프록시 timeout은 사용자 응답 시간, Spring thread 점유, upstream 상태를 함께 결정한다.
- TLS와 정적 파일 설정은 보안과 캐시 장애의 원인이 될 수 있다.
- Nginx Reverse Proxy Static TLS의 문서는 정상 경로와 실패 경로를 함께 설명해야 한다.
- Nginx Reverse Proxy Static TLS에서 좋은 예시는 실제 설정, 확인 명령, 장애 신호, rollback 또는 restore 판단을 포함한다.
- 개인 프로젝트에서는 재현성과 최소 복구 절차가 중요하고, 기업 운영에서는 권한, 감사, 알림, 리허설이 추가된다.

### 헷갈리는 지점
- Nginx 프록시 운영을 도구 목록으로만 외우면 운영 판단이 빠진다.
	- 핵심은 명령을 실행하는 것이 아니라 그 명령이 어떤 실패를 줄이는지 아는 것이다.
- Nginx Reverse Proxy Static TLS는 인프라 담당자만의 일이 아니다.
	- 백엔드 개발자는 요청 경로, 설정 값, 로그, 지표, 최근 배포를 설명해야 한다.
- 작은 서비스에는 운영 기준이 필요 없다고 생각하기 쉽다.
	- 작은 서비스일수록 자동화가 적어 장애 중 사람이 기억에 의존하기 쉽다.

### 확인 질문
- Nginx Reverse Proxy Static TLS에서 가장 먼저 확인할 운영 신호는 무엇인가?
	- health check, 최근 배포, 오류율, latency, 로그, rollback 가능성이다.
- Nginx Reverse Proxy Static TLS가 도구 사용법과 다른 점은 무엇인가?
	- 실패했을 때 영향 범위를 줄이고 복구할 수 있는 판단 기준을 제공한다는 점이다.
- 인프라 담당자와 협업할 때 무엇을 제공해야 하는가?
	- 서비스명, 환경, 버전, 시간대, 오류 샘플, 지표, 이미 시도한 조치를 제공해야 한다.
