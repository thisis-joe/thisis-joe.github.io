>- Kubernetes가 해결하는 문제와 비용과 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Kubernetes가 해결하는 문제와 비용은 Kubernetes 입문과 도입 판단 안에서 컨테이너 운영을 Kubernetes 리소스로 선언하고 도입 가치와 운영 비용을 판단하는 기준을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Kubernetes가 해결하는 문제와 비용은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Kubernetes가 해결하는 문제와 비용 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Kubernetes가 해결하는 문제와 비용에서는 선언한 리소스와 실제 클러스터 상태의 차이를 읽어야 한다.
- Kubernetes가 해결하는 문제와 비용은 컨테이너 재시작, 트래픽 라우팅, 설정 주입, 리소스 격리를 함께 다룬다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Kubernetes가 해결하는 문제와 비용은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: zipon-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: zipon-api
  template:
    metadata:
      labels:
        app: zipon-api
    spec:
      containers:
        - name: api
          image: registry.example.com/zipon-api:2026.06.30
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
```

이 예시는 Kubernetes가 해결하는 문제와 비용의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- Deployment rollout 상태와 ReplicaSet, Pod event를 함께 확인한다.
- ConfigMap과 Secret 변경이 pod 재시작 없이 반영되는지 구분한다.
- requests와 limits는 HPA, scheduler, OOMKill에 어떤 영향을 주는지 확인한다.
- Kubernetes가 해결하는 문제와 비용 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Kubernetes가 해결하는 문제와 비용 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- pod는 Running인데 readiness가 실패해 Service endpoint에서 제외된다.
- ConfigMap 값은 바뀌었지만 기존 pod에는 반영되지 않는다.
- CPU throttling이나 OOMKilled event가 latency 상승과 함께 나타난다.
- Kubernetes가 해결하는 문제와 비용 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Kubernetes가 해결하는 문제와 비용 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Kubernetes가 해결하는 문제와 비용 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Kubernetes가 해결하는 문제와 비용이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Kubernetes가 해결하는 문제와 비용 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Kubernetes가 해결하는 문제와 비용이 적용된 서비스명, 환경, 버전, 적용 시간
- Kubernetes가 해결하는 문제와 비용 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Kubernetes가 해결하는 문제와 비용과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Kubernetes가 해결하는 문제와 비용에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
kubectl get deploy,po,svc,ingress
kubectl describe pod -l app=zipon-api
kubectl logs -l app=zipon-api --tail=100
```

Kubernetes가 해결하는 문제와 비용을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- kubectl describe는 에러 메시지보다 event 순서가 중요하다.
- 개인 프로젝트 도입은 학습 목적과 운영 목적을 분리해서 결정한다.
- Kubernetes가 해결하는 문제와 비용 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Kubernetes가 해결하는 문제와 비용이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- Kubernetes 도입을 모니터링과 로그 수집 없이 진행한다.
- namespace와 secret 권한을 팀 전체에 넓게 열어 둔다.
- Kubernetes가 해결하는 문제와 비용의 성공 여부를 담당자 감각으로만 판단한다.
- Kubernetes가 해결하는 문제와 비용과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Kubernetes가 해결하는 문제와 비용이 줄이려는 대표 장애는 무엇인가?
	- pod는 Running인데 readiness가 실패해 Service endpoint에서 제외된다.
- Kubernetes가 해결하는 문제와 비용을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Kubernetes가 해결하는 문제와 비용에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
