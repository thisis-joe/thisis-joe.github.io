>- ConfigMap Secret Volume은 Spring 백엔드 운영에서 어떤 실패를 줄이는가?
>- ConfigMap Secret Volume을 적용하기 전후에 어떤 신호를 확인해야 하는가?
>- ConfigMap Secret Volume과 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

ConfigMap Secret Volume은 Kubernetes 입문과 도입 판단 안에서 컨테이너 운영을 Kubernetes 리소스로 선언하고 도입 가치와 운영 비용을 판단하는 기준을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 ConfigMap Secret Volume은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `ConfigMap Secret Volume 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- ConfigMap Secret Volume에서는 값 자체보다 접근 경로와 회전 가능성이 더 중요하다.
- ConfigMap Secret Volume의 운영 품질은 누가 언제 어떤 권한으로 배포했는지를 추적할 수 있는지에서 갈린다.
- ConfigMap Secret Volume에서는 일반 설정, 민감 정보, 파일 형태 설정을 어떤 방식으로 주입할지 분리해야 한다.
- ConfigMap Secret Volume은 값 변경이 기존 Pod에 언제 반영되는지와 rollout 절차를 함께 봐야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

ConfigMap Secret Volume은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: zipon-api-config
data:
  SPRING_PROFILES_ACTIVE: prod
  LOG_LEVEL: INFO
---
apiVersion: v1
kind: Secret
metadata:
  name: zipon-api-secret
type: Opaque
stringData:
  DB_USERNAME: app
  DB_PASSWORD: change-me
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: zipon-api
spec:
  template:
    spec:
      containers:
        - name: api
          envFrom:
            - configMapRef:
                name: zipon-api-config
            - secretRef:
                name: zipon-api-secret
          volumeMounts:
            - name: app-config
              mountPath: /config
      volumes:
        - name: app-config
          configMap:
            name: zipon-api-config
```

이 예시는 ConfigMap Secret Volume의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- Secret 값이 manifest, Git history, kubectl describe 출력 공유본에 남지 않는지 확인한다.
- ConfigMap과 Secret을 수정할 수 있는 RBAC 권한을 배포 권한과 구분한다.
- Secret 회전 후 기존 Pod 재시작, connection 재수립, smoke test 순서를 문서화한다.
- envFrom으로 주입한 값과 volume mount로 주입한 값의 반영 시점 차이를 확인한다.
- ConfigMap을 파일로 mount할 때 subPath 사용 여부와 업데이트 반영 방식을 확인한다.
- ConfigMap 변경만으로 충분한지, Deployment rollout restart가 필요한지 결정한다.
- ConfigMap Secret Volume 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- ConfigMap Secret Volume 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 배포 직후 DB 인증 실패나 외부 API 인증 실패가 증가한다.
- Pod event나 application log에 Secret 값 일부가 노출된다.
- Secret 회전 후 일부 Pod만 예전 값을 사용한다.
- ConfigMap 파일 mount 경로가 애플리케이션의 기존 설정 파일을 덮어쓴다.
- 환경 변수 이름이 Spring 설정 키와 맞지 않아 기본값으로 기동된다.
- 같은 이미지가 namespace마다 다른 ConfigMap 값으로 실행되어 drift가 생긴다.
- ConfigMap Secret Volume 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- ConfigMap Secret Volume 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- ConfigMap Secret Volume 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- ConfigMap Secret Volume이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- ConfigMap Secret Volume 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- ConfigMap Secret Volume이 적용된 서비스명, 환경, 버전, 적용 시간
- ConfigMap Secret Volume 변경 전후의 오류율, latency p95, 요청량, health check 상태
- ConfigMap Secret Volume과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- ConfigMap Secret Volume에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
kubectl get deploy,po,svc,ingress
kubectl describe pod -l app=zipon-api
kubectl logs -l app=zipon-api --tail=100
```

ConfigMap Secret Volume을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- Secret은 가능하면 외부 Secret Manager 연동이나 sealed secret 같은 관리 방식을 검토한다.
- Secret 변경은 staging에서 먼저 재기동과 연결 테스트까지 확인한다.
- kubectl describe와 env 출력은 Secret 노출 위험이 있으므로 공유 범위를 제한한다.
- ConfigMap 변경이 자동 반영되는지, 재시작이 필요한지 팀 규칙으로 고정한다.
- kubectl describe는 에러 메시지보다 event 순서가 중요하다.
- ConfigMap Secret Volume 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- ConfigMap Secret Volume이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- Secret 값을 평문 YAML로 Git에 저장한다.
- Secret 이름만 있고 소유자, 회전 주기, 마지막 변경 이력이 없다.
- ConfigMap과 Secret 변경 이력이 애플리케이션 배포 이력과 분리되어 추적되지 않는다.
- ConfigMap을 Secret 대용으로 사용해 민감 정보를 노출한다.
- Kubernetes 도입을 모니터링과 로그 수집 없이 진행한다.
- namespace와 secret 권한을 팀 전체에 넓게 열어 둔다.
- ConfigMap Secret Volume의 성공 여부를 담당자 감각으로만 판단한다.
- ConfigMap Secret Volume과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- ConfigMap Secret Volume이 줄이려는 대표 장애는 무엇인가?
	- 배포 직후 DB 인증 실패나 외부 API 인증 실패가 증가한다.
- ConfigMap Secret Volume을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- ConfigMap Secret Volume에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
