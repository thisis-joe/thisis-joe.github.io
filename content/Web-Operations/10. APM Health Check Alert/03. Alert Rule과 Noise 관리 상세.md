>- Alert Rule과 Noise 관리와 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Alert Rule과 Noise 관리는 APM Health Check Alert 안에서 서비스 상태를 health check, APM 지표, 알림 규칙, SLO로 행동 가능한 신호로 바꾸는 과정을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Alert Rule과 Noise 관리는 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Alert Rule과 Noise 관리 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Alert Rule과 Noise 관리에서는 신호 하나를 보는 것이 아니라 같은 요청과 같은 시간대로 묶는 것이 중요하다.
- Alert Rule과 Noise 관리의 목표는 장애 후 해석 가능한 증거를 남기는 것이다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Alert Rule과 Noise 관리는 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
groups:
  - name: api-alerts
    rules:
      - alert: High5xxRate
        expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count[5m])) > 0.02
        for: 10m
        labels:
          severity: page
          service: zipon-api
        annotations:
          summary: "5xx rate is above 2%"
          runbook: "https://wiki.example.com/runbook/api-5xx"
```

이 예시는 Alert Rule과 Noise 관리의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- endpoint, status, elapsed time, trace id, correlation id를 공통 필드로 둔다.
- metric label은 cardinality가 폭증하지 않게 제한한다.
- 알림은 임계치, 지속 시간, severity, runbook 링크를 가진다.
- Alert Rule과 Noise 관리 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Alert Rule과 Noise 관리 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- p95 latency가 상승하지만 로그에서 느린 endpoint를 찾을 수 없다.
- trace sampling이 너무 낮아 장애 요청을 재구성하지 못한다.
- 알림이 너무 자주 울려 담당자가 무시하기 시작한다.
- Alert Rule과 Noise 관리 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Alert Rule과 Noise 관리 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Alert Rule과 Noise 관리 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Alert Rule과 Noise 관리가 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Alert Rule과 Noise 관리 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Alert Rule과 Noise 관리가 적용된 서비스명, 환경, 버전, 적용 시간
- Alert Rule과 Noise 관리 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Alert Rule과 Noise 관리와 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Alert Rule과 Noise 관리에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
curl -fsS localhost:8080/actuator/health/liveness
curl -fsS localhost:8080/actuator/health/readiness
promtool check rules alerts.yml
```

Alert Rule과 Noise 관리를 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- 로그는 사건, 메트릭은 규모, trace는 경로를 설명하게 역할을 나눈다.
- 장애 회고에는 그래프 캡처보다 쿼리 가능한 지표 이름을 남긴다.
- Alert Rule과 Noise 관리 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Alert Rule과 Noise 관리가 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 사용자 ID나 원문 payload를 로그에 그대로 남긴다.
- 모든 경고를 page 등급으로 보낸다.
- Alert Rule과 Noise 관리의 성공 여부를 담당자 감각으로만 판단한다.
- Alert Rule과 Noise 관리와 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Alert Rule과 Noise 관리가 줄이려는 대표 장애는 무엇인가?
	- p95 latency가 상승하지만 로그에서 느린 endpoint를 찾을 수 없다.
- Alert Rule과 Noise 관리를 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Alert Rule과 Noise 관리에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.

## 리뷰 체크포인트

- Alert Rule과 Noise 관리 변경은 배포 전 검증 항목에 들어가 있는가?
- Alert Rule과 Noise 관리 실패 시 사용자가 보는 증상과 운영자가 보는 지표가 연결되는가?
- Alert Rule과 Noise 관리 담당자, 승인자, rollback 판단자가 문서에 남아 있는가?
- Alert Rule과 Noise 관리 관련 명령은 읽기 명령과 변경 명령이 구분되어 있는가?
- Alert Rule과 Noise 관리 결과를 장애 회고에서 재사용할 수 있는 형태로 남길 수 있는가?

## 운영 메모

Alert Rule과 Noise 관리는 한 번 설정하고 끝나는 항목이 아니다. 배포 방식, 트래픽 규모, 팀 권한, 장애 경험이 바뀌면 같은 설정도 위험도가 달라진다.

Alert Rule과 Noise 관리 문서를 업데이트할 때는 마지막 장애나 마지막 배포 실패에서 실제로 헷갈렸던 지점을 우선 반영한다.
