# Web Operations 전체 지도

### 3줄 요약
- Web Operations는 Spring 코드가 artifact, 설정, 서버, 프록시, 관측 도구, 복구 절차를 거쳐 실제 사용자 트래픽을 받는 서비스가 되는 흐름이다.
- 핵심은 Docker, Nginx, CI/CD, Actuator 같은 도구 이름이 아니라 배포 후 어떤 신호로 정상 여부를 판단하고, 실패했을 때 어떤 순서로 피해를 줄일지 아는 것이다.
- 백엔드 개발자는 코드 변경, 설정 계약, health check, 로그, metric, trace, release note를 통해 인프라 담당자가 운영 판단을 할 수 있는 증거를 제공해야 한다.

### 핵심 정리
- 개발에서 운영까지의 흐름은 `commit -> build -> test -> artifact -> config -> deploy -> route traffic -> observe -> recover`로 이어진다. 어느 단계의 산출물이 빠져도 장애 중 원인 격리가 늦어진다.
- Build는 실행 가능한 결과물을 재현 가능하게 만드는 단계다. 같은 commit에서 같은 jar/image가 나와야 rollback과 재배포가 가능하다.
- Deploy는 artifact를 서버나 컨테이너 런타임에 올리고 실제 트래픽을 연결하는 단계다. 이때 Spring profile, Secret, port, health check, Nginx upstream, DB migration 순서가 함께 맞아야 한다.
- Observe는 로그, metric, trace, health check, alert를 통해 “사용자가 느끼는 문제”와 “운영자가 보는 신호”를 연결하는 단계다.
- Recover는 rollback, roll forward, traffic shift, rate limit, read-only mode, restore 같은 선택지를 상황에 맞게 고르는 단계다. 복구는 장애가 난 뒤 즉흥적으로 만들 수 없다.
- 백엔드와 인프라의 경계는 고정된 벽이 아니라 협업 계약이다. 백엔드는 서비스 동작과 설정 의미를, 인프라는 런타임, 네트워크, 권한, 자원 제약을 설명해야 한다.
- 개인 프로젝트에서는 단순한 구조라도 version tag, deploy script, log 확인, health check, backup/restore 메모가 있으면 운영 가능한 프로젝트로 보인다.
- 기업 운영에서는 승인 절차, 접근 권한, 감사 로그, SLO, 알림, 장애 보고서, 복구 리허설, 변경 동결 같은 절차가 추가된다.

### 헷갈리는 지점
- 운영을 배포 명령 모음으로만 생각하기 쉽다. 명령은 실행 방법이고 운영은 실패했을 때 영향 범위를 줄이는 판단 체계다.
	- 핵심은 “어떻게 띄우는가”보다 “정상인지 어떻게 알고, 비정상일 때 어떻게 되돌리는가”다.
- 백엔드 개발자는 인프라를 몰라도 된다고 생각하기 쉽다. 서버 권한이나 클라우드 콘솔을 직접 다루지 않는 경우가 많기 때문이다.
	- 핵심은 Spring 코드가 runtime config, connection pool, health endpoint, 로그 포맷, DB migration을 통해 인프라 지표를 바꾼다는 점이다.
- 개인 프로젝트에는 운영 기준이 과하다고 느끼기 쉽다. 트래픽이 작을 때는 장애가 잘 드러나지 않기 때문이다.
	- 핵심은 작은 서비스도 재시작, rollback, 백업 복구, 로그 확인 방법이 없으면 장애 원인을 사람의 기억에 의존하게 된다는 점이다.

### 확인 질문
- 개발에서 운영까지 전체 흐름에서 장애 중 가장 먼저 모아야 할 증거는 무엇인가?
	- 배포 시간, artifact 버전, 설정 diff, health check, 오류율, latency, 로그 샘플, trace id, 사용자가 겪는 영향이다.
- Build, Deploy, Observe, Recover를 분리해서 보는 이유는 무엇인가?
	- 빌드 재현성 문제, 배포 경로 문제, 관측 누락, 복구 절차 부재는 서로 다른 원인이며 대응도 다르기 때문이다.
- 백엔드 개발자가 인프라 담당자에게 제공해야 하는 최소 정보는 무엇인가?
	- 서비스명, 환경, 버전, 변경 시각, 문제 API, 오류 샘플, 관련 설정, 지표 변화, 이미 시도한 조치와 원하는 판단 지점이다.
