## 개요

Build Test Package Pipeline은 CI CD Pipeline 안에서 코드 변경을 검증된 산출물과 통제된 배포 작업으로 연결하는 자동화 흐름을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Build Test Package Pipeline은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Build Test Package Pipeline 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Build Test Package Pipeline에서는 실패 지점을 테스트, 패키징, 이미지, 배포, 검증 단계로 나눠야 한다.
- Build Test Package Pipeline의 산출물은 같은 입력에서 다시 만들 수 있고 배포 이력과 연결되어야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Build Test Package Pipeline은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
name: ci
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./gradlew test bootJar
      - uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: build/libs/*.jar
```

이 예시는 Build Test Package Pipeline의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- test job 실패와 deploy job 실패를 같은 장애로 묶지 않는다.
- artifact checksum, image digest, git SHA를 배포 노트에 남긴다.
- 배포 job은 protected branch와 승인 조건을 가진다.
- Build Test Package Pipeline 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Build Test Package Pipeline 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- main branch는 초록색인데 운영 배포 버전을 추적할 수 없다.
- 테스트는 통과하지만 artifact upload 또는 image push가 실패한다.
- 배포 후 smoke test 없이 pipeline이 성공으로 끝난다.
- Build Test Package Pipeline 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Build Test Package Pipeline 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Build Test Package Pipeline 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Build Test Package Pipeline이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Build Test Package Pipeline 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Build Test Package Pipeline이 적용된 서비스명, 환경, 버전, 적용 시간
- Build Test Package Pipeline 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Build Test Package Pipeline과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Build Test Package Pipeline에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
gh run list --limit 5
gh run view --log-failed
docker pull registry.example.com/app:2026.06.30-1
```

Build Test Package Pipeline을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- CI는 빠르게 실패하게 만들고 CD는 천천히 검증하게 만든다.
- 실패한 pipeline은 재실행 전에 실패 단계와 입력 변경 여부를 확인한다.
- Build Test Package Pipeline 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Build Test Package Pipeline이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- CI job에 운영 Secret 전체를 주입한다.
- tag 재사용으로 rollback 대상이 바뀐다.
- Build Test Package Pipeline의 성공 여부를 담당자 감각으로만 판단한다.
- Build Test Package Pipeline과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Build Test Package Pipeline이 줄이려는 대표 장애는 무엇인가?
	- main branch는 초록색인데 운영 배포 버전을 추적할 수 없다.
- Build Test Package Pipeline을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Build Test Package Pipeline에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
