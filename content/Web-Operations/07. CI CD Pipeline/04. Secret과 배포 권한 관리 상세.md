## 개요

Secret과 배포 권한 관리는 CI CD Pipeline 안에서 코드 변경을 검증된 산출물과 통제된 배포 작업으로 연결하는 자동화 흐름을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Secret과 배포 권한 관리는 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Secret과 배포 권한 관리 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Secret과 배포 권한 관리에서는 값 자체보다 접근 경로와 회전 가능성이 더 중요하다.
- Secret과 배포 권한 관리의 운영 품질은 누가 언제 어떤 권한으로 배포했는지를 추적할 수 있는지에서 갈린다.
- Secret과 배포 권한 관리에서는 트래픽 전환 속도보다 실패 반경을 작게 유지하는 것이 우선이다.
- Secret과 배포 권한 관리는 애플리케이션 버전과 데이터 호환성을 같이 봐야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Secret과 배포 권한 관리는 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
name: ci
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./gradlew test bootJar
      - uses: actions/upload-artifact@v4
        with:
          name: app-jar
          path: build/libs/*.jar
```

이 예시는 Secret과 배포 권한 관리의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- Secret 값이 CI 로그, Docker image layer, Git history에 남지 않는지 확인한다.
- 배포 job 권한은 contents read, package write, id-token 등 필요한 범위만 연다.
- 운영 Secret 회전 절차와 실패 시 rollback 절차를 같은 문서에 둔다.
- 새 버전이 readiness를 통과하기 전 기존 버전을 제거하지 않는다.
- 배포 전후 error rate, latency p95, 핵심 API smoke test를 비교한다.
- DB migration은 이전 버전과 새 버전이 동시에 동작할 수 있는지 확인한다.
- Secret과 배포 권한 관리 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Secret과 배포 권한 관리 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 배포 직후 인증 실패나 registry push 실패가 증가한다.
- pipeline log에 환경 변수 값 일부가 노출된다.
- 퇴사자나 개인 토큰이 배포 권한에 남아 있다.
- 배포 직후 특정 endpoint만 5xx가 증가한다.
- rollback 후에도 DB schema 변경 때문에 이전 버전이 실패한다.
- canary 비율을 올렸을 때 latency만 천천히 악화된다.
- Secret과 배포 권한 관리 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Secret과 배포 권한 관리 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Secret과 배포 권한 관리 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Secret과 배포 권한 관리가 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Secret과 배포 권한 관리 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Secret과 배포 권한 관리가 적용된 서비스명, 환경, 버전, 적용 시간
- Secret과 배포 권한 관리 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Secret과 배포 권한 관리와 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Secret과 배포 권한 관리에 대해 이미 시도한 조치와 그 결과

Secret과 배포 권한 관리를 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- OIDC 기반 임시 자격 증명을 우선 검토한다.
- Secret 변경은 staging에서 먼저 smoke test 한다.
- rollback 버튼을 누르기 전에 데이터 변경 여부부터 확인한다.
- canary는 트래픽 비율보다 관측 창과 중단 조건이 중요하다.
- Secret과 배포 권한 관리 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Secret과 배포 권한 관리가 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 개인 access token으로 운영 배포를 수행한다.
- Secret 이름만 있고 소유자와 회전 주기가 없다.
- 배포 실패를 새 배포로 덮어쓴다.
- DB destructive change와 애플리케이션 배포를 한 번에 묶는다.
- Secret과 배포 권한 관리의 성공 여부를 담당자 감각으로만 판단한다.
- Secret과 배포 권한 관리와 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Secret과 배포 권한 관리가 줄이려는 대표 장애는 무엇인가?
	- 배포 직후 인증 실패나 registry push 실패가 증가한다.
- Secret과 배포 권한 관리를 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Secret과 배포 권한 관리에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
