# CI CD Pipeline

### 3줄 요약
- CI CD Pipeline은 코드 변경을 검증된 산출물과 통제된 배포 작업으로 연결하는 자동화 흐름을 다룬다.
- 핵심은 도구 사용법보다 배포 실패, 장애 탐지, 영향 완화, 복구 가능성을 한 흐름으로 보는 것이다.
- CI와 CD 단계 분리, Build Test Package Pipeline, Artifact Version Tagging를 기준으로 Spring 백엔드 운영 판단을 구체화한다.

### 핵심 정리
- CI는 코드가 깨졌는지 확인하고 CD는 운영 변경을 통제한다.
- Pipeline 실패는 테스트 실패, 산출물 실패, 권한 실패, 배포 후 검증 실패로 나눠야 한다.
- Secret은 성공적인 배포보다 노출 사고와 권한 남용을 기준으로 설계한다.
- CI CD Pipeline의 문서는 정상 경로와 실패 경로를 함께 설명해야 한다.
- CI CD Pipeline에서 좋은 예시는 실제 설정, 확인 명령, 장애 신호, rollback 또는 restore 판단을 포함한다.
- 개인 프로젝트에서는 재현성과 최소 복구 절차가 중요하고, 기업 운영에서는 권한, 감사, 알림, 리허설이 추가된다.

### 헷갈리는 지점
- CI/CD 운영을 도구 목록으로만 외우면 운영 판단이 빠진다.
	- 핵심은 명령을 실행하는 것이 아니라 그 명령이 어떤 실패를 줄이는지 아는 것이다.
- CI CD Pipeline은 인프라 담당자만의 일이 아니다.
	- 백엔드 개발자는 요청 경로, 설정 값, 로그, 지표, 최근 배포를 설명해야 한다.
- 작은 서비스에는 운영 기준이 필요 없다고 생각하기 쉽다.
	- 작은 서비스일수록 자동화가 적어 장애 중 사람이 기억에 의존하기 쉽다.

### 확인 질문
- CI CD Pipeline에서 가장 먼저 확인할 운영 신호는 무엇인가?
	- health check, 최근 배포, 오류율, latency, 로그, rollback 가능성이다.
- CI CD Pipeline이 도구 사용법과 다른 점은 무엇인가?
	- 실패했을 때 영향 범위를 줄이고 복구할 수 있는 판단 기준을 제공한다는 점이다.
- 인프라 담당자와 협업할 때 무엇을 제공해야 하는가?
	- 서비스명, 환경, 버전, 시간대, 오류 샘플, 지표, 이미 시도한 조치를 제공해야 한다.
