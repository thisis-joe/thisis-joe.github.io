>- 초기 대응과 커뮤니케이션과 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

초기 대응과 커뮤니케이션은 Incident Response 장애 보고서 안에서 장애를 빠르게 탐지하고 영향을 줄이며 원인과 재발 방지를 문서화하는 대응 체계를 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 초기 대응과 커뮤니케이션은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `초기 대응과 커뮤니케이션 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- 초기 대응과 커뮤니케이션에서는 원인 맞히기보다 사용자 영향 제한과 증거 보존이 먼저다.
- 초기 대응과 커뮤니케이션의 품질은 타임라인, 영향 범위, 의사결정 근거가 남는지로 판단한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

초기 대응과 커뮤니케이션은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```markdown
## Incident Snapshot
- 제목: 주문 API 5xx 증가
- Severity: SEV-2
- 영향: 21:05~21:32 주문 생성 실패율 최대 18%
- 탐지: High5xxRate alert
- 완화: 이전 버전 rollback, DB timeout 설정 복구
- 후속 조치: 설정 diff 검사와 readiness smoke test 추가
```

이 예시는 초기 대응과 커뮤니케이션의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- severity는 내부 에러 수보다 사용자 영향과 우회 가능성으로 정한다.
- incident channel에는 사실, 시간, 담당자, 다음 업데이트 시간을 남긴다.
- 완화 조치마다 어떤 지표가 좋아져야 하는지 미리 적는다.
- 초기 대응과 커뮤니케이션 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- 초기 대응과 커뮤니케이션 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 같은 질문이 여러 채널에서 반복되어 대응자가 로그를 못 본다.
- 원인 분석이 길어지는 동안 사용자 영향이 계속 커진다.
- 복구 후 후속 조치 소유자가 정해지지 않는다.
- 초기 대응과 커뮤니케이션 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- 초기 대응과 커뮤니케이션 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- 초기 대응과 커뮤니케이션 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- 초기 대응과 커뮤니케이션이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- 초기 대응과 커뮤니케이션 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- 초기 대응과 커뮤니케이션이 적용된 서비스명, 환경, 버전, 적용 시간
- 초기 대응과 커뮤니케이션 변경 전후의 오류율, latency p95, 요청량, health check 상태
- 초기 대응과 커뮤니케이션과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- 초기 대응과 커뮤니케이션에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
date -u
curl -fsS https://api.example.com/actuator/health
grep ERROR application.log | tail -50
```

초기 대응과 커뮤니케이션을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- incident commander와 technical lead 역할을 분리한다.
- postmortem에는 탐지 실패와 완화 지연도 함께 적는다.
- 초기 대응과 커뮤니케이션 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- 초기 대응과 커뮤니케이션이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 장애 중 blame을 시작한다.
- 고객 공지와 내부 타임라인이 서로 다르다.
- 초기 대응과 커뮤니케이션의 성공 여부를 담당자 감각으로만 판단한다.
- 초기 대응과 커뮤니케이션과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- 초기 대응과 커뮤니케이션이 줄이려는 대표 장애는 무엇인가?
	- 같은 질문이 여러 채널에서 반복되어 대응자가 로그를 못 본다.
- 초기 대응과 커뮤니케이션을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- 초기 대응과 커뮤니케이션에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.

## 리뷰 체크포인트

- 초기 대응과 커뮤니케이션 변경은 배포 전 검증 항목에 들어가 있는가?
- 초기 대응과 커뮤니케이션 실패 시 사용자가 보는 증상과 운영자가 보는 지표가 연결되는가?
- 초기 대응과 커뮤니케이션 담당자, 승인자, rollback 판단자가 문서에 남아 있는가?
- 초기 대응과 커뮤니케이션 관련 명령은 읽기 명령과 변경 명령이 구분되어 있는가?
- 초기 대응과 커뮤니케이션 결과를 장애 회고에서 재사용할 수 있는 형태로 남길 수 있는가?

## 운영 메모

초기 대응과 커뮤니케이션은 한 번 설정하고 끝나는 항목이 아니다. 배포 방식, 트래픽 규모, 팀 권한, 장애 경험이 바뀌면 같은 설정도 위험도가 달라진다.

초기 대응과 커뮤니케이션 문서를 업데이트할 때는 마지막 장애나 마지막 배포 실패에서 실제로 헷갈렸던 지점을 우선 반영한다.
