# Backup Restore Migration 운영

### 3줄 요약
- Backup Restore Migration 운영은 데이터와 스키마 변경을 장애 이후에도 복구 가능한 상태로 유지하는 절차를 다룬다.
- 핵심은 도구 사용법보다 배포 실패, 장애 탐지, 영향 완화, 복구 가능성을 한 흐름으로 보는 것이다.
- Backup 종류와 복구 목표, Restore Drill과 검증, Schema Migration 운영을 기준으로 Spring 백엔드 운영 판단을 구체화한다.

### 핵심 정리
- 백업이 있다는 말과 복구 가능하다는 말은 다르다.
- 복구 목표는 RTO와 RPO로 말해야 운영 판단이 가능하다.
- 마이그레이션은 데이터 복구 가능성과 배포 호환성을 같이 검토해야 한다.
- Backup Restore Migration 운영의 문서는 정상 경로와 실패 경로를 함께 설명해야 한다.
- Backup Restore Migration 운영에서 좋은 예시는 실제 설정, 확인 명령, 장애 신호, rollback 또는 restore 판단을 포함한다.
- 개인 프로젝트에서는 재현성과 최소 복구 절차가 중요하고, 기업 운영에서는 권한, 감사, 알림, 리허설이 추가된다.

### 헷갈리는 지점
- 백업 복구 운영을 도구 목록으로만 외우면 운영 판단이 빠진다.
	- 핵심은 명령을 실행하는 것이 아니라 그 명령이 어떤 실패를 줄이는지 아는 것이다.
- Backup Restore Migration 운영은 인프라 담당자만의 일이 아니다.
	- 백엔드 개발자는 요청 경로, 설정 값, 로그, 지표, 최근 배포를 설명해야 한다.
- 작은 서비스에는 운영 기준이 필요 없다고 생각하기 쉽다.
	- 작은 서비스일수록 자동화가 적어 장애 중 사람이 기억에 의존하기 쉽다.

### 확인 질문
- Backup Restore Migration 운영에서 가장 먼저 확인할 운영 신호는 무엇인가?
	- health check, 최근 배포, 오류율, latency, 로그, rollback 가능성이다.
- Backup Restore Migration 운영이 도구 사용법과 다른 점은 무엇인가?
	- 실패했을 때 영향 범위를 줄이고 복구할 수 있는 판단 기준을 제공한다는 점이다.
- 인프라 담당자와 협업할 때 무엇을 제공해야 하는가?
	- 서비스명, 환경, 버전, 시간대, 오류 샘플, 지표, 이미 시도한 조치를 제공해야 한다.
