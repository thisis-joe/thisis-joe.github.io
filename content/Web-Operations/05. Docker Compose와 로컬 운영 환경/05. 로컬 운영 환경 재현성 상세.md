>- 로컬 운영 환경 재현성은 왜 Spring 백엔드 개발 품질과 운영 대응 속도에 영향을 주는가?
>- 팀원이 같은 Compose 환경을 반복 실행하려면 무엇을 고정해야 하는가?
>- 로컬 환경이 운영과 다르다는 사실을 어떻게 문서화하고 다뤄야 하는가?

## 개요

로컬 운영 환경 재현성은 팀원이 같은 명령으로 비슷한 의존성 상태를 만들 수 있는 능력이다.

로컬 환경이 매번 다르면 테스트 실패가 코드 문제인지, DB 상태 문제인지, Redis 잔여 key 문제인지, 설정 문제인지 구분하기 어렵다.

Compose는 이 문제를 줄이는 좋은 도구지만, 파일 하나만 있다고 재현성이 생기지는 않는다.

image version, env sample, migration, seed data, reset 절차, health 확인, 운영과의 차이가 함께 문서화되어야 한다.

## 재현성의 입력

로컬 환경을 재현하려면 다음 입력을 고정한다.

- Compose file version
- MySQL image version
- Redis image version
- Spring profile
- env key 목록
- migration 실행 방식
- seed data
- volume reset 방식
- host port
- health 확인 명령

이 중 하나가 팀원마다 다르면 로컬 장애 재현 결과도 달라진다.

## 실행 명령 표준화

README나 Makefile에 실행 명령을 모은다.

```makefile
local-up:
	docker compose up -d mysql redis
	./gradlew bootRun --args='--spring.profiles.active=local'

local-down:
	docker compose down

local-reset:
	docker compose down -v
	docker compose up -d mysql redis
```

명령 이름은 위험도를 드러내야 한다.

`local-reset`은 volume을 삭제하므로 일반 종료 명령과 분리한다.

## env sample

실제 local env는 Git에 넣지 않고 sample만 둔다.

`.env.example`:

```text
SPRING_PROFILES_ACTIVE=local-compose
DB_URL=jdbc:mysql://mysql:3306/app
DB_USERNAME=app
DB_PASSWORD=app-password
REDIS_HOST=redis
```

팀원은 sample을 복사해 `.env.local`을 만든다.

운영 Secret을 sample에 넣지 않는다.

값이 local 가짜 값이라는 점을 명확히 적는다.

## 데이터 상태

재현성은 실행뿐 아니라 데이터 상태도 포함한다.

로컬 DB가 비어 있는지, seed data가 있는지, 이전 테스트 데이터가 남아 있는지에 따라 결과가 달라진다.

```bash
docker compose down -v
docker compose up -d mysql redis
./gradlew flywayMigrate
./gradlew seedLocalData
```

seed data가 없다면 어떤 API를 수동으로 호출해 초기 상태를 만들지 문서화한다.

운영 dump를 local에 복원할 때는 개인정보 마스킹과 접근 권한을 별도로 봐야 한다.

## 운영과의 차이 문서화

Compose local은 운영과 같지 않다.

차이를 알아야 로컬 재현 결과를 과신하지 않는다.

예시:

```text
local:
  mysql: single container, no replication
  redis: no auth, no distributed setup
  network: single Docker bridge network
  storage: local named volume
prod:
  mysql: managed DB, backup/PITR, monitoring
  redis: managed cache, auth, memory policy
  network: VPC, LB, firewall
  storage: managed volume/object storage
```

이 차이를 적어 두면 로컬에서 재현되지 않는 운영 장애를 더 정직하게 다룰 수 있다.

## 운영 체크리스트

- `docker compose up`과 reset 명령이 문서화되어 있는가?
- image version이 고정되어 있는가?
- `.env.example`이 최신 key 목록을 반영하는가?
- migration과 seed data 절차가 있는가?
- local data reset이 위험 명령으로 표시되어 있는가?
- 운영과 local의 차이가 문서화되어 있는가?
- health 확인과 smoke test 명령이 있는가?

## 장애 신호

- 팀원마다 같은 테스트가 다른 결과를 낸다.
- `.env.example`에 없는 key가 실제 Spring 설정에서 필요하다.
- MySQL image version 차이로 collation이나 SQL mode가 다르다.
- Redis에 이전 테스트 key가 남아 재현이 실패한다.
- local reset 후 seed data가 없어 API 검증을 못 한다.
- 운영 장애가 local에서 재현되지 않는데 차이 목록이 없다.

## 안전한 완화 조치

재현이 흔들리면 먼저 환경을 초기화하지 말고 현재 상태를 기록한다.

```bash
docker compose config
docker compose ps
docker compose logs --tail 100 api
```

그 다음 reset이 필요한지 판단한다.

reset은 문제를 없앨 수 있지만 원인 증거도 지운다.

팀 공통 문제라면 `.env.example`, Compose image version, migration/seed 절차를 먼저 수정한다.

운영 장애 재현은 local 한계와 차이점을 함께 기록한다.

## 인프라 담당자와 공유할 자료

```text
로컬 재현 여부: 재현 안 됨
local 차이: Redis single container, no auth, no eviction policy
prod 조건: managed Redis, maxmemory-policy volatile-lru
추정: local Redis 설정 차이로 cache eviction 문제 재현 불가
다음: local redis command로 maxmemory-policy를 prod와 맞춰 재시도
```

로컬 재현 실패도 차이를 명확히 적으면 의미 있는 협업 자료가 된다.

## 실전 팁

- local 환경 문서는 첫 설치보다 반복 reset과 검증에 초점을 둔다.
- image version을 명시하고 의도 없이 major version이 바뀌지 않게 한다.
- seed data는 작고 명확하게 유지한다.
- 운영과 local 차이는 숨기지 않고 표로 적는다.
- local 환경 실패 사례를 체크리스트에 반영한다.

## 위험 신호!

- “내 PC에서는 됨”만 있고 환경 snapshot이 없다.
- `.env.example`이 실제 필요한 key와 다르다.
- local reset 명령이 데이터 삭제를 경고하지 않는다.
- 운영 dump를 마스킹 없이 local에 둔다.
- local이 운영과 같다고 보고 성능 판단까지 한다.

## 확인 질문

- 로컬 환경 재현성이 중요한 이유는 무엇인가?
	- 팀원이 같은 의존성, 설정, 데이터 상태에서 문제를 재현해야 코드 문제와 환경 문제를 구분할 수 있기 때문이다.
- reset 명령을 별도로 문서화해야 하는 이유는 무엇인가?
	- volume과 데이터를 삭제하므로 일반 종료와 다르게 위험하고, 실행 전후 상태가 테스트 결과에 영향을 주기 때문이다.
- 운영과 local 차이를 문서화해야 하는 이유는 무엇인가?
	- local에서 재현되지 않는 장애를 무시하지 않고 managed service, network, auth, backup, resource 차이로 설명하기 위해서다.
