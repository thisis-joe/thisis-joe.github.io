>- Healthcheck와 의존성 순서는 Spring 백엔드 운영에서 어떤 실패를 줄이는가?
>- Healthcheck와 의존성 순서를 적용하기 전후에 어떤 신호를 확인해야 하는가?
>- Healthcheck와 의존성 순서와 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Healthcheck와 의존성 순서는 Docker Compose와 로컬 운영 환경 안에서 운영 의존성과 비슷한 MySQL, Redis, Spring 실행 환경을 로컬에서 반복 재현하는 기준을 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Healthcheck와 의존성 순서는 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Healthcheck와 의존성 순서 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Healthcheck와 의존성 순서에서는 살아 있음과 준비됨을 분리해야 한다.
- Healthcheck와 의존성 순서의 핵심은 트래픽을 받을 수 없는 인스턴스를 빠르게 제외하는 것이다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Healthcheck와 의존성 순서는 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```yaml
services:
  api:
    build: .
    env_file: .env.local
    ports:
      - "8080:8080"
    depends_on:
      mysql:
        condition: service_healthy
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: app
      MYSQL_ROOT_PASSWORD: local-password
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 3s
      retries: 20
volumes:
  mysql-data:
```

이 예시는 Healthcheck와 의존성 순서의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- liveness는 deadlock이나 복구 불가능 상태를 재시작하는 기준으로 둔다.
- readiness는 DB, cache, migration 상태처럼 요청 처리 조건을 반영한다.
- health endpoint가 너무 무거워 장애 중 추가 부하를 만들지 않는지 확인한다.
- Healthcheck와 의존성 순서 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Healthcheck와 의존성 순서 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- health는 UP인데 핵심 API timeout이 증가한다.
- probe 실패로 pod가 반복 재시작된다.
- LB target은 healthy인데 Spring thread가 고갈되어 있다.
- Healthcheck와 의존성 순서 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Healthcheck와 의존성 순서 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Healthcheck와 의존성 순서 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Healthcheck와 의존성 순서가 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Healthcheck와 의존성 순서 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Healthcheck와 의존성 순서가 적용된 서비스명, 환경, 버전, 적용 시간
- Healthcheck와 의존성 순서 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Healthcheck와 의존성 순서와 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Healthcheck와 의존성 순서에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
docker compose config
docker compose ps
docker compose logs --tail 100 api
```

Healthcheck와 의존성 순서를 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- probe 실패 시 애플리케이션 로그와 orchestrator event를 함께 본다.
- DB 장애 시 readiness를 내릴지 degrade mode를 유지할지 미리 정한다.
- Healthcheck와 의존성 순서 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Healthcheck와 의존성 순서가 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 모든 의존성을 liveness에 넣어 작은 지연도 재시작 폭주로 만든다.
- readiness 없이 배포 직후 트래픽을 바로 받는다.
- Healthcheck와 의존성 순서의 성공 여부를 담당자 감각으로만 판단한다.
- Healthcheck와 의존성 순서와 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Healthcheck와 의존성 순서가 줄이려는 대표 장애는 무엇인가?
	- health는 UP인데 핵심 API timeout이 증가한다.
- Healthcheck와 의존성 순서를 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Healthcheck와 의존성 순서에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
