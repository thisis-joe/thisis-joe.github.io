>- Rollback Restore 의사결정 Runbook은 Spring 백엔드 운영에서 어떤 실패를 줄이는가?
>- Rollback Restore 의사결정 Runbook을 적용하기 전후에 어떤 신호를 확인해야 하는가?
>- Rollback Restore 의사결정 Runbook과 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

Rollback Restore 의사결정 Runbook은 Web Operations Runbook 안에서 장애 중에도 같은 순서로 확인하고 안전한 완화와 복구 판단을 내리기 위한 실행 문서를 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 Rollback Restore 의사결정 Runbook은 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `Rollback Restore 의사결정 Runbook 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- Rollback Restore 의사결정 Runbook에서는 트래픽 전환 속도보다 실패 반경을 작게 유지하는 것이 우선이다.
- Rollback Restore 의사결정 Runbook은 애플리케이션 버전과 데이터 호환성을 같이 봐야 한다.
- Rollback Restore 의사결정 Runbook에서는 백업 파일의 존재보다 복구 검증 결과가 중요하다.
- Rollback Restore 의사결정 Runbook은 RTO, RPO, PITR 가능 여부를 숫자와 절차로 설명해야 한다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

Rollback Restore 의사결정 Runbook은 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```markdown
## Runbook Step
1. 최근 배포와 알림 발생 시간을 맞춘다.
2. 사용자 영향 지표를 확인한다.
3. 로그, 메트릭, trace id를 같은 시간대로 묶는다.
4. rollback, 기능 차단, rate limit 중 가장 안전한 완화를 고른다.
5. 복구 후 10분 이상 오류율과 latency를 관찰한다.
```

이 예시는 Rollback Restore 의사결정 Runbook의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- 새 버전이 readiness를 통과하기 전 기존 버전을 제거하지 않는다.
- 배포 전후 error rate, latency p95, 핵심 API smoke test를 비교한다.
- DB migration은 이전 버전과 새 버전이 동시에 동작할 수 있는지 확인한다.
- 마지막 백업 시각과 복구 가능한 시점을 확인한다.
- restore drill은 별도 DB에서 애플리케이션 smoke test까지 수행한다.
- schema change는 expand, deploy, backfill, contract 순서로 나눈다.
- Rollback Restore 의사결정 Runbook 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- Rollback Restore 의사결정 Runbook 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 배포 직후 특정 endpoint만 5xx가 증가한다.
- rollback 후에도 DB schema 변경 때문에 이전 버전이 실패한다.
- canary 비율을 올렸을 때 latency만 천천히 악화된다.
- 대량 변경 후 잘못된 데이터가 뒤늦게 발견된다.
- 백업은 있지만 복구 권한을 가진 사람이 없다.
- object storage lifecycle 정책으로 필요한 파일이 삭제된다.
- Rollback Restore 의사결정 Runbook 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- Rollback Restore 의사결정 Runbook 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- Rollback Restore 의사결정 Runbook 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- Rollback Restore 의사결정 Runbook이 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- Rollback Restore 의사결정 Runbook 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- Rollback Restore 의사결정 Runbook이 적용된 서비스명, 환경, 버전, 적용 시간
- Rollback Restore 의사결정 Runbook 변경 전후의 오류율, latency p95, 요청량, health check 상태
- Rollback Restore 의사결정 Runbook과 관련된 로그 샘플, trace id, correlation id, 설정 diff
- Rollback Restore 의사결정 Runbook에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
curl -fsS https://api.example.com/actuator/health
kubectl rollout status deploy/zipon-api
promtool check rules alerts.yml
```

Rollback Restore 의사결정 Runbook을 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- rollback 버튼을 누르기 전에 데이터 변경 여부부터 확인한다.
- canary는 트래픽 비율보다 관측 창과 중단 조건이 중요하다.
- 복구 리허설 시간과 실패 지점을 문서에 남긴다.
- DB 변경은 rollback보다 forward fix가 안전한 경우도 따로 판단한다.
- runbook은 짧은 문장과 실제 명령으로 쓴다.
- Rollback Restore 의사결정 Runbook 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- Rollback Restore 의사결정 Runbook이 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- 배포 실패를 새 배포로 덮어쓴다.
- DB destructive change와 애플리케이션 배포를 한 번에 묶는다.
- 운영 DB에서 destructive query를 백업 확인 없이 실행한다.
- 마이그레이션 실패 후 수동 수정 내역을 기록하지 않는다.
- runbook을 장애 후 업데이트하지 않는다.
- 권한이 없는 명령을 runbook의 핵심 단계로 둔다.
- Rollback Restore 의사결정 Runbook의 성공 여부를 담당자 감각으로만 판단한다.
- Rollback Restore 의사결정 Runbook과 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- Rollback Restore 의사결정 Runbook이 줄이려는 대표 장애는 무엇인가?
	- 배포 직후 특정 endpoint만 5xx가 증가한다.
- Rollback Restore 의사결정 Runbook을 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- Rollback Restore 의사결정 Runbook에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.
