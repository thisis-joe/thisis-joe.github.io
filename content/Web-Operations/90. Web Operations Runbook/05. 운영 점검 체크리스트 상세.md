>- 운영 점검 체크리스트와 관련해 장애 중 하지 말아야 할 대응은 무엇인가?

## 개요

운영 점검 체크리스트는 Web Operations Runbook 안에서 장애 중에도 같은 순서로 확인하고 안전한 완화와 복구 판단을 내리기 위한 실행 문서를 실제 운영 판단으로 바꾸는 주제다.

백엔드 개발자에게 운영 점검 체크리스트는 이름을 아는 데서 끝나지 않는다. 배포 전 검증, 장애 중 관측, 복구 또는 우회 가능성까지 연결되어야 운영 문서가 된다.

## 원리

이 문서의 원리는 `운영 점검 체크리스트 상세`을 도구 사용법이 아니라 운영 경계로 이해하는 것이다. 운영 경계는 책임자, 입력, 출력, 실패 신호, 되돌리는 방법이 함께 정리된 단위다.

- 운영 점검 체크리스트에서는 담당자가 장애 중 다음 행동을 고를 수 있어야 한다.
- 운영 점검 체크리스트는 명령어 목록이 아니라 분기 조건과 중단 조건을 가진 실행 문서다.

## 요청 흐름에서 보는 위치

```text
client request
  edge or deploy pipeline
    runtime configuration
      Spring application
        logs, metrics, traces
          alert or operator decision
            rollback, retry, restore, or mitigation
```

운영 점검 체크리스트는 이 흐름의 한 지점처럼 보여도 앞뒤 단계와 같이 실패한다. 예를 들어 설정이 잘못되면 health check가 흔들리고, 관측 신호가 없으면 rollback 판단도 늦어진다.

## 설정 또는 코드 예시

```markdown
## Runbook Step
1. 최근 배포와 알림 발생 시간을 맞춘다.
2. 사용자 영향 지표를 확인한다.
3. 로그, 메트릭, trace id를 같은 시간대로 묶는다.
4. rollback, 기능 차단, rate limit 중 가장 안전한 완화를 고른다.
5. 복구 후 10분 이상 오류율과 latency를 관찰한다.
```

이 예시는 운영 점검 체크리스트의 최소 형태다. 실제 운영에서는 서비스 이름, 포트, 권한, timeout, Secret 위치, 로그 경로를 환경에 맞게 고정해야 한다.

## 운영 체크리스트

- runbook 첫 줄에는 적용 대상 서비스와 증상을 적는다.
- 각 단계는 확인 명령, 기대 결과, 실패 시 다음 행동을 가진다.
- rollback과 restore 결정은 데이터 변경 여부를 기준으로 나눈다.
- 운영 점검 체크리스트 변경 전에는 최근 배포와 관련 장애 이력이 있는지 확인한다.
- 운영 점검 체크리스트 변경 후에는 정상 지표가 돌아왔는지 최소 5~10분은 관찰한다.

## 장애 신호

- 장애 중 문서를 읽어도 어떤 명령을 어디서 실행할지 모른다.
- 체크리스트는 있지만 마지막 검증일이 없다.
- 복구 후 안정화 관찰 시간이 정의되어 있지 않다.
- 운영 점검 체크리스트 이후 사용자가 보는 오류와 운영자가 보는 오류가 서로 다르게 나타난다.

## 안전한 완화 조치

- 운영 점검 체크리스트 문제가 의심되면 먼저 신규 배포와 자동 배치를 멈춘다.
- 운영 점검 체크리스트 변경을 되돌릴 수 있으면 이전 설정이나 이전 artifact로 rollback한다.
- 운영 점검 체크리스트가 데이터 변경과 연결되어 있으면 restore보다 forward fix가 안전한지 검토한다.
- 운영 점검 체크리스트 문제를 우회할 수 있으면 rate limit, feature flag, read-only mode, traffic shift를 검토한다.

## 인프라 담당자와 공유할 자료

- 운영 점검 체크리스트가 적용된 서비스명, 환경, 버전, 적용 시간
- 운영 점검 체크리스트 변경 전후의 오류율, latency p95, 요청량, health check 상태
- 운영 점검 체크리스트와 관련된 로그 샘플, trace id, correlation id, 설정 diff
- 운영 점검 체크리스트에 대해 이미 시도한 조치와 그 결과

## 관찰 명령

```bash
curl -fsS https://api.example.com/actuator/health
kubectl rollout status deploy/zipon-api
promtool check rules alerts.yml
```

운영 점검 체크리스트를 확인할 때는 명령 출력만 저장하지 말고 실행 시각, 대상 환경, 기대값과 실제값을 같이 남긴다.

## 실전 팁

- runbook은 짧은 문장과 실제 명령으로 쓴다.
- 분기 조건은 예/아니오로 답할 수 있게 만든다.
- 운영 점검 체크리스트 문서는 마지막 성공 사례보다 마지막 실패 사례를 기준으로 업데이트한다.
- 운영 점검 체크리스트가 여러 팀 책임에 걸치면 소유자와 승인자를 따로 적는다.

## 위험 신호!

- runbook을 장애 후 업데이트하지 않는다.
- 권한이 없는 명령을 runbook의 핵심 단계로 둔다.
- 운영 점검 체크리스트의 성공 여부를 담당자 감각으로만 판단한다.
- 운영 점검 체크리스트와 관련된 rollback 조건이 문서에 없다.

## 확인 질문

- 운영 점검 체크리스트가 줄이려는 대표 장애는 무엇인가?
	- 장애 중 문서를 읽어도 어떤 명령을 어디서 실행할지 모른다.
- 운영 점검 체크리스트를 운영 기준으로 볼 때 가장 중요한 증거는 무엇인가?
	- 설정 diff, 배포 시간, health check, 오류율, 로그와 trace id를 같은 시간대로 묶은 증거다.
- 운영 점검 체크리스트에서 가장 조심해야 할 대응은 무엇인가?
	- 원인을 확정하기 전에 여러 설정을 동시에 바꾸거나 복구 가능성을 확인하지 않고 파괴적 작업을 실행하는 것이다.

## 리뷰 체크포인트

- 운영 점검 체크리스트 실패 시 사용자가 보는 증상과 운영자가 보는 지표가 연결되는가?
- 운영 점검 체크리스트 담당자, 승인자, rollback 판단자가 문서에 남아 있는가?
- 운영 점검 체크리스트 관련 명령은 읽기 명령과 변경 명령이 구분되어 있는가?
- 운영 점검 체크리스트 결과를 장애 회고에서 재사용할 수 있는 형태로 남길 수 있는가?

## 운영 메모

운영 점검 체크리스트는 한 번 설정하고 끝나는 항목이 아니다. 배포 방식, 트래픽 규모, 팀 권한, 장애 경험이 바뀌면 같은 설정도 위험도가 달라진다.

운영 점검 체크리스트 문서를 업데이트할 때는 마지막 장애나 마지막 배포 실패에서 실제로 헷갈렸던 지점을 우선 반영한다.
