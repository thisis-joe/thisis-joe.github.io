>- 개인 프로젝트에서는 무엇을 줄이고, 기업 운영에서는 무엇을 추가해야 하는가?

## 개요

freshness는 최신성, completeness는 누락 여부, accuracy는 값의 맞음 여부다. 세 문제는 대응 방식이 다르다.

이 문서는 `Data Quality Monitoring` 챕터 안에서 `Freshness Completeness Accuracy` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 매출 대시보드 수치가 0으로 떨어졌지만 API는 정상이라 batch 누락, 스키마 변경, source 오류를 구분해야 하는 상황이다. 이 상황에서 `Freshness Completeness Accuracy` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `Freshness Completeness Accuracy` 관점: 품질 이상을 freshness, completeness, accuracy로 먼저 분류한다.
- `Freshness Completeness Accuracy` 관점: 검증 rule은 pipeline 코드와 독립적으로 실행 가능하게 둔다.
- `Freshness Completeness Accuracy` 관점: 알림 등급은 사용자 영향과 의사결정 영향으로 나눈다.
- `Freshness Completeness Accuracy` 관점: 품질 장애에는 재처리와 임시 공지 기준이 필요하다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `Freshness Completeness Accuracy` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: Freshness Completeness Accuracy
챕터: Data Quality Monitoring
관심사: 데이터가 최신이고 완전하며 정확한지 검증하고, 품질 이상을 알림, 장애 등급, 재처리, 회고로 연결한다
```

```text
pipeline output
  freshness rule
  completeness rule
  accuracy rule
  severity 분류
  replay 또는 incident
```

이 흐름에서는 품질 이상을 source 오류, pipeline 지연, mart 변환 오류, dashboard 문제로 나눠 본다.

## 판단 축

- 품질 이상을 freshness, completeness, accuracy로 먼저 분류한다.
- 검증 rule은 pipeline 코드와 독립적으로 실행 가능하게 둔다.
- 알림 등급은 사용자 영향과 의사결정 영향으로 나눈다.
- 품질 장애에는 재처리와 임시 공지 기준이 필요하다.
- 회고에는 누락된 rule과 늦은 감지 이유를 남긴다.

리뷰에서는 freshness만이 아니라 completeness와 accuracy rule이 함께 있는지 확인한다.

## 예시

```sql
-- freshness
SELECT max(event_time) < now() - interval '30 minutes' AS stale
FROM mart_order_daily;

-- completeness
SELECT abs(source.cnt - mart.cnt) AS diff
FROM (SELECT count(*) cnt FROM orders WHERE created_at >= current_date) source
CROSS JOIN (SELECT count(*) cnt FROM mart_order_daily WHERE order_date = current_date) mart;
```

예시는 하나의 정답이 아니다. 핵심은 `Freshness Completeness Accuracy`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `Freshness Completeness Accuracy` 실패 신호: 대시보드 사용자가 먼저 데이터 이상을 발견한다.
- `Freshness Completeness Accuracy` 실패 신호: freshness만 보고 금액 정확성을 검증하지 않는다.
- `Freshness Completeness Accuracy` 실패 신호: 품질 rule 실패가 조용히 무시된다.
- `Freshness Completeness Accuracy` 실패 신호: 알림 등급이 없어 모든 이상이 같은 긴급도로 취급된다.
- `Freshness Completeness Accuracy` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `Freshness Completeness Accuracy` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `Freshness Completeness Accuracy` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

## 운영 지표

- `freshness_lag`: Freshness Completeness Accuracy 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `completeness_ratio`: Freshness Completeness Accuracy 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `accuracy_mismatch`: Freshness Completeness Accuracy 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `null_ratio`: Freshness Completeness Accuracy 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `rule_failure_count`: Freshness Completeness Accuracy 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.

품질 지표는 API 정상 여부와 별개로 데이터 사용 가능성을 판단하는 데 쓴다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `Freshness Completeness Accuracy` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `데이터 품질` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `데이터 품질` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `데이터 품질` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `Freshness Completeness Accuracy`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `데이터 품질` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `데이터 품질` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `데이터 품질` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `Freshness Completeness Accuracy`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `데이터 품질` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `데이터 품질` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `데이터 품질` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- 품질 이상을 freshness, completeness, accuracy로 먼저 분류하는지 코드와 운영 지표에서 함께 확인한다.
- 검증 rule은 pipeline 코드와 독립적으로 실행 가능하게 두었는지 실패 케이스로 확인한다.
- 알림 등급은 사용자 영향과 의사결정 영향으로 나눈다.
- 품질 장애에는 재처리와 임시 공지 기준이 필요하다.
- 회고에는 누락된 rule과 늦은 감지 이유를 남긴다.

## 위험 신호!

- 대시보드 사용자가 먼저 데이터 이상을 발견한다.
- freshness만 보고 금액 정확성을 검증하지 않는다.
- 품질 rule 실패가 조용히 무시된다.
- 알림 등급이 없어 모든 이상이 같은 긴급도로 취급된다.
- 회고가 사람 실수 지적에서 끝난다.
