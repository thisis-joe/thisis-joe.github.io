## 개요

Redis는 가볍지만 장기 보관, 대규모 replay, partition 확장, 복잡한 consumer 운영에서는 Kafka보다 한계가 빨리 온다.

이 문서는 `Redis Stream PubSub` 챕터 안에서 `Redis 기반 이벤트 처리 한계` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 가벼운 알림 이벤트를 Redis Pub/Sub으로 처리하다가 subscriber 장애 중 메시지가 사라지고 Stream 전환 후 pending entry가 쌓이는 상황이다. 이 상황에서 `Redis 기반 이벤트 처리 한계` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `Redis 기반 이벤트 처리 한계` 관점: 유실 가능성이 허용되면 Pub/Sub, 재처리가 필요하면 Stream을 검토한다.
- `Redis 기반 이벤트 처리 한계` 관점: pending entry를 주기적으로 확인하고 claim 기준을 둔다.
- `Redis 기반 이벤트 처리 한계` 관점: Stream trim 정책이 replay 요구와 충돌하지 않게 한다.
- `Redis 기반 이벤트 처리 한계` 관점: 메모리 사용량과 보관 기간을 같이 관리한다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `Redis 기반 이벤트 처리 한계` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: Redis 기반 이벤트 처리 한계
챕터: Redis Stream PubSub
관심사: Redis Pub/Sub과 Redis Streams의 지속성, ack, pending entry, replay 한계를 구분하고 적절한 사용 범위를 정한다
```

```text
producer
  XADD 또는 PUBLISH
  consumer group/subscriber
  ack 또는 유실
  pending claim
  trim/보관 관리
```

이 흐름에서는 메시지가 사라져도 되는지, pending 상태로 남아야 하는지부터 선택한다.

## 판단 축

- 유실 가능성이 허용되면 Pub/Sub, 재처리가 필요하면 Stream을 검토한다.
- pending entry를 주기적으로 확인하고 claim 기준을 둔다.
- Stream trim 정책이 replay 요구와 충돌하지 않게 한다.
- 메모리 사용량과 보관 기간을 같이 관리한다.
- 장기 이벤트 로그가 필요하면 Kafka를 먼저 검토한다.

리뷰에서는 pending entry와 trim 정책이 장애 복구 요구와 충돌하지 않는지 본다.

## 예시

```redis
XADD order-events * eventType OrderPaid orderId 10042 amount 49000
XGROUP CREATE order-events settlement-group $ MKSTREAM
XREADGROUP GROUP settlement-group consumer-1 COUNT 20 STREAMS order-events >
XACK order-events settlement-group 1719720000000-0
XPENDING order-events settlement-group
```

예시는 하나의 정답이 아니다. 핵심은 `Redis 기반 이벤트 처리 한계`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `Redis 기반 이벤트 처리 한계` 실패 신호: Pub/Sub으로 반드시 전달되어야 하는 이벤트를 처리한다.
- `Redis 기반 이벤트 처리 한계` 실패 신호: pending entry를 확인하지 않아 장애 consumer 메시지가 묶인다.
- `Redis 기반 이벤트 처리 한계` 실패 신호: Stream trim으로 필요한 replay 범위를 지워버린다.
- `Redis 기반 이벤트 처리 한계` 실패 신호: 메모리 한계를 보지 않고 이벤트를 장기 보관한다.
- `Redis 기반 이벤트 처리 한계` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `Redis 기반 이벤트 처리 한계` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `Redis 기반 이벤트 처리 한계` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `Redis 기반 이벤트 처리 한계` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `Redis 이벤트` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `Redis 이벤트` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `Redis 이벤트` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `Redis 기반 이벤트 처리 한계`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `Redis 이벤트` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `Redis 이벤트` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `Redis 이벤트` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `Redis 기반 이벤트 처리 한계`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `Redis 이벤트` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `Redis 이벤트` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `Redis 이벤트` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- 유실 가능성이 허용되면 Pub/Sub, 재처리가 필요하면 Stream을 검토하는지 코드와 운영 지표에서 함께 확인한다.
- pending entry를 주기적으로 확인하고 claim 기준을 두었는지 실패 케이스로 확인한다.
- Stream trim 정책이 replay 요구와 충돌하지 않게 하는지 코드와 운영 지표에서 함께 확인한다.
- 메모리 사용량과 보관 기간을 같이 관리하는지 코드와 운영 지표에서 함께 확인한다.
- 장기 이벤트 로그가 필요하면 Kafka를 먼저 검토하는지 코드와 운영 지표에서 함께 확인한다.

## 위험 신호!

- Pub/Sub으로 반드시 전달되어야 하는 이벤트를 처리한다.
- pending entry를 확인하지 않아 장애 consumer 메시지가 묶인다.
- Stream trim으로 필요한 replay 범위를 지워버린다.
- 메모리 한계를 보지 않고 이벤트를 장기 보관한다.
- Kafka가 필요한 규모를 Redis로 계속 버틴다.
