## 개요

API transaction은 원천 상태 commit을 책임지고 event 발행은 외부 세계에 사실을 알리는 경계다.

이 문서는 `백엔드 서비스와 데이터 파이프라인 연결` 챕터 안에서 `API Transaction과 Event 발행 경계` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 추천 기능을 만들면서 백엔드는 어떤 이벤트를 언제 발행하고 데이터 팀은 어떤 feature와 mart를 기대하는지 맞춰야 하는 상황이다. 이 상황에서 `API Transaction과 Event 발행 경계` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `API Transaction과 Event 발행 경계` 관점: API commit 성공과 downstream 반영 성공을 같은 의미로 말하지 않는다.
- `API Transaction과 Event 발행 경계` 관점: domain event와 integration event를 분리한다.
- `API Transaction과 Event 발행 경계` 관점: 리포트, 검색, 추천의 지연 허용치를 따로 합의한다.
- `API Transaction과 Event 발행 경계` 관점: 데이터 팀에 event 의미와 취소 규칙을 제공한다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `API Transaction과 Event 발행 경계` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: API Transaction과 Event 발행 경계
챕터: 백엔드 서비스와 데이터 파이프라인 연결
관심사: API 트랜잭션과 데이터 파이프라인 경계를 명확히 하고 데이터 팀이 사용할 이벤트, 지연 허용치, 품질 기준을 제공한다
```

```text
API change
  event contract
  downstream consumer
  mart/search/recommendation
  품질 rule
  협업 회고
```

이 흐름에서는 API 변경이 어떤 event, mart, search index, recommendation feature에 영향을 주는지 연결한다.

## 판단 축

- API commit 성공과 downstream 반영 성공을 같은 의미로 말하지 않는다.
- domain event와 integration event를 분리한다.
- 리포트, 검색, 추천의 지연 허용치를 따로 합의한다.
- 데이터 팀에 event 의미와 취소 규칙을 제공한다.
- 기능 배포 체크리스트에 pipeline 영향 항목을 넣는다.

리뷰에서는 데이터 팀이 event 의미와 지연 허용치를 보고 작업할 수 있는지 확인한다.

## 예시

```text
데이터 파이프라인 요청서
- source: order-service
- event: OrderPaid v2
- key: orderId
- 지연 허용: 리포트 30분, 추천 6시간
- 재처리 범위: 최근 90일
- 삭제/취소 표현: OrderCanceled 별도 이벤트
- 품질 규칙: source 금액 합계와 mart 금액 합계 차이 0.1% 이하
```

예시는 하나의 정답이 아니다. 핵심은 `API Transaction과 Event 발행 경계`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `API Transaction과 Event 발행 경계` 실패 신호: API 응답 성공을 검색/추천 반영 성공으로 설명한다.
- `API Transaction과 Event 발행 경계` 실패 신호: 데이터 팀에 컬럼명만 전달하고 이벤트 의미를 설명하지 않는다.
- `API Transaction과 Event 발행 경계` 실패 신호: 취소/삭제 이벤트가 없어 feature가 오래된 상태를 유지한다.
- `API Transaction과 Event 발행 경계` 실패 신호: 기능 배포 후 mart와 quality rule 변경이 누락된다.
- `API Transaction과 Event 발행 경계` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `API Transaction과 Event 발행 경계` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `API Transaction과 Event 발행 경계` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

- `pipeline_freshness`: API Transaction과 Event 발행 경계 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `schema_review_lead_time`: API Transaction과 Event 발행 경계 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `downstream_failure_count`: API Transaction과 Event 발행 경계 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `missing_context_count`: API Transaction과 Event 발행 경계 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.

연동 지표는 기능 배포가 downstream 데이터에 준 영향을 추적하는 데 쓴다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `API Transaction과 Event 발행 경계` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `서비스 연동` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `서비스 연동` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `서비스 연동` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `API Transaction과 Event 발행 경계`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `서비스 연동` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `서비스 연동` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `서비스 연동` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `API Transaction과 Event 발행 경계`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `서비스 연동` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `서비스 연동` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `서비스 연동` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- API commit 성공과 downstream 반영 성공을 같은 의미로 말하지 않는다.
- domain event와 integration event를 분리하는지 코드와 운영 지표에서 함께 확인한다.
- 리포트, 검색, 추천의 지연 허용치를 따로 합의하는지 코드와 운영 지표에서 함께 확인한다.
- 데이터 팀에 event 의미와 취소 규칙을 제공하는지 코드와 운영 지표에서 함께 확인한다.
- 기능 배포 체크리스트에 pipeline 영향 항목을 넣는다.

## 위험 신호!

- API 응답 성공을 검색/추천 반영 성공으로 설명한다.
- 데이터 팀에 컬럼명만 전달하고 이벤트 의미를 설명하지 않는다.
- 취소/삭제 이벤트가 없어 feature가 오래된 상태를 유지한다.
- 기능 배포 후 mart와 quality rule 변경이 누락된다.
- downstream 장애 owner가 불분명하다.
