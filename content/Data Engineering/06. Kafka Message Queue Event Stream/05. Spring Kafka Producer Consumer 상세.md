## 개요

Spring Kafka는 listener와 template을 쉽게 제공하지만 ack mode, transaction, error handler 설정이 처리 보장을 좌우한다.

이 문서는 `Kafka Message Queue Event Stream` 챕터 안에서 `Spring Kafka Producer Consumer` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 주문 이벤트 consumer 중 하나가 실패해 lag가 커지고 같은 메시지가 재전달되어 side effect가 중복될 수 있는 상황이다. 이 상황에서 `Spring Kafka Producer Consumer` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `Spring Kafka Producer Consumer` 관점: partition key는 순서 보장 단위를 기준으로 고른다.
- `Spring Kafka Producer Consumer` 관점: offset commit은 업무 처리 commit 이후로 둔다.
- `Spring Kafka Producer Consumer` 관점: retry 가능한 오류와 DLQ로 보낼 오류를 분리한다.
- `Spring Kafka Producer Consumer` 관점: consumer lag는 처리량 문제인지 poison message인지 나눠 본다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `Spring Kafka Producer Consumer` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: Spring Kafka Producer Consumer
챕터: Kafka Message Queue Event Stream
관심사: 메시지 큐와 이벤트 스트림의 차이를 이해하고 topic, partition, offset, consumer group을 신뢰성 관점에서 설계한다
```

```text
producer
  topic partition
  consumer poll
  business transaction
  offset commit
  retry/DLQ/replay
```

이 흐름에서는 offset commit이 처리 완료 선언이라는 점을 기준으로 DB transaction과 순서를 맞춘다.

## 판단 축

- partition key는 순서 보장 단위를 기준으로 고른다.
- offset commit은 업무 처리 commit 이후로 둔다.
- retry 가능한 오류와 DLQ로 보낼 오류를 분리한다.
- consumer lag는 처리량 문제인지 poison message인지 나눠 본다.
- 중복 처리를 consumer 설계의 기본값으로 둔다.

리뷰에서는 partition key, ack mode, retry/DLQ 분기가 처리 보장과 맞는지 본다.

## 예시

```java
@KafkaListener(topics = "order.events", groupId = "settlement-service")
public void consume(ConsumerRecord<String, OrderPaidEvent> record, Acknowledgment ack) {
    try {
        settlementService.apply(record.key(), record.value());
        ack.acknowledge();
    } catch (PermanentEventException ex) {
        dlqPublisher.publish("order.events.dlq", record, ex);
        ack.acknowledge();
    }
}
```

예시는 하나의 정답이 아니다. 핵심은 `Spring Kafka Producer Consumer`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `Spring Kafka Producer Consumer` 실패 신호: consumer가 DB 저장 전에 offset을 commit한다.
- `Spring Kafka Producer Consumer` 실패 신호: partition key 없이 순서를 기대한다.
- `Spring Kafka Producer Consumer` 실패 신호: DLQ를 버리는 topic처럼 방치한다.
- `Spring Kafka Producer Consumer` 실패 신호: poison message 하나가 partition 처리를 막는다.
- `Spring Kafka Producer Consumer` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `Spring Kafka Producer Consumer` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `Spring Kafka Producer Consumer` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `Spring Kafka Producer Consumer` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `Kafka 스트림` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `Kafka 스트림` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `Kafka 스트림` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `Spring Kafka Producer Consumer`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `Kafka 스트림` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `Kafka 스트림` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `Kafka 스트림` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `Spring Kafka Producer Consumer`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `Kafka 스트림` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `Kafka 스트림` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `Kafka 스트림` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- partition key는 순서 보장 단위를 기준으로 고른다.
- offset commit은 업무 처리 commit 이후로 두었는지 실패 케이스로 확인한다.
- retry 가능한 오류와 DLQ로 보낼 오류를 분리하는지 코드와 운영 지표에서 함께 확인한다.
- consumer lag는 처리량 문제인지 poison message인지 나눠 본다.
- 중복 처리를 consumer 설계의 기본값으로 두었는지 실패 케이스로 확인한다.

## 위험 신호!

- consumer가 DB 저장 전에 offset을 commit한다.
- partition key 없이 순서를 기대한다.
- DLQ를 버리는 topic처럼 방치한다.
- poison message 하나가 partition 처리를 막는다.
- rebalance와 lag 증가를 배포 이벤트와 연결하지 않는다.
