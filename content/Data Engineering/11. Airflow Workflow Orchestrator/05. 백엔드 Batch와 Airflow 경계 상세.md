## 개요

Spring Batch는 업무 처리 구현에 강하고 Airflow는 여러 작업의 순서와 운영 관측에 강하다.

이 문서는 `Airflow Workflow Orchestrator` 챕터 안에서 `백엔드 Batch와 Airflow 경계` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 주문 추출, 결제 정합성 검증, mart 생성, 리포트 발송이 순서대로 실행되어야 하는데 중간 task가 실패하는 상황이다. 이 상황에서 `백엔드 Batch와 Airflow 경계` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `백엔드 Batch와 Airflow 경계` 관점: DAG는 업무 로직보다 의존성과 운영 상태를 표현한다.
- `백엔드 Batch와 Airflow 경계` 관점: task는 재시도해도 안전한 단위로 나눈다.
- `백엔드 Batch와 Airflow 경계` 관점: catchup과 backfill의 데이터 영향 범위를 이해한다.
- `백엔드 Batch와 Airflow 경계` 관점: SLA miss를 task 실패와 별도 사건으로 본다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `백엔드 Batch와 Airflow 경계` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 판단 축

- DAG는 업무 로직보다 의존성과 운영 상태를 표현한다.
- task는 재시도해도 안전한 단위로 나눈다.
- catchup과 backfill의 데이터 영향 범위를 이해한다.
- SLA miss를 task 실패와 별도 사건으로 본다.
- Spring Batch와 Airflow 중 어디가 owner인지 정한다.

리뷰에서는 task가 재시도 가능한 단위인지, catchup이 과거 데이터를 과하게 다시 처리하지 않는지 본다.

## 예시

```python
from airflow.decorators import dag, task
from datetime import datetime

@dag(schedule="0 3 * * *", start_date=datetime(2026, 1, 1), catchup=False)
def daily_order_mart():
    @task(retries=3)
    def extract_orders(ds=None):
        return f"s3://raw/orders/ds={ds}/"

    @task
    def validate_raw(path: str):
        return {"path": path, "valid": True}

    @task
    def build_mart(result: dict):
        assert result["valid"]

    build_mart(validate_raw(extract_orders()))

daily_order_mart()
```

예시는 하나의 정답이 아니다. 핵심은 `백엔드 Batch와 Airflow 경계`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `백엔드 Batch와 Airflow 경계` 실패 신호: DAG에 업무 로직을 너무 많이 넣어 테스트하기 어렵다.
- `백엔드 Batch와 Airflow 경계` 실패 신호: task가 재시도 불가능한 side effect를 포함한다.
- `백엔드 Batch와 Airflow 경계` 실패 신호: catchup이 과거 전체 데이터를 예상 없이 다시 처리한다.
- `백엔드 Batch와 Airflow 경계` 실패 신호: SLA miss와 task failure를 같은 알림으로 처리한다.
- `백엔드 Batch와 Airflow 경계` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `백엔드 Batch와 Airflow 경계` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `백엔드 Batch와 Airflow 경계` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.
