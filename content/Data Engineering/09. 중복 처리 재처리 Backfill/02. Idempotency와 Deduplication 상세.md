>- `Idempotency와 Deduplication` 주제는 서비스 데이터 흐름에서 어떤 판단을 가능하게 하는가?
>- `Idempotency와 Deduplication` 설계에서 key, transaction, checkpoint, retry 경계는 어디에 두어야 하는가?
>- 장애가 났을 때 어떤 지표와 로그로 영향 범위와 재처리 범위를 찾을 수 있는가?
>- 개인 프로젝트에서는 무엇을 줄이고, 기업 운영에서는 무엇을 추가해야 하는가?

## 개요

idempotency는 같은 입력을 여러 번 처리해도 결과가 같게 만드는 설계이고 deduplication은 이미 처리한 입력을 걸러내는 기술이다.

이 문서는 `중복 처리 재처리 Backfill` 챕터 안에서 `Idempotency와 Deduplication` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 누락된 3개월치 주문 집계를 다시 채우는 동안 일부 이벤트가 중복 도착하고 downstream mart가 흔들리는 상황이다. 이 상황에서 `Idempotency와 Deduplication` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `Idempotency와 Deduplication` 관점: 재처리 대상 범위를 명시한다.
- `Idempotency와 Deduplication` 관점: 이미 처리한 입력을 구분할 key를 둔다.
- `Idempotency와 Deduplication` 관점: 운영 부하에 따라 batch size와 sleep을 조절한다.
- `Idempotency와 Deduplication` 관점: 재처리 전후 count와 금액 합계를 비교한다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `Idempotency와 Deduplication` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: Idempotency와 Deduplication
챕터: 중복 처리 재처리 Backfill
관심사: 중복과 재처리를 예외가 아니라 운영 조건으로 보고 idempotency, deduplication, checkpoint, 속도 제한을 설계한다
```

```text
대상 범위 선정
  checkpoint 조회
  작은 batch 처리
  중복 방지
  속도 제한
  검증 쿼리
```

이 흐름에서는 재처리가 운영 트래픽에 주는 영향을 보면서 batch size와 중단 조건을 조절한다.

## 판단 축

- 재처리 대상 범위를 명시한다.
- 이미 처리한 입력을 구분할 key를 둔다.
- 운영 부하에 따라 batch size와 sleep을 조절한다.
- 재처리 전후 count와 금액 합계를 비교한다.
- 수동 작업도 runbook과 작업 로그를 남긴다.

리뷰에서는 재처리 대상 범위, 속도 제한, 완료 검증 쿼리가 문서에 있는지 확인한다.

## 예시

```text
backfill_name: order-summary-2026-q2
range: order_id 1000000..9000000
batch_size: 10000
sleep_ms: 300
checkpoint: last_success_order_id
stop_condition: api_p95 > 800ms or replica_lag > 30s
verification: source_sum == mart_sum
```

예시는 하나의 정답이 아니다. 핵심은 `Idempotency와 Deduplication`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `Idempotency와 Deduplication` 실패 신호: backfill 범위와 완료 조건이 없다.
- `Idempotency와 Deduplication` 실패 신호: 운영 peak 시간에 대량 재처리를 시작한다.
- `Idempotency와 Deduplication` 실패 신호: 중복 안전성 없이 같은 이벤트를 다시 흘린다.
- `Idempotency와 Deduplication` 실패 신호: 검증 없이 checkpoint만 마지막으로 옮긴다.
- `Idempotency와 Deduplication` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `Idempotency와 Deduplication` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `Idempotency와 Deduplication` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

## 운영 지표

- `processed_rows`: Idempotency와 Deduplication 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `duplicate_count`: Idempotency와 Deduplication 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `checkpoint_position`: Idempotency와 Deduplication 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `backfill_throughput`: Idempotency와 Deduplication 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `api_latency_during_backfill`: Idempotency와 Deduplication 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.

재처리 지표는 운영 부하와 보정 진행률을 동시에 보는 데 쓴다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `Idempotency와 Deduplication` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `재처리` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `재처리` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `재처리` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `Idempotency와 Deduplication`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `재처리` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `재처리` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `재처리` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `Idempotency와 Deduplication`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `재처리` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `재처리` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `재처리` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- 재처리 대상 범위를 명시하는지 코드와 운영 지표에서 함께 확인한다.
- 이미 처리한 입력을 구분할 key를 두었는지 실패 케이스로 확인한다.
- 운영 부하에 따라 batch size와 sleep을 조절하는지 코드와 운영 지표에서 함께 확인한다.
- 재처리 전후 count와 금액 합계를 비교하는지 코드와 운영 지표에서 함께 확인한다.
- 수동 작업도 runbook과 작업 로그를 남긴다.

## 위험 신호!

- backfill 범위와 완료 조건이 없다.
- 운영 peak 시간에 대량 재처리를 시작한다.
- 중복 안전성 없이 같은 이벤트를 다시 흘린다.
- 검증 없이 checkpoint만 마지막으로 옮긴다.
- 수동 SQL 수정 내역을 남기지 않는다.

- `Idempotency와 Deduplication`의 완료를 무엇으로 검증하는가?
	- source와 target의 count, 합계, 최신 시각, 품질 rule 결과로 검증한다.
