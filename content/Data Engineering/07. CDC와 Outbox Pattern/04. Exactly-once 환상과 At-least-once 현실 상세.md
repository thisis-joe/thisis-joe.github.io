## 개요

end-to-end exactly-once는 대부분 환상에 가깝다. 현실적인 설계는 at-least-once와 idempotent consumer다.

이 문서는 `CDC와 Outbox Pattern` 챕터 안에서 `Exactly-once 환상과 At-least-once 현실` 주제를 백엔드 서비스 데이터 흐름의 일부로 정리한다. 중요한 것은 구현 API 이름이 아니라 source, event, processor, target, quality check가 어떤 계약으로 이어지는지다.

기준 상황은 주문 저장은 성공했지만 Kafka 발행이 실패하거나, 발행은 됐지만 DB commit이 실패해 downstream 데이터가 어긋나는 상황이다. 이 상황에서 `Exactly-once 환상과 At-least-once 현실` 주제를 제대로 설계하지 않으면 API는 정상이어도 downstream 데이터가 늦거나, 중복되거나, 누락되거나, 잘못된 지표로 사용될 수 있다.

## 원리

- `Exactly-once 환상과 At-least-once 현실` 관점: 업무 row 변경과 outbox insert를 같은 transaction에 둔다.
- `Exactly-once 환상과 At-least-once 현실` 관점: publisher 장애는 pending outbox로 복구한다.
- `Exactly-once 환상과 At-least-once 현실` 관점: CDC lag와 outbox pending count를 동시에 본다.
- `Exactly-once 환상과 At-least-once 현실` 관점: published row 정리는 보관 기간과 감사 요구를 함께 고려한다.

이 원칙들은 모두 source, key, 처리 단위, 재처리 가능성으로 연결된다. `Exactly-once 환상과 At-least-once 현실` 문서를 읽을 때는 "어떤 데이터가 사실인가", "어느 단위부터 다시 처리할 수 있는가", "완료를 어떤 쿼리로 검증하는가"를 계속 확인한다.

## 흐름

```text
주제: Exactly-once 환상과 At-least-once 현실
챕터: CDC와 Outbox Pattern
관심사: DB 저장과 이벤트 발행 사이의 dual write 문제를 outbox와 CDC로 줄이고, 발행 지연과 정리 전략을 관리한다
```

```text
service transaction
  business row 변경
  outbox row insert
  CDC 또는 publisher
  Kafka publish
  consumer idempotency
```

이 흐름에서는 service transaction 안의 outbox 기록과 transaction 밖의 발행 지연을 분리해서 본다.

## 판단 축

- 업무 row 변경과 outbox insert를 같은 transaction에 둔다.
- publisher 장애는 pending outbox로 복구한다.
- CDC lag와 outbox pending count를 동시에 본다.
- published row 정리는 보관 기간과 감사 요구를 함께 고려한다.
- exactly-once보다 idempotent consumer를 우선 설계한다.

리뷰에서는 outbox row가 commit된 뒤 발행 전까지 얼마나 쌓일 수 있는지 확인한다.

## 예시

```sql
CREATE TABLE outbox_events (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_type varchar(50) NOT NULL,
    aggregate_id varchar(100) NOT NULL,
    event_type varchar(100) NOT NULL,
    event_version int NOT NULL,
    payload jsonb NOT NULL,
    status varchar(20) NOT NULL DEFAULT 'PENDING',
    created_at timestamp NOT NULL DEFAULT now(),
    published_at timestamp NULL
);
```

```java
@Transactional
public void pay(OrderPayCommand command) {
    Order order = orderRepository.getById(command.orderId());
    order.markPaid(command.paymentId());
    outboxRepository.save(OutboxEvent.orderPaid(order));
}
```

예시는 하나의 정답이 아니다. 핵심은 `Exactly-once 환상과 At-least-once 현실`에서 처리 key, 상태 기록, 실패 보관, 재처리 범위가 코드나 SQL에 드러나야 한다는 점이다.

## 실패 모델

- `Exactly-once 환상과 At-least-once 현실` 실패 신호: DB 저장 후 바로 Kafka 발행을 별도 try-catch로 처리한다.
- `Exactly-once 환상과 At-least-once 현실` 실패 신호: outbox pending count를 보지 않는다.
- `Exactly-once 환상과 At-least-once 현실` 실패 신호: published outbox를 정리하지 않아 운영 DB가 커진다.
- `Exactly-once 환상과 At-least-once 현실` 실패 신호: Debezium connector lag를 서비스 지연으로 해석하지 못한다.
- `Exactly-once 환상과 At-least-once 현실` 복구 기준: transient failure는 제한된 retry와 backoff로 처리하고, permanent failure는 사람이 분류할 수 있는 위치에 남긴다.
- `Exactly-once 환상과 At-least-once 현실` 재처리 기준: 같은 입력을 다시 넣어도 결과가 안전한지 idempotency 또는 deduplication으로 확인한다.
- `Exactly-once 환상과 At-least-once 현실` 완료 기준: 처리 건수뿐 아니라 source와 target의 의미 있는 합계와 최신 시각을 비교한다.

## 운영 지표

- `outbox_pending_count`: Exactly-once 환상과 At-least-once 현실 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `cdc_lag`: Exactly-once 환상과 At-least-once 현실 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `connector_error_count`: Exactly-once 환상과 At-least-once 현실 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `duplicate_event_count`: Exactly-once 환상과 At-least-once 현실 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.
- `cleanup_lag`: Exactly-once 환상과 At-least-once 현실 관점에서 지연, 실패, 누락, 재처리 필요성을 판단하는 지표다.

outbox 지표는 DB commit 이후 발행 지연이 얼마나 쌓였는지 보는 데 쓴다.

## 개인 프로젝트 기준

- 개인 프로젝트에서 `Exactly-once 환상과 At-least-once 현실` 주제를 다룰 때는 별도 플랫폼보다 단순한 table, log, scheduler로 시작해도 된다.
- `Outbox CDC` 관점의 개인 프로젝트 기준을 작게 시작하되 재실행 가능성은 남긴다.
- `Outbox CDC` 실습에서는 실패 로그와 처리 이력을 먼저 만든다.
- `Outbox CDC` 검증은 count, 최신 시각, 샘플 row 비교부터 시작한다.

## 기업 운영 기준

- `Exactly-once 환상과 At-least-once 현실`의 owner, 알림 채널, 지연 허용치, 재처리 권한을 명시한다.
- `Outbox CDC` 운영에서는 owner, alert, SLA 또는 지연 허용치를 명시한다.
- `Outbox CDC` 변경은 producer, consumer, 운영자가 함께 리뷰한다.
- `Outbox CDC` 장애 회고에는 재처리 범위와 품질 검증 결과를 남긴다.

## 협업 포인트

- 데이터 팀에는 `Exactly-once 환상과 At-least-once 현실`의 business meaning, key, version, 취소/삭제 표현을 제공한다.
- `Outbox CDC` 협업에서는 source, key, 예상 처리량, 보관 기간을 공유한다.
- `Outbox CDC` 관련 DBA/인프라 협의에는 lock, lag, storage, peak time을 포함한다.
- `Outbox CDC` QA에는 정상 흐름뿐 아니라 중복, 지연, 실패 후 replay 케이스를 제공한다.

## 실전 팁

- 업무 row 변경과 outbox insert를 같은 transaction에 두었는지 실패 케이스로 확인한다.
- publisher 장애는 pending outbox로 복구하는지 코드와 운영 지표에서 함께 확인한다.
- CDC lag와 outbox pending count를 동시에 본다.
- published row 정리는 보관 기간과 감사 요구를 함께 고려하는지 코드와 운영 지표에서 함께 확인한다.
- exactly-once보다 idempotent consumer를 우선 설계하는지 코드와 운영 지표에서 함께 확인한다.

## 위험 신호!

- DB 저장 후 바로 Kafka 발행을 별도 try-catch로 처리한다.
- outbox pending count를 보지 않는다.
- published outbox를 정리하지 않아 운영 DB가 커진다.
- Debezium connector lag를 서비스 지연으로 해석하지 못한다.
- consumer 멱등성 없이 outbox만으로 exactly-once를 기대한다.

## 확인 질문

- `Exactly-once 환상과 At-least-once 현실`에서 재처리 시작점을 어떻게 찾을 수 있는가?
	- `Outbox CDC` 주제가 사용하는 좌표를 기록한다. 예를 들어 offset, checkpoint, range, DAG run, 처리 이력 중 하나다.
- `Exactly-once 환상과 At-least-once 현실`에서 중복 입력은 어떤 결과를 만드는가?
	- 같은 key가 다시 들어와도 결과가 안전한지 중복 입력 테스트로 확인한다.
- `Exactly-once 환상과 At-least-once 현실`의 완료를 무엇으로 검증하는가?
	- source와 target의 count, 합계, 최신 시각, 품질 rule 결과로 검증한다.
