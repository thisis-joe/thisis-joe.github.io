# Load Balancer / Health Check / Traffic Routing

### 3줄 요약
- Load Balancer는 여러 backend로 traffic을 나누고 장애 target을 제외해 가용성을 높인다.
- Health check가 정상이어도 실제 요청은 실패할 수 있으므로 readiness와 실제 기능 검증 범위를 신중히 정해야 한다.
- idle timeout, draining, stickiness, routing rule은 배포와 실시간 연결 장애에 직접 영향을 준다.

### 핵심 정리
- LB는 listener, rule, target group, health check, routing algorithm으로 구성된다.
- liveness는 프로세스 생존, readiness는 traffic 수용 가능성을 뜻한다.
- draining은 배포나 scale-in 때 기존 연결을 부드럽게 종료하는 장치다.
- SSE, WebSocket, long polling은 LB idle timeout과 stickiness를 특별히 고려한다.

### 헷갈리는 지점
- Health check 200이면 서비스가 정상이라고 생각하기 쉽다.
	- 핵심 판단 포인트는 실제 핵심 dependency와 요청 경로는 별도로 확인해야 한다.
- LB가 알아서 모든 장애를 숨긴다고 생각하기 쉽다.
	- 핵심 판단 포인트는 모든 target이 unhealthy이거나 app이 부분 장애면 LB도 해결하지 못한다.
- 배포와 네트워크 설정을 분리해서 보기 쉽다.
	- 핵심 판단 포인트는 draining, readiness, connection close는 배포 품질의 일부다.

### 확인 질문
- readiness와 liveness를 나누는 이유는 무엇인가?
	- 프로세스가 살아 있어도 traffic을 받을 준비가 안 된 상태를 분리하기 위해서다.
- health check는 정상인데 실제 요청이 실패하는 이유는 무엇인가?
	- health path가 너무 얕거나 실제 요청과 다른 Host, protocol, dependency를 사용하기 때문이다.
- draining이 필요한 이유는 무엇인가?
	- 기존 연결과 진행 중 요청을 갑자기 끊지 않고 target을 제외하기 위해서다.
