# HTTP 기본 구조

### 3줄 요약
- HTTP는 request와 response로 리소스 상태를 주고받는 애플리케이션 계층 프로토콜이다.
- 메서드, path, header, body, status code를 구분하면 API 계약과 장애 원인을 함께 설명할 수 있다.
- HTTP 버전과 message framing을 이해하면 keep-alive, streaming, proxy 오류를 더 잘 다룬다.

### 핵심 정리
- HTTP 메시지는 start line, header, body로 구성된다.
- body가 어디서 끝나는지는 `Content-Length`, chunked transfer, connection close 같은 framing 규칙에 좌우된다.
- HTTP/1.1, HTTP/2, HTTP/3는 같은 의미 계층을 공유하지만 연결 관리와 multiplexing 방식이 다르다.
- 백엔드는 HTTP를 단순 JSON 운반 수단이 아니라 proxy와 cache가 해석하는 계약으로 봐야 한다.

### 헷갈리는 지점
- HTTP body만 보면 된다고 생각하기 쉽다.
	- 핵심 판단 포인트는 실무 장애는 header, method, status, framing에서 자주 난다.
- HTTP/2면 모든 문제가 빨라진다고 생각하기 쉽다.
	- 핵심 판단 포인트는 multiplexing은 좋지만 upstream, LB, app 한계는 여전히 남는다.
- Content-Length를 대충 다뤄도 된다고 생각하기 쉽다.
	- 핵심 판단 포인트는 body 크기와 framing 오류는 400, 413, 502로 이어진다.

### 확인 질문
- HTTP 메시지에서 header가 중요한 이유는 무엇인가?
	- 인증, 캐시, CORS, content negotiation, routing, tracing 같은 운영 계약이 header로 표현되기 때문이다.
- HTTP/1.1과 HTTP/2의 실무 차이는 무엇인가?
	- 연결 재사용과 multiplexing 방식이 달라 latency와 proxy 설정에 영향을 준다.
- body framing을 알아야 하는 이유는 무엇인가?
	- proxy와 server가 body 끝을 다르게 이해하면 요청 지연, 400, 413, 502가 날 수 있기 때문이다.
