# Cookie / Session / SameSite / CORS

### 3줄 요약
- Cookie와 Session은 인증 상태를 HTTP 위에 유지하는 대표 방식이다.
- SameSite, Secure, HttpOnly, Domain, Path는 로그인 안정성과 보안에 직접 영향을 준다.
- CORS는 서버 간 통신 문제가 아니라 브라우저가 cross-origin 요청을 제한하는 보안 정책이다.

### 핵심 정리
- Cookie는 브라우저가 조건에 맞는 요청에 자동으로 붙이는 header다. 조건은 domain, path, secure, sameSite, 만료 정책에 좌우된다.
- Session은 서버나 저장소에 상태를 두고 cookie에는 session id를 담는 방식이다. 분산 환경에서는 sticky session, shared store, session fixation을 고려한다.
- CORS는 Origin이 다른 브라우저 요청에서 서버가 허용 범위를 명시하게 하는 정책이다. preflight와 credential 요청을 분리해야 한다.
- 인증 문제는 네트워크처럼 보이지만 실제로는 cookie 미전송, redirect, SameSite, secure, domain mismatch인 경우가 많다.

### 헷갈리는 지점
- CORS를 서버 간 API 호출 문제로 오해하기 쉽다.
	- 핵심 판단 포인트는 CORS는 브라우저가 적용하는 정책이다.
- 쿠키가 발급되면 항상 전송된다고 생각하기 쉽다.
	- 핵심 판단 포인트는 Domain, Path, Secure, SameSite 조건을 만족해야 한다.
- 세션을 쓰면 LB 설정은 상관없다고 생각하기 쉽다.
	- 핵심 판단 포인트는 서버 메모리 세션이면 sticky나 shared store가 필요할 수 있다.

### 확인 질문
- CORS와 인증 실패를 구분하는 기준은 무엇인가?
	- CORS는 브라우저 콘솔과 preflight 응답에서 보이고, 인증 실패는 서버가 401/403을 응답하는 형태로 보인다.
- SameSite=None 쿠키에 Secure가 필요한 이유는 무엇인가?
	- cross-site 전송을 허용하는 쿠키는 HTTPS에서만 보내도록 제한하기 위해서다.
- 분산 세션에서 인프라와 맞춰야 할 것은 무엇인가?
	- sticky session 여부, shared session store, cookie domain/path, TLS termination이다.
