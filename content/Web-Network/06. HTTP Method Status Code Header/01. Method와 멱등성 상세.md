>- Method와 멱등성의 백엔드 실무 의미는 무엇인가?
>- Method와 멱등성에서 장애가 나면 어떤 증거부터 확인해야 하는가?
>- 이 주제를 실무에서 설계할 때 가장 조심할 점은 무엇인가?

## 개요

`Method와 멱등성` 문서는 `HTTP Method / Status Code / Header` 주제를 단순 암기가 아니라 운영 가능한 지식으로 바꾸는 부분이다. 백엔드 개발자는 이 주제를 통해 요청이 어디서 만들어지고, 어느 계층을 지나며, 실패했을 때 어떤 증거를 남기는지 설명할 수 있어야 한다.

- Method는 서버에 기대하는 동작의 의미를 표현한다.
- 멱등성은 retry와 중복 처리 방지의 기준이다.
- 결제/주문은 POST라도 idempotency key로 중복 실행을 막아야 한다.

## 왜 백엔드 개발자가 알아야 하는가

백엔드 코드는 HTTP 요청의 마지막 일부만 처리하는 것처럼 보이지만, 실제 장애는 코드 앞뒤의 경계에서 많이 발생한다. 이 문서를 읽으면 “서버가 느리다”, “네트워크 문제 같다”, “가끔 502가 난다” 같은 모호한 증상을 구체적인 계층과 증거로 바꿀 수 있다.

- 사용자에게 보이는 실패를 애플리케이션 코드, 프록시, 로드밸런서, DNS, TLS, 브라우저 정책 중 어디와 연결할지 판단한다.
- 인프라 담당자에게 확인을 요청할 때 필요한 정보와 불필요한 추측을 구분한다.
- 개인 프로젝트에서도 운영자처럼 로그, 명령, 설정, 재현 절차를 남길 수 있다.

## 요청 흐름에서의 위치

`HTTP Method / Status Code / Header` 흐름 안에서 `Method와 멱등성` 주제가 실제 요청 처리와 운영 판단을 연결하는 지점이다.

이 위치를 모르면 장애가 앱 내부인지, 앱으로 들어오기 전인지, 앱이 호출한 외부 의존성인지 구분하기 어렵다. 반대로 위치를 알면 확인해야 할 로그와 명령이 자연스럽게 좁혀진다.

## 원리

- Method는 서버에 기대하는 동작의 의미를 표현한다.
- 멱등성은 retry와 중복 처리 방지의 기준이다.
- 결제/주문은 POST라도 idempotency key로 중복 실행을 막아야 한다.

핵심은 계층을 나누되 계층 사이의 계약을 함께 보는 것이다. HTTP header, timeout, connection, TLS, cache, health check는 모두 한 계층에만 머물지 않고 다음 계층의 동작을 바꾼다.

## 핵심 판단 기준

- 이 주제가 사용자 요청의 전단, 애플리케이션 내부, 후단 의존성 중 어디에 있는지 먼저 표시한다.
- 성공한 요청과 실패한 요청을 비교할 때 status code, response header, latency, request id, server log 도달 여부를 함께 본다.
- 설정값은 단독으로 보지 않고 client, proxy, load balancer, application, database, external API 사이의 순서와 관계로 본다.
- 운영 문서에는 기본값이 아니라 우리 서비스에서 실제 적용된 값을 남긴다.

## 실무에서 자주 만나는 문제

- POST 재시도로 중복 결제가 난다.
- GET에 상태 변경을 숨겨 cache와 crawler가 문제를 만든다.
- DELETE를 비멱등하게 구현해 재시도 때 500을 낸다.

이 문제들은 대부분 한 번에 재현되지 않는다. 그래서 평균값보다 p95/p99, 특정 사용자, 특정 네트워크, 특정 endpoint, 특정 시간대의 차이를 보는 습관이 필요하다.

## 디버깅 방법

- CLI 명령과 로그를 같은 시각대로 맞춘다.
- 성공 요청과 실패 요청의 헤더, status, latency를 비교한다.
- 응답 주체가 app인지 proxy인지 먼저 확인한다.

가능하면 한 명령의 결과로 결론을 내리지 않는다. CLI 결과, 브라우저 DevTools, proxy log, application log, metric, trace를 같은 시간대에 놓고 서로 맞는지 확인한다.

## 코드로 확인하기

```bash
curl -vI https://example.com/api/orders
curl -X POST https://example.com/api/orders \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-20260630-001' \
  -d '{"productId": 10, "quantity": 1}'
```

`Server`, `Via`, `Location`, `Retry-After`, `X-Request-ID` 같은 헤더는 응답을 만든 계층과 다음 확인 위치를 알려준다.

코드와 명령은 “실행해 볼 수 있는 형태”로 남겨야 한다. 그래야 장애가 났을 때 문서를 읽는 시간이 아니라 바로 검증하는 시간이 된다.

## 주니어가 자주 하는 오해

- 눈앞의 status code를 최종 원인으로 해석한다.
- 애플리케이션 로그에 없으면 애플리케이션과 무관하다고 판단한다.
- 라이브러리와 인프라의 기본값을 운영 정책이라고 착각한다.
- 재현이 한 번 실패하면 간헐적 장애를 없는 문제로 취급한다.

## 시니어의 설계 판단 기준

- 실패가 발생했을 때 어느 계층에서 어떤 증거가 남을지 먼저 설계한다.
- timeout, retry, pool, cache, health check는 사용자 경험과 downstream 보호를 함께 만족하도록 정한다.
- rare case를 모두 막으려 하기보다 영향 범위, 감지 속도, 완화 절차를 현실적으로 설계한다.
- 인프라와 보안의 제약을 뒤늦은 방해물이 아니라 시스템 요구사항으로 다룬다.

## 인프라 협업 포인트

- DNS, TLS, LB, proxy, WAF, firewall, service discovery 변경은 적용 전후 검증 명령을 함께 공유한다.
- 장애 제보에는 발생 시각, URL, method, status, response header, request id, client IP 대역, 최근 변경을 포함한다.
- 앱이 readiness, graceful shutdown, request id, access log를 제공하면 인프라 팀의 확인 범위가 크게 줄어든다.

## 실전 팁

- “네트워크 문제”라는 말을 쓰기 전에 DNS, TCP, TLS, HTTP, proxy, app log 중 어디까지 확인했는지 적는다.
- 설정 변경은 값 하나보다 앞뒤 계층과의 정렬이 중요하다.
- 개인 프로젝트에서도 `curl -w`, health endpoint, access log, 인증서 만료 알림은 기본으로 둔다.
- 기업 운영에서는 SLO, error budget, rollback, canary, capacity planning까지 연결해서 본다.

## 위험 신호!

- 장애 보고에 status code만 있고 응답 주체와 request id가 없다.
- timeout과 retry가 여러 계층에 흩어져 있지만 문서화되어 있지 않다.
- health check는 200인데 실제 핵심 기능은 실패한다.
- proxy나 LB 설정 변경 후 애플리케이션 팀이 어떤 header와 path가 들어오는지 모른다.

## 확인 질문

- `Method와 멱등성`에서 가장 먼저 확인할 증거는 무엇인가?
	- status code만 보지 말고 응답 주체, latency, request id, 요청이 도달한 마지막 로그 위치를 함께 확인한다.
- 이 주제를 인프라 담당자와 이야기할 때 준비해야 할 정보는 무엇인가?
	- 발생 시각, URL, method, header, client 영향 범위, 최근 변경, CLI 확인 결과, 기대 동작과 실제 동작이다.
- 개인 프로젝트에서 이 주제를 적용한다면 무엇부터 할 수 있는가?
	- 기본 timeout과 로그를 명시하고, 배포 후 `curl` 기반 smoke test와 health check를 남긴다.
