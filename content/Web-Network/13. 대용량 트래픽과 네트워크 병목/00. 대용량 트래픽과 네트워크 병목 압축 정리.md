# 대용량 트래픽과 네트워크 병목

### 3줄 요약
- 대용량 트래픽 장애는 CPU만의 문제가 아니라 connection, DB pool, lock, cache, external API, NAT, bandwidth가 함께 만든다.
- 평균 응답시간보다 p95/p99, error rate, saturation, queue length를 봐야 병목을 찾을 수 있다.
- 백엔드는 개인 프로젝트에서도 부하 테스트, rate limit, cache, graceful degradation을 설계할 수 있어야 한다.

### 핵심 정리
- 병목은 utilization, saturation, error로 관찰한다. CPU가 낮아도 connection pool이나 DB lock이 포화될 수 있다.
- 대량 요청은 queue를 만들고 queue는 tail latency를 만든다.
- Rate limiting과 backpressure는 서비스를 무너뜨리지 않기 위한 방어 장치다.
- 희귀한 장애로는 ephemeral port exhaustion, DNS resolver limit, NAT gateway port exhaustion, TLS handshake spike가 있다.

### 헷갈리는 지점
- CPU가 낮으면 병목이 없다고 생각하기 쉽다.
	- 핵심 판단 포인트는 connection, lock, pool, queue, external API saturation을 함께 본다.
- scale out이 모든 병목을 해결한다고 생각하기 쉽다.
	- 핵심 판단 포인트는 DB, cache, external API, NAT 같은 공유 자원이 먼저 찰 수 있다.
- 부하 테스트는 RPS만 높이면 된다고 생각하기 쉽다.
	- 핵심 판단 포인트는 실제 사용자 패턴, payload, think time, cache hit ratio를 반영해야 한다.

### 확인 질문
- p99 latency가 중요한 이유는 무엇인가?
	- 일부 느린 요청이 사용자 경험과 resource 점유를 크게 악화시킬 수 있기 때문이다.
- scale out 후에도 장애가 나는 이유는 무엇인가?
	- 공유 downstream 자원이나 connection 한계가 그대로일 수 있기 때문이다.
- backpressure의 목적은 무엇인가?
	- 시스템이 감당할 수 없는 요청을 일찍 제한해 전체 장애를 막는 것이다.
