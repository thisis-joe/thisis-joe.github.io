# Cache / CDN / Conditional Request

### 3줄 요약
- 캐시는 응답을 재사용해 성능과 비용을 줄이지만 오래된 응답을 정답처럼 보이게 만들 수 있다.
- CDN은 사용자 가까운 edge에서 응답을 제공하지만 origin, purge, cache key, header 정책을 정확히 설계해야 한다.
- 조건부 요청은 `ETag`와 `Last-Modified`로 변경되지 않은 리소스의 전송 비용을 줄인다.

### 핵심 정리
- HTTP cache는 `Cache-Control`, `ETag`, `Last-Modified`, `Vary` 같은 header로 동작한다.
- CDN은 origin 앞에 있는 reverse proxy cache다. cache HIT이면 origin log가 없을 수 있다.
- Cache key에 query, header, cookie가 어떻게 포함되는지 모르면 사용자별 데이터가 섞일 수 있다.
- 정적 자원은 fingerprint와 long max-age가 잘 맞고, 개인화 API는 신중히 캐시해야 한다.

### 헷갈리는 지점
- 캐시는 성능 기능이므로 안전하다고 생각하기 쉽다.
	- 핵심 판단 포인트는 정합성, 개인정보, 권한 변경 지연까지 함께 본다.
- CDN HIT이면 서버가 정상이라고 생각하기 쉽다.
	- 핵심 판단 포인트는 origin까지 요청이 가지 않았을 수 있다.
- 304를 에러로 보기 쉽다.
	- 핵심 판단 포인트는 304는 body를 다시 보내지 않아도 된다는 정상 조건부 응답이다.

### 확인 질문
- Cache-Control에서 private과 public의 차이는 무엇인가?
	- public은 공유 캐시에 저장될 수 있고 private은 사용자 브라우저 같은 개인 캐시에 한정된다.
- CDN purge가 필요한 상황은 무엇인가?
	- 잘못된 응답이 edge에 저장되었거나 긴 TTL 리소스를 즉시 교체해야 할 때다.
- Vary 헤더가 중요한 이유는 무엇인가?
	- 요청 헤더 차이에 따라 캐시 키를 나눠야 잘못된 응답 재사용을 막을 수 있기 때문이다.
