# Proxy / Reverse Proxy / Gateway

### 3줄 요약
- Proxy는 클라이언트와 서버 사이에서 요청을 중계하고 reverse proxy는 서버 앞단에서 routing, TLS, buffering, 보안을 담당한다.
- Gateway는 인증, rate limit, routing, observability 같은 API 경계 정책을 중앙화한다.
- 백엔드는 proxy가 바꾸는 Host, scheme, client IP, path, timeout, body size를 알고 있어야 한다.

### 핵심 정리
- Reverse proxy는 TLS termination, path rewrite, upstream 선택, header 추가, buffering, timeout을 처리한다.
- Forwarded header는 원래 client IP와 scheme을 전달하지만 신뢰 가능한 proxy에서 온 값만 믿어야 한다.
- Gateway나 WAF가 만든 4xx/5xx는 애플리케이션 로그에 남지 않을 수 있다.
- path rewrite와 trailing slash는 백엔드 routing 장애의 흔한 원인이다.

### 헷갈리는 지점
- 프록시는 단순 통로라고 생각하기 쉽다.
	- 핵심 판단 포인트는 프록시는 HTTP 계약을 바꾸거나 차단할 수 있는 능동 계층이다.
- X-Forwarded-For를 그대로 믿기 쉽다.
	- 핵심 판단 포인트는 클라이언트도 조작할 수 있으므로 신뢰 가능한 proxy chain만 인정한다.
- 502가 나오면 앱이 죽었다고만 생각하기 쉽다.
	- 핵심 판단 포인트는 proxy 설정, upstream protocol, DNS, TLS, timeout도 확인한다.

### 확인 질문
- reverse proxy 뒤에서 scheme을 신뢰하려면 무엇이 필요한가?
	- 신뢰 가능한 proxy가 설정한 `X-Forwarded-Proto` 또는 `Forwarded`를 앱이 올바르게 해석해야 한다.
- path rewrite 장애는 어떻게 드러나는가?
	- proxy는 요청을 보냈지만 앱에서는 404나 잘못된 route로 보일 수 있다.
- 프록시 timeout이 중요한 이유는 무엇인가?
	- 앱이 처리 중이어도 proxy가 먼저 끊으면 사용자는 504나 연결 종료를 보게 되기 때문이다.
