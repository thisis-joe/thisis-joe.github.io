# 결론
결론은 이렇다. 이해되면 바로 다음 문서로..

```text
Spring Security을 적용한 로그인은 Controller가 직접 로그인 성공/실패를 판단하지 않는다.
사용자의 자격 증명을 Authentication으로 만들고,
AuthenticationManager와 AuthenticationProvider가 검증한 뒤,
성공한 인증 정보를 SecurityContextHolder에 넣고,
이후 AuthorizationFilter가 권한을 판단하도록 만드는 구조다.

JWT 방식에서는 세션처럼 서버가 인증 상태를 저장하지 않으므로,
매 요청마다 토큰으로 Authentication을 다시 구성해야 하고,
로그아웃/탈취 대응을 위해 refresh token 저장소,
access token jti denylist, token version 같은 별도 무효화 전략이 필요하다.
```

# 결론에 도달해보자!
## 전형적인 MVC 기반 로그인의 문제점

처음 MVC 구조를 배운뒤 로그인의 순서에 대해 답변해 본다면, 자연스럽게 아래와 같을 것이다.

```text
1. 사용자가 아이디/비밀번호 입력
2. Controller가 받음
3. DB에서 사용자 조회
4. 비밀번호 맞는지 if문으로 비교
5. 맞으면 로그인 성공
6. 틀리면 로그인 실패
```

> [!example] 예시
> 
> ```java
> @PostMapping("/login")
> public ResponseEntity<?> login(@RequestBody LoginRequest request) {
> 	User user = userMapper.findByUsername(request.username());
> 
> 	if (user == null) {
> 		return ResponseEntity.status(401).build();
> 	}
> 
> 	if (!request.password().equals(user.getPassword())) {
> 		return ResponseEntity.status(401).build();
> 	}
> 
> 	return ResponseEntity.ok("login success");
> }
> ```

이 방식에 문제가 있다면 그건 무엇일까?

컨트롤러가 너무 많은 일을 한다는 것이다. 

```text
요청 받기
사용자 조회하기
비밀번호 비교하기
로그인 성공/실패 판단하기
권한 만들기
인증 상태 저장하기
```

## Security를 이용하면 책임을 나눌 수 있다.

무슨 책임을 나누느냐 하면, '인증' 작업을 컨트롤러가 직접하지 않고 외부의 인증 전용 클래스 메서드 에 맡긴다는 것이다.

그렇게 하면 이제 로그인 API 컨트롤러는 2개만 하면 된다.

```
아이디/비밀번호를 보냈군. -> Authentication이라는 인증 요청 객체로 만들어야지.
검증도 내가 직접 하지 말자 -> AuthenticationManager에게 맡겨야지.
```

코드 친화적으로 말하면, 

```
- 로그인 요청 받기
- username/password를 Authentication으로 포장하기
- AuthenticationManager 호출하기
- 성공 결과를 바탕으로 응답 만들기
```

> [!example] 예시 
> ```java
> @PostMapping("/api/auth/login")
> public TokenResponse login(@RequestBody LoginRequest request) {
>     Authentication input =
>         new UsernamePasswordAuthenticationToken(
>             request.username(),
>             request.password()
>         ); //인증 요청 객체 만들기
> 
>     Authentication result =
>         authenticationManager.authenticate(input); //검증 시키기
> 
>     return tokenService.issue(result);
> }
> ```

이제 로그인 API 컨트롤러는 아래와 같은 일은 하지 않게 되었다.

```
Controller가 하지 않게 된 일:
- DB password_hash 직접 조회
- raw password 직접 비교
- 로그인 성공/실패를 if문으로 최종 판단
```

## 컨트롤러가 위임한 인증 작업에 대해 더 알아보자.

### 내가 나임을 증명하기

위 코드에서 `Authentication` 타입으로 '인증 요청 객체'를 만들고, '검증' 도 시켰다. 

`Authentication`이란 무엇일까?  

`Authentication` 이란, 자격증명, 즉  내가 나임을 증명하기 위한 정보를 의미한다.

| 상황         | 자격 증명               |
| ---------- | ------------------- |
| 일반 로그인     | username + password |
| JWT API 요청 | Bearer access token |
| OAuth 로그인  | authorization code  |
| API Key 방식 | API key             |

조금 더 정확히 말하면 아래와 같다.

`Authentication`은 자격 증명을 담아 인증을 요청하거나, 인증 완료된 사용자를 표현하는 Spring Security의 중심 객체.

이 `Authentication` 객체는 4개 값을 가진다. 

```java
Authentication
- principal: 사용자 식별 정보
- credentials: 비밀번호, 토큰 등 자격 증명
- authorities: 권한 목록
- authenticated: 인증 완료 여부
```

하나의 Authentication 타입이지만 , 인증 전과 후의 의미는 다르다.

| 시점   | Authentication의 의미 | 로그인에서의 예시                                                                                                                                                                                               | 예시-의미                                     |
| ---- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 인증 전 | 검증 요청 객체           | `Authentication input = new UsernamePasswordAuthenticationToken(username, rawPassword)`  //  토큰화 방식으로 Authenticaion을 생성<br><br>`Authentication result = authenticationManager.authenticate(input);`<br> | 이 사용자가 보낸 username/password가 맞는지 검증해 주세요. |
| 인증 후 | 검증 완료된 사용자 정보 객체   | `Authentication result = authenticationManager.authenticate(input);`                                                                                                                                    | 이 사용자는 검증되었으며<br>권한은 ROLE_USER입니다.        |

### 인증 요청 접수 담당자 따로, 실제 검증 담당자 따로.

인증 단계 내부를 살펴보자. 앞서, 인증을 위해 authenticationManager를 호출하는것을 알 수 있었다.

이때, '어떤 인증 방식인지 알아내, 처리가능한 Provider에게 위임하는것'이 authenticationManager의 역할이다. authenticationManager는 온갖 인증방식에 대해 일단 접수를 받은 다음,  ProviderManager는 처리 가능한 AuthenticationProvider에게 검증을 위임한다.

인증 성공 결과는 SecurityContext에 담기고, SecurityContextHolder를 통해 현재 요청 흐름에서 접근할 수 있다.

마치 병원 원무과에서 접수하면 원무과에서 적절한 과를 선택해주는 것과 같다.

```
AuthenticationManager:
"인증 요청이 왔네. 이건 username/password 방식이군.
DaoAuthenticationProvider에게 맡기자."

AuthenticationProvider:
"DB에서 사용자를 찾고,
PasswordEncoder로 비밀번호를 비교하고,
권한을 구성해서 인증 결과를 만들자."
```

### 권한을 아는 법

인증된 사용자라고 해서 모든 곳에 접근할 수 있으면 안된다. 

특정 포털에 로그인 했다고 해서, 다른 사람이 쓴 글을 다 볼 수는 없다.

즉, 인증되었음이 인가되었음을 의미하지 않는다. 인가란, 권한을 의미한다. 

이 판단을 하는 필터는 `AuthorizationFilter` 이다.

그러므로, 인증용 검증과 인가용 검증을 하는 곳은 다르다.

```
AuthenticationProvider가 “너 누구냐”를 검증한다.
AuthorizationFilter가 “너 이 요청 해도 되냐”를 판단한다.
```

### Controller들, Service들, .. 여러 컴포넌트들에서 어떻게 이 사람이 누군지, 무슨 권한을 가지는지 알 수 있을까? 

매번 로그인 할 수 없기 때문에. '인증 완료'와 '인가 정보' 은 Spring의 어딘가에 저장되어 있어야 한다.

저장위치는, `SecurityContext`이다.

이곳  `SecurityContext`에 접근하려면 `SecurityContextHolder` 를 통해야만 한다.

> [!example] 예시
> ```java
> Authentication auth =
>     SecurityContextHolder.getContext().getAuthentication();
> 
> String username = auth.getName();
> ```

그렇다면, 서버는 그럼 항상 로그인 상태를 기억하고 있다는 말일까? 

그렇게 하는게 세션이고, 그렇게 안하는게 JWT 방식이다. 

세션 방식
```
- 인증 결과를 서버 세션에 저장해두고 다음 요청에서 복원한다. 
- 즉 로그인된 사용자의 상태를 서버가 항상 기억하고 있다.

[예시]
로그인 성공
→ 서버 세션에 인증 정보 저장
→ 클라이언트는 session id cookie 보냄
→ 서버는 session id로 인증 정보 복원
```

JWT 방식
```
- 서버에 저장된 사용자의 상태를 이용하지 않는다. 
- 사용자가 토큰을 가지고 있으면서 매 요청마다 보내준다. 
- 서버는 JWT를 매 요청마다 다시 검증해서, Authentication을 다시 만든다.
- 즉 매 요청마다 토큰을 근거로 현재 사용자를 다시 인증하는 방식

[예시]
로그인 성공
→ 서버가 access token 발급
→ 클라이언트가 Authorization header에 token 보냄
→ 서버는 매 요청마다 token 검증
→ Authentication을 다시 만듦

[예시-상세]
0. 요청 예시 : 
	GET /api/me     
	Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.....
1. Authorization header에서 Bearer token 추출
2. JWT 서명 검증
3. exp 만료 확인
4. claim 읽기
5. claim을 authority로 변환
6. Authentication 생성
7. SecurityContextHolder에 저장
8. AuthorizationFilter가 권한 판단
```

### JWT방식 인증/인가 에서, 로그아웃 하기. 그리고 JWT의 장단점

세션 방식에서 로그아웃하려면 서버에서 세션을 expired 하면 끝이다.

```
로그아웃
→ 서버 세션 삭제
→ session id가 와도 더 이상 인증 정보 없음
```

하지만, JWT access token은 그 자체 안에 유효기간과 서명을 가지고 있다.

그래서 로그아웃했다고 클라이언트에서 토큰을 삭제해도, 

누군가 복사해둔 access token이 있다면 해당 토큰의 만료 전까지 쓸 수 있다.

JWT access token 의 특징을 정리하면 아래와 같다.

```
JWT access token 의 특징
- 서명이 맞고
- 만료 시간이 지나지 않았고
- 서버가 별도 차단 검사를 하지 않으면
- 누구나(!) 계속 사용 가능
```

그래서, 의도에 맞게 전략이 필요하다

| 전략                        | 의도                               |
| ------------------------- | -------------------------------- |
| 짧은 access token 만료        | access token 수명을 짧게 해서 피해 시간 줄이기 |
| refresh token DB 저장       | refresh token을 서버에서 폐기 가능하게 만들기  |
| refresh token rotation    | 재발급 때마다 refresh token 교체         |
| access token jti denylist | 특정 access token ID를 차단 목록에 등록    |
| tokenVersion              | 사용자 단위로 기존 토큰 전체 무효화             |

이제 JWT의 장단점이 드러났다. 

JWT는, stateless하다는 장점이 있다. 

하지만, 로그아웃/탈취/강제 만료를 제대로 처리하려면 일부 state를 다시 서버에 도입해야 한다.
