# API Security SQL Injection Validation

### 3줄 요약
- API Security SQL Injection Validation의 핵심은 신뢰할 수 없는 요청 환경에서 다음 자산을 보호하는 판단 기준이다: `API 입력값, DTO 바인딩, SQL 파라미터, 오류 응답, 호출량`.
- 공격자는 입력값과 JSON 필드를 조작해 SQL Injection, Mass Assignment, 정보 노출, 자동화를 시도한다.
- 방어는 `입력 검증, 파라미터 바인딩, 출력 인코딩, 오류 축소, rate limit을 계층별로 둔다`는 구조로 설계하고 로그와 테스트로 검증한다.

### 핵심 정리
- Web Security 문서는 Spring Security 사용법 요약이 아니라 공격 시나리오와 방어 선택 기준을 설명해야 한다.
- Java/Spring 백엔드에서는 Filter, Controller, Service, Repository, Cookie, Token, Log가 서로 다른 방어선이다.
- 인증은 신원을 확인하는 일이고, 인가는 특정 resource와 action에 대한 허용 여부를 결정하는 일이다.
- 브라우저 환경에서는 쿠키 자동 전송, Origin, DOM 실행 모델을 서버 정책과 함께 이해해야 한다.
- 운영 로그는 보안 설계의 일부다. 사고가 난 뒤 누가 무엇을 언제 왜 했는지 복원할 수 있어야 한다.
- 개인 프로젝트에서도 HTTPS, 안전한 쿠키, 비밀번호 해시, 권한 테스트, 민감 로그 마스킹은 기본선이다.

### 하위 문서 연결
- 01. SQL Injection 공격과 Prepared Statement: Prepared Statement는 값 바인딩을 보호하지만 컬럼명, 정렬 방향, 테이블명 같은 구조는 allowlist가 필요하다.
- 02. Input Validation과 Output Encoding: Input validation은 서버가 처리할 수 있는 값의 범위를 줄이는 일이다.
- 03. Mass Assignment와 DTO 경계: Mass Assignment는 요청 JSON의 추가 필드가 엔티티나 권한 필드에 바인딩될 때 발생한다.
- 04. Error Message 정보 노출 방지: 클라이언트 오류 메시지는 행동을 안내하되 stack trace, SQL, class name, 내부 path를 숨긴다.
- 05. Rate Limit과 Abuse 방어: Rate limit는 IP 하나만 기준으로 잡으면 NAT, VPN, 분산 공격에서 한계가 크다.

### 헷갈리는 지점
- Spring Security를 켜면 보안이 끝난다고 생각하기 쉽다. 실제로는 공통 경계만 일부 해결된다.
	- 핵심은 프레임워크가 막는 공격과 애플리케이션이 직접 막아야 하는 공격을 구분하는 것이다.
	- 설정을 볼 때 항상 “막는 공격”, “남는 우회 경로”, “실패 로그”를 함께 본다.
- 공격 요청은 이상한 모양일 것이라고 기대하기 쉽다. 실제로는 정상 API에 일부 값만 바뀐 경우가 많다.
	- 핵심은 클라이언트 입력을 보안 결정의 근거로 바로 쓰지 않는 것이다.
	- userId, role, redirect_uri, Origin, token payload는 서버 검증 없이는 신뢰할 수 없다.
- 로그는 장애 분석용이라고만 생각하기 쉽다. 보안 사고는 시간이 지난 뒤 발견되는 경우가 많다.
	- 핵심은 감사 로그가 나중에 권한 변경, token 사용, 이상 요청을 재구성하는 증거라는 점이다.
	- 민감값은 남기지 말고 decision reason과 trace id는 남긴다.

### 확인 질문
- API Security SQL Injection Validation에서 가장 중요한 설계 질문은 무엇인가?
	- 어떤 자산을 누구에게서 보호하고, 어느 신뢰 경계에서 검증하며, 실패를 어떤 로그로 남길 것인가다.
- 취약한 설계의 공통점은 무엇인가?
	- 클라이언트가 보낸 식별자나 권한 값을 서버가 그대로 믿고, 실패 케이스 테스트와 감사 로그가 부족한 점이다.
- 좋은 Web Security 문서는 무엇을 함께 보여 주어야 하는가?
	- 공격 시나리오, 방어 설계, Spring/HTTP 예시, 운영 로그, 위험 신호를 함께 보여 주어야 한다.
