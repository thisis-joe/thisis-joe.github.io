## 개요

이 문서의 주제는 `Input Validation과 Output Encoding`이다. 단독 기능 설명으로 끝나면 위험하다. 웹 보안에서는 신뢰할 수 없는 요청 환경에서 다음 자산을 지키는 문제로 본다: `API 입력값, DTO 바인딩, SQL 파라미터, 오류 응답, 호출량`.

기준 독자는 Java/Spring 기반 백엔드 개발자다. `Input Validation과 Output Encoding`에서는 옵션 이름을 외우는 것보다 요청이 어느 경계에서 검증되고, 권한 결정이 어디서 내려지며, 실패가 어떤 운영 로그로 남는지 설명하는 능력이 더 중요하다.

이 문서에서 공격자는 입력값과 JSON 필드를 조작해 SQL Injection, Mass Assignment, 정보 노출, 자동화를 시도한다. 완전히 이상한 패킷보다 정상 API의 일부 값만 바꾼 요청이 더 자주 문제가 된다.

## 공격 시나리오

- 공격자는 `Input Validation과 Output Encoding`에 연결된 공개 진입점, 인증 후 API, 오류 응답, 로그 누락 지점을 먼저 찾는다.
- 정상 사용자의 요청을 관찰한 뒤 `userId`, `role`, `Origin`, `redirect_uri`, `Authorization`, `Cookie` 중 서버가 과신하는 값을 조작한다.
- 서버가 `API 입력값, DTO 바인딩, SQL 파라미터, 오류 응답, 호출량`의 출처와 검증 책임을 구분하지 않으면 공격은 비즈니스 로직을 거의 건드리지 않고 진행된다.
- 단일 요청이 차단되어도 공격자는 낮은 빈도, 여러 IP, 오래된 token, 경계값 입력으로 탐지를 늦출 수 있다.
- 피해는 데이터 조회뿐 아니라 권한 상승, 계정 연결, 결제 조작, 감사 로그 오염, 장애 유도로 이어질 수 있다.

## 취약한 요청/응답 예시

```http
POST /api/Input-Validation과-Output-Encoding HTTP/1.1
Host: api.example.com
Cookie: SESSION=valid
Content-Type: application/json

{"topic":"Input Validation과 Output Encoding","actor":"client-controlled","resourceId":"other-user-resource","admin":true}
```

```http
HTTP/1.1 200 OK
```

서버가 클라이언트 입력을 신뢰 경계 밖 값으로 보지 않으면 정상 요청 모양의 공격을 구분하지 못한다.

## 주제별 핵심 판단

- Input validation은 서버가 처리할 수 있는 값의 범위를 줄이는 일이다.
- Output encoding은 값이 HTML, JavaScript, URL, SQL 중 어디에 놓이는지에 따라 달라진다.
- 검증은 가능하면 allowlist와 타입 제한으로 표현하고 blacklist 필터만 믿지 않는다.
- 검증 실패 응답은 친절하되 내부 정책과 정규식 전체를 노출하지 않는다.

## 개선된 요청/응답 예시

```java
public record InputValidationOutputEncodingRequest(
    @Size(max = 100) String keyword,
    @Min(1) @Max(100) int size
) {}

@PostMapping("/api/Input-Validation과-Output-Encoding")
public ResponseEntity<?> handle(@Valid @RequestBody InputValidationOutputEncodingRequest request,
                                Authentication authentication) {
    audit.record("api_request_validated", authentication.getName());
    return ResponseEntity.accepted().build();
}
```

DTO allowlist와 Bean Validation으로 서버가 처리할 수 있는 입력 범위를 먼저 줄인다.

## 방어 설계

- `Input Validation과 Output Encoding`의 보호 대상은 `API 입력값, DTO 바인딩, SQL 파라미터, 오류 응답, 호출량`이다. 보호 대상을 먼저 정해야 검증 위치가 보인다.
- 브라우저, 모바일 앱, Gateway, Spring Filter, Controller, Service, Repository, DB는 같은 신뢰 수준이 아니다.
- 클라이언트가 보낸 식별자는 조회 후보일 뿐 권한 결정의 근거가 아니다.
- 인증, 인가, 입력 검증, 출력 인코딩, 감사 로그는 서로 대체하지 않는다.
- 실패는 조용히 삼키지 않고 `api_validation_rejected` 같은 구조화된 보안 이벤트로 남긴다.
- 오류 응답은 공격자에게 내부 구조를 설명하지 않게 줄이고, 서버 로그에는 추적 가능한 request id를 남긴다.
- 새 API, 새 role, 새 OAuth client, 새 Origin은 기본 허용이 아니라 기본 거부에서 시작한다.
- 테스트는 성공 케이스보다 다른 사용자 리소스, 만료 token, 잘못된 Origin, 예상 밖 필드를 먼저 넣어 본다.

## Spring/HTTP 예시

```java
public record InputValidationOutputEncodingRequest(
    @Size(max = 100) String keyword,
    @Min(1) @Max(100) int size
) {}

@PostMapping("/api/Input-Validation과-Output-Encoding")
public ResponseEntity<?> handle(@Valid @RequestBody InputValidationOutputEncodingRequest request,
                                Authentication authentication) {
    audit.record("api_request_validated", authentication.getName());
    return ResponseEntity.accepted().build();
}
```

DTO allowlist와 Bean Validation으로 서버가 처리할 수 있는 입력 범위를 먼저 줄인다.

`Input Validation과 Output Encoding`에서 Spring Security 설정은 방어의 일부다. Filter 경계에서 공통 인증과 일부 공격 방어를 맡더라도, resource ownership과 업무 예외는 Service 또는 domain policy에서 다시 확인해야 한다.

## 운영 로그와 감사 지점

```text
level=WARN event=api_validation_rejected result=blocked topic="Input Validation과 Output Encoding" principal=member:1004 ip=203.0.113.10 path=/api/security/Input-Validation과-Output-Encoding reason=policy_violation traceId=7f9c2b0e
```

`Input Validation과 Output Encoding` 로그는 누가, 어떤 자산에, 어떤 경계에서, 어떤 이유로 거부되었는지를 복원할 수 있어야 한다.

- `Input Validation과 Output Encoding` 이벤트에는 principal, resource type, resource id, action, result, reason을 분리된 필드로 남긴다.
- `Input Validation과 Output Encoding` 로그에는 token 원문, 비밀번호, 전체 주민번호, 전체 카드번호, secret을 남기지 않는다.
- `Input Validation과 Output Encoding` 실패는 단일 로그보다 반복 패턴을 볼 수 있게 계정별, IP별, user agent별 집계가 가능해야 한다.
- `Input Validation과 Output Encoding`의 차단 이벤트와 허용 이벤트를 모두 남길지, 민감 이벤트만 남길지 보존 비용과 감사 요구를 함께 본다.

## 테스트 포인트

- `Input Validation과 Output Encoding` 성공 케이스만 두지 말고 인증 없음, 권한 없음, 만료 token, 잘못된 Origin을 분리해서 검증한다.
- `Input Validation과 Output Encoding` 테스트에는 정상 사용자와 비소유자 사용자를 모두 넣어 resource ownership 누락을 확인한다.
- `Input Validation과 Output Encoding` 실패 시 응답 status와 서버 로그 event 이름이 설계와 일치하는지 확인한다.
- `Input Validation과 Output Encoding`에서 민감값이 응답, 로그, metric label, trace attribute에 섞이지 않는지 확인한다.
- `Input Validation과 Output Encoding` 정책 변경 후 기존 세션, 기존 token, 기존 권한 캐시가 어떻게 동작하는지 회귀 테스트한다.

## 위험 신호!

- Input Validation과 Output Encoding에서 클라이언트가 보낸 식별자를 서버 검증 없이 신뢰한다.
- Input Validation과 Output Encoding 실패가 401, 403, 400, 429, 500 중 무엇인지 일관되게 정리되어 있지 않다.
- Input Validation과 Output Encoding 관련 로그에 trace id나 decision reason이 없다.
- DTO와 Entity를 직접 연결하고 예상 밖 필드를 테스트하지 않는다.
- 오류 응답에 SQL, class name, stack trace가 노출된다.

## 확인 질문

- `Input Validation과 Output Encoding`에서 가장 먼저 정해야 하는 것은 무엇인가?
	- 보호할 자산, actor, entry point, trust boundary다. 이것이 정해져야 검증 위치와 로그 기준을 결정할 수 있다.
- 클라이언트가 보낸 값 중 바로 신뢰하면 안 되는 것은 무엇인가?
	- userId, role, ownerId, price, redirect_uri, Origin, token payload처럼 공격자가 만들거나 바꿀 수 있는 값이다.
- Spring Security 설정만으로 충분하지 않은 이유는 무엇인가?
	- Filter 경계는 공통 방어를 맡지만 resource ownership, 업무 예외, 감사 로그, 사고 대응은 애플리케이션 설계가 함께 책임져야 하기 때문이다.
