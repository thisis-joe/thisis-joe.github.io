## 개요

Lock wait는 기다림이고, deadlock은 순환 대기다. 둘 다 API 지연과 실패를 만들지만 대응은 다르다. Lock wait는 blocking transaction을 찾고 줄여야 하며, deadlock은 접근 순서와 트랜잭션 구조를 바꿔야 할 수 있다.

Deadlock은 완전히 0으로 만들기 어려운 경우도 있지만, 빈번한 deadlock은 설계 냄새다.

## 원리

이 문서의 원리는 `03. Deadlock과 Lock Wait 상세`을 단순 기능이나 문법으로 보지 않고, DB 내부 동작, 백엔드 코드 경계, 운영 지표가 만나는 지점으로 이해하는 것이다. 뒤의 섹션들은 이 원리를 실제 SQL, 코드 예시, 장애 신호, 협업 판단으로 나누어 설명한다.

## Lock Wait

다음 흐름은 lock wait를 만든다.

```text
T1: UPDATE products SET stock = stock - 1 WHERE id = 10; -- commit 안 함
T2: UPDATE products SET stock = stock - 1 WHERE id = 10; -- T1 대기
```

T2는 T1이 commit 또는 rollback할 때까지 기다린다. T1이 외부 API를 호출하느라 오래 걸리면 T2와 뒤 요청들이 줄줄이 대기한다.

## Deadlock

Deadlock은 서로의 lock을 기다리는 순환이다.

```text
T1: A lock 획득 -> B lock 대기
T2: B lock 획득 -> A lock 대기
```

DB는 한쪽을 롤백시키고 오류를 반환한다. 애플리케이션은 이 오류를 잡아 재시도하거나 사용자에게 적절히 실패를 알려야 한다.

## 코드 원인

서로 다른 순서로 업데이트하는 코드가 대표적이다.

```java
@Transactional
public void mergeTeam(Long sourceTeamId, Long targetTeamId) {
    Team source = teamRepository.findByIdForUpdate(sourceTeamId);
    Team target = teamRepository.findByIdForUpdate(targetTeamId);
    target.merge(source);
}
```

동시에 반대 방향 요청이 들어오면 위험하다. 항상 ID 오름차순으로 lock을 잡거나, 비즈니스적으로 동시에 실행되지 않게 큐잉한다.

## 확인 쿼리

PostgreSQL에서 대기 상태를 본다.

```sql
SELECT pid, wait_event_type, wait_event, state, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

MySQL에서는 `SHOW ENGINE INNODB STATUS`에서 최근 deadlock 정보를 확인할 수 있다.

```sql
SHOW ENGINE INNODB STATUS;
```

운영에서는 직접 실행 권한이 없을 수 있으므로 인프라/DBA에게 시간대와 문제 SQL을 전달한다.

## 재시도 기준

Deadlock victim은 재시도 후보지만 무조건 재시도하면 안 된다.

- 작업이 짧은가?
- 멱등성이 있는가?
- 같은 요청을 여러 번 실행해도 안전한가?
- deadlock 빈도가 낮은가?
- backoff와 최대 횟수가 있는가?

빈번한 deadlock은 재시도보다 원인 제거가 우선이다.

## 실전 팁

- 여러 테이블을 업데이트하는 순서를 팀 규칙으로 정한다.
- 사용자 API와 batch가 같은 데이터를 업데이트하면 시간대나 범위를 분리한다.
- deadlock 로그의 SQL 두 개를 코드 경로로 역추적한다.
- lock wait timeout과 deadlock 오류를 구분해 로깅한다.
- 재시도는 짧은 트랜잭션과 멱등 작업에만 제한한다.

## 위험 신호!

- deadlock이 매일 발생하는데 재시도로만 숨긴다.
- 어떤 코드 경로가 lock을 잡는지 문서화되어 있지 않다.
- batch가 사용자 API와 반대 순서로 테이블을 업데이트한다.
- deadlock 로그를 수집하지 않는다.
- 재시도에 backoff가 없다.

## 확인 질문

- Lock wait와 deadlock의 대응 차이는 무엇인가?
	- Lock wait는 blocking transaction과 긴 lock 보유를 줄이는 것이 우선이고, deadlock은 lock 획득 순서와 트랜잭션 구조를 바꾸는 것이 중요하다.
- Deadlock victim을 재시도할 때 필요한 조건은 무엇인가?
	- 작업이 멱등적이고 짧으며, backoff와 최대 횟수가 있고, 중복 부작용이 없어야 한다.
- 빈번한 deadlock이 위험 신호인 이유는 무엇인가?
	- 접근 순서, 인덱스, 트랜잭션 경계, batch 충돌 같은 구조적 문제가 반복되고 있을 가능성이 높기 때문이다.
