## 개요

Resilience4j는 annotation을 붙이면 장애 격리가 끝나는 도구가 아니다. 설정값 하나가 사용자 latency, fallback 비율, provider 호출량, 내부 스레드 점유에 영향을 준다.

배송 조회 client에 `@CircuitBreaker`를 붙였다고 하자. timeout이 없으면 느린 호출은 여전히 스레드를 오래 잡는다. fallback이 정상 응답과 구분되지 않으면 사용자는 오래된 배송 정보를 믿는다. metric이 없으면 breaker가 열렸는지조차 알기 어렵다.

이 문서는 Resilience4j를 Spring 백엔드에서 어떻게 설계 문서와 운영 기준으로 연결할지 다룬다.

## 먼저 정할 요구사항

설정 전에 다음을 정한다.

- 사용자 API latency 목표는 얼마인가?
- 외부 의존성 p95, p99는 얼마인가?
- timeout이 나면 어떤 fallback을 줄 수 있는가?
- 재시도해도 안전한 호출인가?
- 중복 호출이 외부 시스템에 부작용을 만드는가?
- breaker가 열리면 어떤 alert를 보낼 것인가?
- bulkhead full이면 사용자에게 어떤 응답을 줄 것인가?

이 질문 없이 설정 숫자만 복사하면 운영 중 왜 열렸는지, 왜 안 열렸는지 설명할 수 없다.

## 설정 예시

```yaml
resilience4j:
  timelimiter:
    instances:
      shippingClient:
        timeout-duration: 1s
  circuitbreaker:
    instances:
      shippingClient:
        sliding-window-size: 100
        minimum-number-of-calls: 20
        failure-rate-threshold: 50
        slow-call-rate-threshold: 50
        slow-call-duration-threshold: 800ms
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 5
  bulkhead:
    instances:
      shippingClient:
        max-concurrent-calls: 30
        max-wait-duration: 0
```

`max-wait-duration: 0`은 bulkhead가 가득 차면 기다리지 않고 빠르게 fallback하도록 만든다. 배송 조회처럼 부가 정보라면 대기보다 빠른 축소 응답이 나을 수 있다.

## 조합 순서

실무에서는 다음 책임을 분리해 생각한다.

| 장치 | 책임 |
| --- | --- |
| TimeLimiter/timeout | 개별 호출 최대 대기 시간 제한 |
| Retry | 일시 장애에 제한적으로 재시도 |
| CircuitBreaker | 반복 실패와 slow call 차단 |
| Bulkhead | 동시 실행 수와 리소스 점유 제한 |
| Fallback | 사용자와 API에 축소 상태 표현 |

Retry는 항상 조심한다. timeout 1초, retry 2회면 한 요청이 최대 3초 이상 의존성을 붙잡을 수 있다. 사용자 API 목표가 500ms라면 retry를 빼거나 비동기 보정으로 바꾸는 것이 맞을 수 있다.

## Spring 코드

Client 경계에 정책을 둔다.

```java
@Component
class ShippingClient {
    @CircuitBreaker(name = "shippingClient", fallbackMethod = "fallback")
    @Bulkhead(name = "shippingClient", fallbackMethod = "bulkheadFallback")
    public ShippingStatus getStatus(String orderId) {
        return provider.getStatus(orderId);
    }

    private ShippingStatus fallback(String orderId, Throwable cause) {
        return ShippingStatus.degraded(orderId, "provider_unavailable");
    }

    private ShippingStatus bulkheadFallback(String orderId, BulkheadFullException cause) {
        return ShippingStatus.degraded(orderId, "bulkhead_full");
    }
}
```

Fallback reason을 나누면 운영자가 provider 장애와 내부 격리 동작을 구분할 수 있다.

## API 응답 연결

Service는 fallback 상태를 숨기지 않는다.

```json
{
  "orderId": "ord-1001",
  "shipping": {
    "status": "DEGRADED",
    "reason": "provider_unavailable",
    "retryable": true
  }
}
```

이 응답은 HTTP 200일 수 있지만 완전한 성공은 아니다. API 문서에는 부분 축소 상태를 명시해야 한다.

## Metric

Resilience4j metric은 최소 다음을 본다.

- circuit breaker state
- failure rate
- slow call rate
- buffered calls
- not permitted calls
- bulkhead available concurrent calls
- bulkhead rejected calls
- fallback reason count

`not permitted calls`가 늘면 circuit이 open되어 호출이 차단되고 있다는 뜻이다. `bulkhead rejected calls`가 늘면 격리된 pool이 가득 찼다는 뜻이다. 두 지표의 대응은 다르다.

## 테스트

운영 가능한 설정은 실패 테스트로 확인한다.

- provider가 5초 지연될 때 timeout이 먼저 발생하는가?
- 실패율이 threshold를 넘으면 circuit이 open되는가?
- open 상태에서 provider 호출이 차단되는가?
- half-open에서 제한된 호출만 나가는가?
- bulkhead가 가득 차면 즉시 fallback되는가?
- fallback 응답이 정상 응답과 구분되는가?

테스트가 없으면 설정 파일은 문서처럼 보이지만 실제 동작을 보장하지 않는다.

## 흔한 실수

첫 번째 실수는 timeout 없이 breaker만 두는 것이다. 느린 호출은 breaker가 열리기 전까지 계속 리소스를 잡는다.

두 번째 실수는 retry와 breaker를 무작정 같이 켜는 것이다. retry가 provider 호출량을 늘려 장애를 증폭할 수 있다.

세 번째 실수는 fallback을 모든 예외에 똑같이 주는 것이다. bulkhead full, timeout, provider 500, validation error는 원인도 대응도 다르다.

네 번째 실수는 annotation을 service 전체에 붙이는 것이다. 정책은 보통 외부 의존성 client 경계에 두어야 호출 책임이 명확해진다.

## 개인 프로젝트 기준

- 외부 API client 하나에 timeout, circuit breaker, fallback을 적용한다.
- 실패와 지연을 재현하는 테스트나 mock을 둔다.
- fallback 응답에 reason을 남긴다.
- 설정값의 이유를 latency 목표와 연결해 적는다.

## 기업 운영 기준

- 의존성별 Resilience4j 설정 owner를 둔다.
- 설정 변경은 metric 변화와 incident 회고에 연결한다.
- fallback reason별 alert와 dashboard를 만든다.
- client SDK나 공통 starter를 써도 서비스별 예외 정책은 문서화한다.

## 확인 질문

- 확인 질문: Resilience4j 설정을 복사해 쓰면 위험한 이유는 무엇인가?
	- 답변: latency 목표, provider 특성, fallback 가능 여부, retry 안전성이 서비스마다 달라 같은 threshold가 다른 장애를 만들 수 있기 때문이다.
- 확인 질문: `not permitted calls`와 `bulkhead rejected calls`는 어떻게 다른가?
	- 답변: 전자는 circuit open으로 호출이 차단된 것이고, 후자는 격리된 동시 실행 리소스가 가득 차 거절된 것이다.
- 확인 질문: fallback reason을 나누어야 하는 이유는 무엇인가?
	- 답변: timeout, provider 오류, circuit open, bulkhead full은 원인과 운영 대응이 다르므로 같은 fallback으로 숨기면 장애 분석이 어렵다.
