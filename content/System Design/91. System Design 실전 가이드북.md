# System Design 실전 가이드북

## 이 문서를 쓰는 이유

System Design 문서를 많이 읽어도 실제 상황에서는 어디부터 다시 펼쳐야 할지 막힐 수 있다.

이 문서는 개념을 다시 설명하는 요약본이 아니다. 요구사항 회의, 장애 대응, 설계 리뷰, 면접 답안, 포트폴리오 문서 작성 같은 상황을 먼저 던지고, 그때 어떤 기존 문서를 어떤 순서로 다시 봐야 하는지 안내하는 실전 가이드북이다.

읽는 순서는 단순하다.

- 먼저 지금 겪는 상황과 가장 가까운 Case를 고른다.
- `관찰할 증거 또는 확인할 단서`로 문제가 어느 축에 가까운지 확인한다.
- `먼저 생각해보기` 질문에 짧게 답해본다.
- `찾아볼 문서`를 열어 기존 문서의 계산, 계약, 실패 모델, 운영 기준을 다시 확인한다.
- 마지막에 `가져갈 한 문장`을 설계 문서나 리뷰 코멘트의 기준으로 삼는다.

System Design은 기술 이름을 많이 아는 일이 아니라, 요구사항을 성능, 정합성, 장애 격리, 운영 복잡도의 결정으로 바꾸는 일이다. 이 문서는 그 전환을 반복 연습하기 위한 안내서다.

## 실전 Case

### Case 1. 요구사항 회의가 기능 목록으로만 끝날 때

#### 상황

새 기능 회의가 끝났는데 남은 것은 "알림 보내기", "상태 조회하기", "관리자 화면 추가" 같은 기능 목록뿐이다. 팀은 바로 API를 만들자고 하지만, 성공 기준과 실패 응답, 지연 허용 범위가 아직 없다.

#### 관찰할 증거 또는 확인할 단서

- 성공 응답만 있고 pending, retry, 거절, 실패 응답이 없다.
- 기능 요구사항과 비기능 요구사항이 한 문장 안에 섞여 있다.
- 제약과 가정이 "일단 트래픽은 적을 것"처럼 검증 불가능한 말로 남아 있다.
- 설계 리뷰에서 "이건 어디까지 하는 기능인가?"라는 질문이 반복된다.

#### 먼저 생각해보기

- 사용자가 성공으로 기대하는 결과는 무엇인가?
- 지금 꼭 보장해야 하는 값과 늦게 맞아도 되는 값은 무엇인가?
- 아직 모르는 값은 제약인가, 가정인가, 검증해야 할 질문인가?

#### 정리

먼저 기능 목록을 사용자 성공 기준으로 바꾼다. 그다음 API 계약, 상태 전이, 비기능 요구사항, 제약과 가정을 분리한다. 이 단계에서 기술 선택을 확정하지 말고, 어떤 요구가 cache, queue, rate limit, 장애 격리를 요구하는지 추적 가능한 형태로 남긴다.

#### 가져갈 한 문장

기능 목록은 설계 입력일 뿐이고, 설계는 그 목록을 계약, 상태, 지표, 실패 응답으로 번역할 때 시작된다.

### Case 2. 숫자 없이 캐시, 큐, replica를 고르려 할 때

#### 상황

팀원이 "트래픽이 많을 것 같으니 Redis와 Kafka를 넣자"고 말한다. 그런데 DAU, peak, read/write 비율, payload 크기, 여유율, 실패 시 허용 지연이 아직 없다.

#### 관찰할 증거 또는 확인할 단서

- 평균 트래픽만 있고 peak traffic이 없다.
- p95 latency 목표와 throughput 목표가 분리되어 있지 않다.
- 저장량, bandwidth, memory 계산 없이 DB와 cache 크기를 정한다.
- "나중에 늘리면 된다"는 말은 있지만 headroom과 saturation 기준이 없다.

#### 먼저 생각해보기

- 숫자가 바뀌면 설계 선택도 바뀌는 항목은 무엇인가?
- 지금 필요한 것은 cache인가, queue인가, read replica인가, 아니면 계산 자체인가?
- 불확실한 값은 어느 범위까지 흔들려도 설계가 유지되는가?

숫자는 예측의 정답을 맞히기 위한 장식이 아니다. cache hit 목표, DB fallback QPS, queue drain time, memory 한계, replica lag 같은 설계 판단을 만들기 위한 입력이다. 먼저 계산 표를 만든 뒤, 그 계산이 어떤 컴포넌트를 정당화하는지 연결한다.

#### 가져갈 한 문장

숫자 없이 고른 컴포넌트는 설계 결정이 아니라 아직 검증되지 않은 취향에 가깝다.

### Case 3. 트래픽 급증 하루 전, 어디가 먼저 포화될지 모를 때

#### 상황

이벤트 오픈을 앞두고 API 서버를 두 배로 늘리자는 의견이 나온다. 하지만 병목이 앱 서버인지, DB connection인지, queue backlog인지, 외부 API quota인지 확인되지 않았다.

#### 관찰할 증거 또는 확인할 단서

- read peak와 write peak가 분리되어 있지 않다.
- autoscaling 계획은 있지만 downstream budget이 없다.
- queue depth는 보는데 oldest age와 drain time은 보지 않는다.
- traffic shed 기준과 기능 축소 기준이 없다.

#### 먼저 생각해보기

- 앱 서버를 늘리면 DB connection 총합도 같이 늘어나는가?
- 사용자 요청을 거절할 기준과 늦게 처리할 기준은 서로 다른가?
- 급증 중에 지킬 핵심 경로와 낮출 부가 기능은 무엇인가?

#### 가져갈 한 문장

급증 대응의 핵심은 더 많이 받는 것이 아니라, 무엇을 보호하고 무엇을 늦출지 빠르게 정하는 것이다.

### Case 4. 로그인 세션이 늘면서 서버 증설이 먹히지 않을 때

#### 상황

사용자가 늘어나자 앱 서버를 늘렸는데 일부 사용자는 계속 로그아웃되거나 요청이 특정 인스턴스에 묶인다. 세션, 로컬 캐시, scheduler, lock 같은 상태가 서버 안에 남아 있을 가능성이 있다.

#### 관찰할 증거 또는 확인할 단서

- 서버를 늘렸는데 특정 인스턴스 장애가 사용자 세션 장애로 이어진다.
- sticky session을 켰지만 장애 전환과 배포가 어려워졌다.
- 로컬 메모리 cache, local lock, ThreadLocal context가 설계 문서에 빠져 있다.
- 상태 owner가 둘 이상이거나 최종 진실의 원천이 불명확하다.

#### 먼저 생각해보기

- 이 상태는 요청 중 임시 상태인가, 세션 상태인가, 영속 상태인가?
- 인스턴스가 사라지면 복구해야 하는 값은 무엇인가?
- session store가 필요한가, token 방식으로 충분한가?

stateless 확장은 서버 수의 문제가 아니라 서버 안에 남겨둔 상태를 어디로 옮길지의 문제다.

### Case 5. 상품 상세 캐시가 빠르지만 값이 자꾸 어긋날 때

#### 상황

상품 상세 조회 p95는 좋아졌지만 가격, 재고, 리뷰 요약, 판매 상태가 서로 다른 시점의 값으로 보인다. 캐시가 성능 문제는 줄였지만 정합성 계약을 흐리게 만들었다.

#### 관찰할 증거 또는 확인할 단서

- TTL 값은 있지만 왜 그 시간인지 설명이 없다.
- cache invalidation 실패와 stale data 허용 범위가 문서에 없다.
- cache miss가 몰릴 때 DB fallback이 급증한다.
- 사용자 화면과 관리자 화면의 정합성 기준이 같다.

#### 먼저 생각해보기

- 캐시해도 되는 값과 반드시 DB 기준으로 재검증할 값은 무엇인가?
- stale data를 사용자에게 보여줘도 되는 시간은 얼마인가?
- cache down, stampede, hot key가 생기면 어떤 경로를 끌 것인가?

#### 가져갈 한 문장

캐시는 성능 장치이면서 동시에 오래된 값을 어디까지 허용할지 정하는 계약이다.

### Case 6. 주문 API에서 결제, 알림, 포인트까지 한 번에 처리할 때

#### 상황

주문 생성 API가 결제 승인, 포인트 적립, 쿠폰 사용, 알림 발송, 통계 기록까지 동기 호출로 처리한다. 하나의 부가 기능이 느려지면 주문 전체가 느려지고, 실패 후 재시도하면 중복 side effect가 생긴다.

#### 관찰할 증거 또는 확인할 단서

- 핵심 성공 경로와 부가 경로가 같은 transaction처럼 묶여 있다.
- 알림이나 통계 실패가 주문 실패로 전파된다.
- 중복 요청을 막는 idempotency key가 없다.
- 이벤트 발행 성공과 consumer 처리 성공이 구분되어 있지 않다.

#### 먼저 생각해보기

- 사용자에게 즉시 확정해야 하는 상태는 무엇인가?
- 늦게 처리해도 되는 작업은 어떤 이벤트로 분리할 수 있는가?
- 재시도와 중복 처리에 안전한 side effect는 무엇인가?

비동기 경계는 속도를 위한 도구이기 전에 실패가 핵심 경로를 막지 않게 하는 경계다.

### Case 7. 큐 적체와 재시도가 동시에 커질 때

#### 상황

consumer가 느려져 queue가 밀리기 시작했다. 운영자는 consumer 수를 늘리고 retry 횟수도 늘리려 하지만, oldest age와 provider 429, 중복 처리, DLQ 기준이 정리되어 있지 않다.

#### 관찰할 증거 또는 확인할 단서

- queue depth는 커지지만 처리 성공률은 올라가지 않는다.
- retry가 같은 시간대에 몰려 downstream을 다시 때린다.
- DLQ는 있지만 재처리 기준과 owner가 없다.
- consumer concurrency를 늘리면 DB, 외부 API, lock wait가 같이 포화된다.

#### 먼저 생각해보기

- 지금 필요한 것은 consumer 증가인가, producer 제한인가?
- retry 대상과 포기할 실패를 분리했는가?
- 메시지를 다시 처리해도 같은 결과가 나오는가?

queue 적체는 consumer만의 문제가 아니다. producer 유입량, retry budget, DLQ 기준, ordering 비용, idempotency, downstream quota를 같이 봐야 한다. consumer를 늘리기 전에 오래된 작업을 버릴 수 있는지, 우선순위를 나눌 수 있는지, retry를 늦출 수 있는지 판단한다.

#### 가져갈 한 문장

큐가 밀릴 때 가장 먼저 할 일은 더 빨리 소비하는 것이 아니라 더 위험한 유입과 재시도를 멈추는 것이다.

### Case 8. 외부 API가 느려지자 우리 서비스도 같이 느려질 때

#### 상황

결제, 배송, 메시지 provider 중 하나가 느려졌는데 우리 API p95와 error rate도 같이 흔들린다. timeout은 길고, retry는 즉시 반복되며, fallback과 circuit breaker의 기준은 없다.

#### 관찰할 증거 또는 확인할 단서

- 외부 API timeout이 사용자 요청 timeout보다 길다.
- retry가 backoff 없이 같은 provider로 몰린다.
- circuit breaker가 없거나 어떤 실패를 세는지 정해져 있지 않다.
- 429, 503, timeout, unknown 상태를 같은 실패로 처리한다.

#### 먼저 생각해보기

- 외부 호출 실패를 사용자가 즉시 알아야 하는가, pending으로 둘 수 있는가?
- timeout, retry, circuit breaker, fallback의 순서는 어떻게 되어야 하는가?
- provider 장애 때 핵심 기능과 낮출 기능은 무엇인가?

#### 가져갈 한 문장

외부 API 안정성은 실패하지 않게 만드는 것이 아니라 실패가 우리 핵심 경로를 끌고 가지 않게 만드는 것이다.

### Case 9. 이벤트 오픈에서 일부 사용자가 모든 요청을 가져갈 때

#### 상황

선착순 이벤트를 열자 일부 사용자나 봇이 요청을 집중적으로 보낸다. 전체 서버는 아직 살아 있지만 일반 사용자는 계속 timeout을 보고, 클라이언트는 실패를 즉시 재시도한다.

#### 관찰할 증거 또는 확인할 단서

- 전체 RPS보다 특정 user, IP, API key, endpoint의 요청 집중이 더 크다.
- 429 응답에 retry 가능 시간이나 quota header가 없다.
- 무료, 유료, 내부, 관리자 요청이 같은 제한 정책을 쓴다.
- 제한 정책이 abuse 방어인지 비용 방어인지 공정성 보장인지 불분명하다.

#### 먼저 생각해보기

- 제한의 기준은 사용자, IP, tenant, API key, endpoint 중 무엇인가?
- burst를 어느 정도 허용하고 평균을 어느 정도 제한할 것인가?
- 클라이언트가 429를 받았을 때 어떤 행동을 해야 하는가?

rate limit은 서버 보호만이 아니라 공정성과 계약의 문제다. 제한 위치, 제한 키, 알고리즘, 사용자군별 정책, 429 응답 형식을 같이 정한다. 클라이언트가 따라야 할 계약이 없으면 제한은 거절이 아니라 재시도 폭주로 되돌아올 수 있다.

#### 가져갈 한 문장

좋은 rate limit은 요청을 막는 규칙이 아니라 시스템과 클라이언트가 함께 지키는 사용 계약이다.

### Case 10. 주문, 재고, 결제에서 언제 강한 일관성이 필요한지 헷갈릴 때

#### 상황

주문 완료 화면, 재고 차감, 결제 승인, 알림, 포인트 적립이 서로 다른 저장소와 이벤트를 거친다. 어떤 값은 즉시 맞아야 하고 어떤 값은 늦어도 되지만, 설계 문서에는 모두 "정합성 유지"라고만 적혀 있다.

#### 관찰할 증거 또는 확인할 단서

- strong consistency와 eventual consistency가 데이터별로 나뉘어 있지 않다.
- read-after-write가 필요한 화면과 그렇지 않은 화면이 구분되지 않는다.
- partial failure나 unknown 상태가 API 응답에 없다.
- stale 표시, conflict 처리, retry 버튼 기준이 없다.

#### 먼저 생각해보기

- 사용자 돈, 재고, 권한처럼 즉시 맞아야 하는 값은 무엇인가?
- 늦어도 되는 값은 사용자에게 어떻게 보여줄 것인가?
- partition이나 provider 장애 중에는 가용성과 일관성 중 무엇을 우선할 것인가?

#### 가져갈 한 문장

정합성 설계는 모든 값을 즉시 맞추는 일이 아니라 어떤 값은 반드시 맞추고 어떤 값은 늦어도 된다고 계약하는 일이다.

### Case 11. 조회가 느려서 Read/Write 분리를 고민할 때

#### 상황

대시보드와 목록 조회가 느려져 read replica나 CQRS 이야기가 나온다. 하지만 조회 모델을 따로 만들면 projection lag, rebuild, migration, stale 표시, 운영 비용이 따라온다.

#### 관찰할 증거 또는 확인할 단서

- 읽기 병목이 쿼리, 인덱스, join, lock, 네트워크 중 어디인지 모른다.
- command와 query의 책임이 코드에서 섞여 있다.
- read model lag를 사용자에게 어떻게 보여줄지 정하지 않았다.
- rebuild와 backfill 절차가 없다.

#### 먼저 생각해보기

- 단순 read replica로 충분한가, 별도 projection이 필요한가?
- 조회 결과가 몇 초 늦어도 되는가?
- read model이 틀렸을 때 어떤 지표와 절차로 복구할 것인가?

CQRS는 조회를 빠르게 만드는 선택이면서, 동기화 지연과 운영 절차를 새로 소유하는 선택이다.

### Case 12. DB가 커져서 partition과 sharding 이야기가 나올 때

#### 상황

테이블이 커지고 특정 고객이나 특정 상품에 트래픽이 몰리자 sharding 제안이 나온다. 하지만 scale up, partitioning, read replica, archive, index 개선, hot partition 완화 중 무엇이 먼저인지 정해지지 않았다.

#### 관찰할 증거 또는 확인할 단서

- 전체 평균 QPS는 낮지만 특정 key만 뜨겁다.
- partition key 후보와 query pattern이 맞지 않는다.
- cross-shard query와 transaction 비용을 계산하지 않았다.
- 확장 뒤 백업, migration, rebalancing, 운영 비용이 빠져 있다.

#### 먼저 생각해보기

- 현재 병목은 CPU, memory, storage, lock, connection, hot key 중 무엇인가?
- 데이터 분할 기준은 조회 경로와 쓰기 경로를 동시에 만족하는가?
- sharding을 하면 어떤 운영 작업이 매일 생기는가?

### Case 14. 장애가 번질 때 끊고, 낮추고, 남겨야 할 것

#### 상황

한 downstream의 지연이 thread pool을 잡아먹고, retry가 늘고, API 전체가 느려진다. 팀은 circuit breaker를 넣자고 하지만 어떤 실패를 세고 어떤 fallback을 줄지 정하지 않았다.

#### 관찰할 증거 또는 확인할 단서

- fallback이 사용하면 안 되는 데이터까지 반환한다.
- circuit breaker 설정은 있지만 alert, half-open 검증, 테스트 기준이 없다.

- 장애가 전파되는 호출 경로는 어디인가?

- 격리 대상은 thread, connection, queue, tenant, DB 중 무엇인가?

### Case 16. Notification System이 중복 발송과 provider 제한을 만날 때

#### 상황

알림 시스템이 주문, 결제, 배송 이벤트를 받아 이메일, SMS, push로 보낸다. provider 429가 발생하고 일부 메시지는 중복 발송되며, 사용자는 수신 거부 후에도 알림을 받았다고 신고한다.

#### 관찰할 증거 또는 확인할 단서

- 발송 요청, 접수, provider 전송, 최종 전달 상태가 분리되어 있지 않다.
- 수신 거부, channel priority, provider quota가 메시지 계약에 없다.
- retry와 DLQ는 있지만 idempotency key가 없다.
- provider별 실패를 모두 같은 방식으로 재시도한다.

#### 먼저 생각해보기

- 알림 API가 반환하는 것은 발송 완료인가, 접수 완료인가?
- 중복 발송이 절대 안 되는 알림과 중복 허용 가능한 알림은 무엇인가?
- provider 429를 받으면 retry, delay, channel switch, 포기 중 무엇을 할 것인가?

- [[02. Queue Producer Consumer 기본 상세#Consumer Idempotency]]

#### 정리

Notification은 "보낸다"가 아니라 접수, 예약, 전송 시도, provider 응답, 최종 상태를 분리하는 시스템이다. provider 제한과 장애는 정상적인 실패 모델로 보고, idempotency, retry budget, DLQ, 상태 조회, 수신 거부 정책을 메시지 계약에 포함한다.

#### 가져갈 한 문장

알림 시스템의 안정성은 발송 성공률보다 중복, 지연, 거절, 포기를 상태로 설명할 수 있는지에 달려 있다.

### Case 17. Chat System에서 저장, 전달, 읽음이 서로 다른 속도로 움직일 때

#### 상황

채팅 메시지가 서버에 저장되었지만 일부 클라이언트에는 늦게 전달된다. 읽음 표시와 presence는 더 자주 흔들리고, 재접속한 사용자는 일부 메시지를 놓쳤다고 말한다.

#### 관찰할 증거 또는 확인할 단서

- 메시지 저장 성공과 실시간 전달 성공이 같은 상태로 표현된다.
- room ordering과 global ordering을 구분하지 않는다.
- presence와 read receipt가 강한 정합성을 요구하는 것처럼 설계되어 있다.
- reconnect 후 missed messages를 가져오는 계약이 없다.

#### 먼저 생각해보기

- 사용자가 가장 신뢰해야 하는 상태는 저장인가, 전달인가, 읽음인가?
- ordering은 어느 범위에서 보장해야 하는가?
- 실시간 전달 실패 후 복구 경로는 무엇인가?

- [[03. Projection Read Model 상세#Projection lag]]

#### 정리

채팅은 모든 상태를 같은 속도로 맞추기 어렵다. 메시지 저장을 최종 기준으로 두고, 실시간 전달, presence, read receipt, missed message 복구를 별도 계약으로 분리한다. ordering 범위와 재접속 절차를 명확히 해야 지연과 누락을 사용자에게 설명할 수 있다.

#### 가져갈 한 문장

채팅 설계에서는 "메시지가 저장됐다"와 "모두에게 전달됐다"를 같은 사건으로 보면 안 된다.

### Case 18. Feed Timeline에서 fanout, freshness, celebrity path를 나눌 때

#### 상황

피드 시스템에서 일반 사용자의 게시물은 잘 퍼지지만 팔로워가 많은 계정의 게시물은 queue를 오래 잡아먹는다. 최신성 요구와 fanout 비용, rebuild, 삭제 반영 기준이 충돌한다.

#### 관찰할 증거 또는 확인할 단서

- follower 수에 따른 write amplification을 계산하지 않았다.
- fanout on write와 fanout on read를 사용자군별로 나누지 않았다.
- timeline read model의 rebuild와 backfill 절차가 없다.
- 유명 계정 게시물이 hot partition을 만든다.

#### 먼저 생각해보기

- 모든 사용자에게 같은 fanout 전략을 적용해야 하는가?
- 최신성은 몇 초까지 늦어도 되는가?
- 삭제, 차단, privacy 변경은 materialized timeline에 어떻게 반영되는가?

- [[02. Read Write 비율과 Peak Traffic 상세#hot row를 따로 본다]]

#### 정리

Feed는 평균 사용자 기준으로만 설계하면 유명 계정과 특정 이벤트에서 깨진다. follower skew를 따로 보고, fanout on write, fanout on read, hybrid 전략을 나눈다. freshness, rebuild, 삭제 반영, hot partition 완화, queue priority를 함께 설계해야 운영 가능한 timeline이 된다.

#### 가져갈 한 문장

피드 설계의 어려움은 게시물을 보여주는 일이 아니라 누구의 게시물을 언제 누구에게 미리 계산할지 정하는 일이다.

### Case 19. 신규 기능 설계 리뷰를 30분 안에 끝내야 할 때

#### 상황

리뷰 시간이 30분뿐인데 설계안에는 API, DB, cache, queue, 운영 지표가 모두 들어 있다. 어디부터 봐야 할지 모르면 컴포넌트 이름을 훑다가 중요한 실패 모델을 놓치기 쉽다.

#### 관찰할 증거 또는 확인할 단서

- 리뷰 코멘트가 기술 추가 제안으로만 흐른다.
- 목표와 비목표, 제약과 가정, 선택지 비교가 빠져 있다.
- 상태 owner와 최종 진실의 원천이 그림에 표시되지 않는다.
- 운영 지표가 사용자 영향보다 기술 지표에 치우쳐 있다.

#### 먼저 생각해보기

- 이 설계가 해결하려는 사용자 문제는 무엇인가?
- 네 축 중 어떤 축을 개선하고 어떤 축을 더 어렵게 만드는가?
- 장애가 났을 때 운영자가 첫 5분에 볼 지표는 무엇인가?

### Case 20. 학습을 포트폴리오 설계 문서로 바꿀 때

#### 상황

System Design 문서를 모두 읽었지만 포트폴리오나 면접 답안으로 쓰려니 설명이 개념 나열로 흐른다. "Redis를 썼다", "Kafka를 썼다"는 말은 있지만 왜 필요했고 무엇을 포기했는지 보이지 않는다.

#### 관찰할 증거 또는 확인할 단서

- 설계 문서가 구현한 기술 목록으로 시작한다.
- 개인 프로젝트 수준과 기업 운영 수준의 차이가 드러나지 않는다.
- 학습 사례마다 같은 아키텍처 그림을 반복한다.
- 결정, 제외 범위, 지표, rollback, 미해결 질문이 없다.

#### 먼저 생각해보기

- 이 설계에서 실제로 바뀐 축은 성능, 정합성, 장애 격리, 운영 복잡도 중 무엇인가?
- 내가 생략한 운영 기준은 무엇이고, 나중에 전환할 조건은 무엇인가?
- 면접관이나 리뷰어가 물을 다음 질문은 무엇인가?
