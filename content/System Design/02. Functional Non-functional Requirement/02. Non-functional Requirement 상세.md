>- Non-functional Requirement를 측정 가능한 SLO와 운영 지표로 어떻게 바꾸는가?
>- latency, throughput, availability, durability, security, retention은 각각 어떤 설계 결정을 강제하는가?
>- 비기능 요구사항은 성능, 정합성, 장애 격리, 운영 복잡도를 어떻게 바꾸는가?

## 개요

Non-functional Requirement는 "빠르게", "안정적으로", "확장 가능하게" 같은 좋은 말의 모음이 아니다.

기능이 어떤 품질로 동작해야 하는지 측정 가능한 기준으로 정하는 일이다.

비기능 요구사항은 설계 선택을 직접 바꾼다.

`p95 200ms`는 cache, index, 외부 API 호출 위치를 묻게 만든다.

`99.9% availability`는 장애 허용 시간과 fallback 정책을 묻게 만든다.

`데이터 5년 보존`은 storage, partition, 분리 보관, 삭제 정책을 묻게 만든다.

## 품질 속성 분리

비기능 요구사항은 한 문장으로 묶지 않는다.

| 속성 | 질문 | 설계 영향 |
| --- | --- | --- |
| Latency | 사용자는 몇 ms 안에 응답을 받아야 하는가? | cache, index, timeout, 비동기 분리 |
| Throughput | 초당 몇 요청이나 작업을 처리해야 하는가? | scale out, queue, batch, partition |
| Availability | 어느 정도 장애를 허용하는가? | redundancy, failover, degradation |
| Durability | 저장된 데이터는 얼마나 잃으면 안 되는가? | transaction, replication, backup |
| Consistency | 최신성이나 중복 방지가 얼마나 중요한가? | lock, unique constraint, idempotency |
| Security | 누가 무엇을 할 수 있는가? | authn/authz, audit, encryption |
| Retention | 얼마나 오래 보관하고 언제 삭제하는가? | 분리 보관, partition, lifecycle |
| Observability | 무엇을 보고 장애를 판단하는가? | metrics, logs, tracing, alert |

이 표는 기능보다 덜 중요한 부록이 아니다.

실제로는 비기능 요구사항이 아키텍처의 복잡도를 결정하는 경우가 많다.

## 알림 시스템 예시

알림 발송 기능의 비기능 요구사항을 다음처럼 정할 수 있다.

```text
API 접수 latency = p95 200ms
캠페인 발송 시작 지연 = scheduledAt 기준 60s 이내
발송 처리량 = peak 20,000 messages/min
월 가용성 = 99.9%
중복 발송 = 사용자/캠페인 기준 0건 목표
발송 이력 보존 = 1년
수신 거부 반영 = 즉시 strong consistency
```

이 요구는 구조를 강제한다.

API 접수는 빠르게 끝내기 위해 실제 provider 호출과 분리한다.

발송 처리량은 worker 수와 provider rate limit을 함께 봐야 한다.

중복 발송 0건 목표는 idempotency key나 unique constraint를 요구한다.

수신 거부 반영은 cache stale을 허용하기 어렵다.

## SLO로 바꾸기

비기능 요구사항은 SLO와 측정 방식으로 바꾼다.

| 요구 | SLI | SLO | 제외 범위 |
| --- | --- | --- | --- |
| 접수 API가 빠르다 | request latency p95 | 200ms 이하 | client network 지연 제외 |
| 예약 발송이 제때 시작된다 | schedule lag | 60초 이하 99% | provider 장애 제외 |
| 서비스가 안정적이다 | successful request ratio | 월 99.9% | 계획 점검 제외 |
| 중복 발송이 없다 | duplicate delivery count | 0건 | provider 자체 중복 제외 후 보정 |
| 이력을 오래 보관한다 | retrievable history age | 1년 | 법적 삭제 요청 제외 |

SLO는 숫자를 쓰는 것으로 끝나지 않는다.

측정 위치와 제외 범위를 정해야 운영 중 논쟁이 줄어든다.

## 설계 선택으로 연결

비기능 요구사항은 다음처럼 설계 선택으로 이어진다.

| 비기능 요구 | 가능한 선택 | 새 비용 |
| --- | --- | --- |
| p95 200ms | provider 호출을 queue 뒤로 분리 | pending 상태, 재처리 |
| 20,000 messages/min | worker scale out, partition key | ordering, hot partition |
| 99.9% availability | degraded mode, retry 제한 | fallback 품질 관리 |
| 중복 발송 0건 | unique constraint, idempotency table | 저장소 비용, conflict 처리 |
| 이력 1년 | partitioned table, 보관 저장소 | 조회 경로와 삭제 정책 |
| 수신 거부 즉시 반영 | write DB 직접 확인 또는 짧은 TTL | latency 증가, cache hit 감소 |

성능을 올리면 정합성이나 운영 복잡도가 바뀐다.

정합성을 강하게 잡으면 latency나 throughput이 나빠질 수 있다.

이 trade-off를 숫자와 함께 적는 것이 비기능 요구사항의 역할이다.

## Spring 경계 예시

SLO가 있으면 API가 어떤 일을 동기 처리하지 말아야 하는지 보인다.

```java
@PostMapping("/notification-campaigns/{id}/dispatch")
public ResponseEntity<DispatchResponse> dispatch(@PathVariable Long id) {
    DispatchJob job = dispatchService.enqueue(id);
    return ResponseEntity.accepted().body(
        new DispatchResponse(job.id(), "ACCEPTED", "Dispatch will start within 60 seconds")
    );
}
```

`202 Accepted`는 기능 회피가 아니다.

비기능 요구사항이 "접수 API p95 200ms"와 "발송 시작 60초 이내"로 나뉘어 있기 때문에 가능한 계약이다.

반대로 API가 provider 호출까지 동기 처리하면 접수 latency와 provider availability가 묶인다.

## 관측 기준

비기능 요구사항은 관측 지표로 이어져야 한다.

- `http.server.requests.p95`
- `dispatch.schedule_lag.seconds`
- `dispatch.worker.throughput`
- `dispatch.duplicate.count`
- `dispatch.provider.timeout.rate`
- `history.retention.partition.count`
- `unsubscribe.consistency_violation.count`

지표가 없으면 요구사항은 선언으로만 남는다.

운영자가 볼 수 없는 비기능 요구사항은 장애 때 검증할 수 없다.

## 위험 신호

- "빠르게", "많이", "안정적으로"만 있고 숫자가 없다.
- SLO는 있지만 측정 위치와 제외 범위가 없다.
- latency 목표와 외부 API timeout이 모순된다.
- availability 목표가 있는데 degradation 정책이 없다.
- retention 요구가 있는데 삭제와 분리 보관 설계가 없다.
- security 요구가 있는데 audit log와 권한 경계가 없다.

## 개인 프로젝트 기준

개인 프로젝트에서는 모든 SLO를 정교하게 만들 필요는 없다.

하지만 최소한 다음은 숫자로 둔다.

- 핵심 API 목표 p95
- 예상 peak QPS 또는 작업량
- 장애 때 허용할 기능 축소
- 데이터 보존 기간
- 외부 API timeout

이 정도만 있어도 "좋은 성능"이 아니라 "어떤 성능을 목표로 했는지"를 설명할 수 있다.

## 기업 운영 기준

기업 운영에서는 비기능 요구사항이 책임과 비용으로 이어진다.

- SLO owner가 있어야 한다.
- error budget을 어떻게 쓸지 정해야 한다.
- 알림 기준이 SLO와 연결되어야 한다.
- 용량 계획과 비용 추정이 필요하다.
- 보안과 보존 요구는 감사 증거로 남아야 한다.
- SLO 위반 후 개선 작업과 일정이 기록되어야 한다.

## 확인 질문

- 확인 질문: Non-functional Requirement를 숫자로 바꿔야 하는 이유는 무엇인가?
	- 답변: 숫자와 측정 방식이 있어야 설계 선택의 성공 여부와 운영 알림 기준을 판단할 수 있기 때문이다.
- 확인 질문: `202 Accepted` 응답이 비기능 요구사항과 연결되는 이유는 무엇인가?
	- 답변: API 접수 latency와 실제 발송 완료 시간을 분리해 성능 목표와 비동기 운영을 함께 만족시키기 때문이다.
- 확인 질문: 비기능 요구사항이 바꾸는 설계 축은 무엇인가?
	- 답변: 성능과 가용성 목표를 명확히 하지만, 측정, 알림, fallback, 보존, 보안 운영 복잡도를 증가시킨다.
