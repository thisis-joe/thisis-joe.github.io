## 개요
Sticky Session은 같은 사용자의 요청을 같은 서버 인스턴스로 보내는 방식이다.
서버 메모리 세션을 유지하면서도 여러 인스턴스를 둘 수 있어 빠른 완화책처럼 보인다.
하지만 sticky는 상태를 없애지 않는다.
사용자를 특정 인스턴스에 묶어서 상태 위치 문제를 뒤로 미루는 방식이다.
인스턴스가 죽거나 rolling deploy로 교체되면 해당 인스턴스의 세션은 여전히 사라진다.
그래서 sticky는 장기 설계인지 임시 전환 단계인지 분명히 해야 한다.

## 이 문서가 바꾸는 설계 축
| 축 | 바뀌는 내용 |
| --- | --- |
| 성능 | 로컬 메모리 접근은 빠르지만 인스턴스별 부하 불균형이 생길 수 있다. |
| 정합성 | 세션 상태가 특정 인스턴스에만 있어 logout, 권한 변경 반영이 어려워질 수 있다. |
| 장애 격리 | 특정 인스턴스 장애가 해당 사용자 세션 유실로 이어진다. |
| 운영 복잡도 | load balancer cookie, drain, deploy 순서, session migration을 관리해야 한다. |

## 선택지를 구분한다
| 방식 | 상태 위치 | 장점 | 대표 비용 |
| --- | --- | --- | --- |
| In-memory Session | Spring 인스턴스 | 가장 단순하고 빠르다 | scale out과 failover가 약하다. |
| Sticky Session | Spring 인스턴스 + LB routing | 기존 구조를 크게 바꾸지 않는다 | 장애와 배포 때 세션 유실이 남는다. |
| Session Store | Redis, DB 등 외부 저장소 | 인스턴스 독립성이 높다 | store latency와 장애 대응이 필요하다. |
| Stateless Token | client token | 서버 저장소 조회를 줄인다 | revoke, 권한 변경, token leak 대응이 어렵다. |
같은 로그인 기능이라도 요구하는 보안 수준과 장애 허용 범위에 따라 답이 달라진다.

## 대표 시나리오
기존 단일 서버 쇼핑몰을 4대 Spring 인스턴스로 늘린다고 하자.
| 항목 | 값 |
| --- | ---: |
| 동시 로그인 사용자 | 80,000 |
| 인증 필요 QPS | 4,000 |
| 배포 주기 | 하루 1회 |
| 장바구니 세션 저장 | 서버 메모리 |
| 로그아웃 유실 허용 | 낮음 |
빠른 확장만 보면 sticky session이 가장 쉽다.
하지만 하루 한 번 배포 때마다 일부 사용자의 세션과 장바구니가 사라질 수 있다.
결제 직전 장바구니가 세션에만 있으면 사용자 영향이 크다.
이 상태는 session store 또는 DB-backed cart로 옮겨야 한다.

## Sticky Session의 실제 비용
Sticky는 다음 문제를 남긴다.
| 문제 | 설명 |
| --- | --- |
| 인스턴스 장애 | 해당 인스턴스의 session이 유실된다. |
| 부하 불균형 | 오래 머문 사용자가 특정 인스턴스에 몰릴 수 있다. |
| 배포 drain | 세션을 가진 인스턴스를 언제 내릴지 결정해야 한다. |
| scale in | 인스턴스를 줄이면 묶인 사용자를 잃을 수 있다. |
| multi-region | 지역 전환 시 session을 유지하기 어렵다. |
Sticky가 나쁜 선택이라는 뜻은 아니다.
전환 기간 동안 사용자 영향이 작고 구조 변경 비용이 큰 경우에는 현실적인 완화책이 될 수 있다.
다만 “언제 session store로 옮길지” 전환 조건이 있어야 한다.

## Session Store 계산
외부 session store를 쓰면 인스턴스 독립성이 생긴다.
대신 session store가 모든 인증 요청의 읽기 경로에 들어간다.
```text
authenticated_qps = 4,000
session_read_per_request = 1
session_write_ratio = 0.05

redis_read_qps = 4,000
redis_write_qps = 4,000 * 0.05 = 200
```
Redis read latency가 p95 3ms라면 모든 인증 API의 latency budget에 3ms가 추가된다.
Redis가 느려지면 API 서버는 정상이어도 인증 경로가 느려진다.
그래서 session store는 cache가 아니라 인증 핵심 의존성으로 봐야 한다.

## Load Balancer 설정 예시
Sticky를 쓴다면 의도를 설정에 드러내야 한다.
```yaml
load-balancer:
  sticky-session:
    enabled: true
    cookie-name: APP_ROUTE
    ttl: 30m
  connection-draining:
    enabled: true
    timeout: 120s
```
이 설정은 임시 완화책일 수 있다.
운영 문서에는 Pod drain 때 사용자 영향, scale-in 기준, cookie TTL을 함께 적는다.
sticky cookie TTL이 session TTL보다 길면 죽은 route를 계속 시도하는 문제가 생길 수 있다.

## Spring Session 전환 예시
장기적으로 session store를 선택했다면 session 값을 최소화한다.
```yaml
spring:
  session:
    store-type: redis
    timeout: 30m
server:
  servlet:
    session:
      cookie:
        name: SID
        http-only: true
        secure: true
```
Spring Security의 인증 객체를 그대로 크게 저장하면 Redis memory와 배포 호환성 문제가 생긴다.
세션에는 userId, sessionVersion, 최소 role 정도만 두고 상세 profile은 owner DB나 cache에서 조회한다.

## Token 방식이 적합한 경우
token 방식은 API 서버를 더 가볍게 만들 수 있다.
하지만 강제 logout과 권한 변경 즉시 반영이 약하다.
| 요구 | token 단독 | session store |
| --- | --- | --- |
| 매 요청 저장소 조회 최소화 | 유리 | 불리 |
| 즉시 logout | 불리 | 유리 |
| 권한 변경 즉시 반영 | 불리 | 유리 |
| multi-device 관리 | 별도 상태 필요 | 세션 목록으로 관리 가능 |
| 탈취 token 무효화 | blacklist 필요 | 세션 삭제 가능 |
JWT를 쓰더라도 refresh token, revoke list, device session을 저장하면 완전한 무상태는 아니다.
어떤 상태를 client에 두고 어떤 상태를 서버에 둘지 정책으로 나눠야 한다.

## 장애 대응 계약
세션 전략은 장애 응답을 바꾼다.
```http
401 Unauthorized
{
  "code": "SESSION_LOST",
  "action": "LOGIN_REQUIRED"
}
```
sticky 장애로 세션이 사라진 경우와 정상 만료는 구분할 수 있어야 한다.
사용자 문의와 장애 분석이 달라지기 때문이다.
session store 장애라면 `SESSION_STORE_UNAVAILABLE`처럼 내부 원인을 metric으로는 구분하되 사용자 메시지는 단순하게 둔다.

## 전환 기준
sticky에서 session store로 넘어갈 신호는 다음과 같다.
- rolling deploy 때 로그아웃 문의가 반복된다.
- scale-in을 사용자 적은 시간에만 할 수 있다.
- 특정 인스턴스에 로그인 사용자가 몰려 memory가 튄다.
- multi-AZ 장애 전환 때 인증 상태 유지가 요구된다.
- 장바구니, checkout, 2FA 상태가 세션에 있어 유실 비용이 크다.

## 개인 프로젝트 기준
- sticky session을 쓴다면 임시 선택인지 장기 선택인지 적는다.
- 메모리 세션에 넣는 값 목록을 문서화한다.
- 배포 때 로그아웃이 허용되는지 사용자 경험으로 설명한다.
- session store를 쓰면 TTL, key 크기, Redis 장애 시 동작을 정한다.

## 기업 운영 기준
- sticky session은 load balancer 설정, drain 정책, scale-in 절차와 함께 리뷰한다.
- session store는 인증 SLO, Redis alert, failover test 대상이다.
- token 방식은 revoke, refresh rotation, device 관리 정책과 함께 검토한다.
- 세션 전략 변경은 old/new cookie, migration 기간, rollback 조건을 포함한다.

## 위험 신호
- sticky session을 쓰면서 stateless 구조라고 설명한다.
- rolling deploy 중 세션 유실 범위를 계산하지 않는다.
- session store 장애가 로그인뿐 아니라 모든 API를 멈추는지 모른다.
- JWT를 쓰면서 강제 로그아웃 요구사항을 무시한다.
- 세션에 큰 객체를 저장하고 Redis memory 계획이 없다.
- load balancer cookie TTL과 session TTL이 맞지 않는다.

## 확인 질문
- 확인 질문: Sticky Session은 왜 근본적인 stateless 설계가 아닌가?
	- 답변: 상태가 여전히 특정 인스턴스 메모리에 남고, routing으로 같은 인스턴스에 보내는 방식이기 때문이다.
- 확인 질문: Session Store를 도입하면 어떤 의존성이 새로 생기는가?
	- 답변: 인증 요청마다 외부 저장소 latency와 장애 가능성이 생기므로 Redis 같은 store를 핵심 의존성으로 운영해야 한다.
- 확인 질문: Token 방식 선택 전에 확인할 요구사항은 무엇인가?
	- 답변: 즉시 logout, 권한 변경 반영, 탈취 대응, multi-device 관리가 필요한지 확인해야 한다.
