>- Spring 기반 로그인 서비스에서 세션 저장 위치를 어떻게 결정하는가?

## 개요
Stateless 서버는 아무 상태도 쓰지 않는 서버가 아니다.
요청 사이에 유지되어야 하는 상태를 특정 Spring 인스턴스의 메모리에 묶지 않는 서버다.
사용자가 로그인한 뒤 다음 요청이 다른 인스턴스로 가도 같은 인증 상태를 확인할 수 있어야 한다.
이 기준을 만족하면 rolling deploy, autoscaling, failover가 쉬워진다.
하지만 세션을 외부화하면 session store latency, TTL, 직렬화, 장애 시 로그인 경험을 새로 설계해야 한다.

## 이 문서가 바꾸는 설계 축
| 축 | 바뀌는 내용 |
| --- | --- |
| 성능 | 인스턴스 로컬 접근은 빠르지만 session store 호출이 추가되면 p95 latency가 늘 수 있다. |
| 정합성 | logout, 권한 변경, 세션 만료를 여러 인스턴스에서 같은 기준으로 적용한다. |
| 장애 격리 | 한 인스턴스 장애가 사용자 세션 유실로 이어지지 않게 한다. |
| 운영 복잡도 | Redis, DB, token revoke list, TTL, serialization compatibility를 운영해야 한다. |

## 상태를 먼저 분류한다
세션 분리 판단은 상태의 종류를 나누는 데서 시작한다.
| 상태 | 예시 | 인스턴스 메모리에 둬도 되는가? |
| --- | --- | --- |
| 요청 내 임시 상태 | request validation result | 가능하다. 요청이 끝나면 사라져도 된다. |
| 인증 세션 | login principal, roles | 보통 불가하다. 인스턴스 변경에도 유지되어야 한다. |
| CSRF token | form 제출 보호 token | 저장 방식에 따라 session store나 cookie 전략이 필요하다. |
| 장바구니 | 비로그인/로그인 cart | 유실 허용 여부와 전환 정책을 정해야 한다. |
| idempotency key | 결제/주문 중복 방지 | 인스턴스 장애와 retry를 넘어 유지되어야 한다. |
| local cache | 상품 이름, 설정값 | 재생성 가능하고 stale 허용 범위가 있으면 가능하다. |
세션과 중복 방지 상태를 메모리에 두면 서버 증설이 곧 사용자 경험 변화가 된다.
인스턴스가 늘거나 줄 때 사용자가 로그아웃되거나 중복 주문이 발생할 수 있다.

## 대표 시나리오
Spring Boot 로그인 서비스를 8개 Pod로 운영한다고 하자.
| 항목 | 값 |
| --- | ---: |
| 동시 로그인 사용자 | 300,000 |
| 세션 평균 크기 | 2KB |
| 세션 TTL | 30분 |
| peak authenticated request | 12,000 QPS |
| rolling deploy 주기 | 주 3회 |
| 사용자 로그아웃 허용 영향 | 낮음 |
서버 메모리 세션이면 Pod 하나가 죽을 때 그 Pod에 붙어 있던 사용자는 인증 상태를 잃는다.
sticky session을 쓰면 정상 요청은 유지될 수 있지만, Pod 장애나 배포 때 같은 문제가 남는다.
session store를 쓰면 인스턴스 독립성은 높아지지만 Redis가 인증 경로의 핵심 의존성이 된다.

## 세션 메모리 계산
세션 store 용량은 세션 수와 값 크기만으로 끝나지 않는다.
```text
concurrent_sessions = 300,000
avg_session_size = 2KB
redis_overhead_factor = 1.8
replication_factor = 2
memory = 300,000 * 2KB * 1.8 * 2
       = 약 2.16GB
```
이 계산은 최소치다.
serialization metadata, key length, fragmentation, expire dictionary overhead가 붙는다.
세션 크기가 10KB로 커지면 같은 사용자 수에서 10GB 이상이 필요할 수 있다.
세션에는 필요한 식별자만 넣고, 큰 profile이나 권한 목록은 별도 조회 전략을 둔다.

## Spring Session 경계
Spring에서 session store를 분리할 때 설정은 짧다.
```yaml
spring:
  session:
    store-type: redis
    timeout: 30m
```
설정이 짧다고 설계가 끝난 것은 아니다.
다음 항목을 같이 고정해야 한다.
| 항목 | 판단 |
| --- | --- |
| timeout | 보안과 UX 사이의 균형이다. 짧으면 재로그인이 많고 길면 탈취 위험이 커진다. |
| principal size | 세션 값이 커질수록 Redis memory와 network가 커진다. |
| serialization | 배포 중 old/new class 호환성이 깨지면 세션 역직렬화가 실패한다. |
| logout | session 삭제가 모든 인스턴스에 즉시 반영되어야 한다. |
| role change | 권한 변경 즉시 반영이 필요한지 TTL까지 지연 가능한지 정한다. |

## API 계약에 남길 것
세션 만료와 revoke는 사용자에게 보이는 계약이다.
```http
GET /me
401 Unauthorized
{
  "code": "SESSION_EXPIRED",
  "message": "다시 로그인해야 합니다."
}
```
Redis 장애 때 모든 요청을 500으로 만들지, 로그인 사용자만 제한할지, 일부 read API를 비로그인 상태로 낮출지 정해야 한다.
인증이 필요한 주문/결제 API는 fallback이 어렵다.
반면 공개 상품 조회는 세션 장애와 분리할 수 있다.

## Token 방식과 비교한다
JWT 같은 self-contained token은 session store 호출을 줄일 수 있다.
하지만 logout, 탈취 대응, 권한 변경 즉시 반영은 별도 상태를 요구한다.
| 방식 | 장점 | 비용 |
| --- | --- | --- |
| 서버 메모리 세션 | 구현이 단순하고 빠르다 | scale out, 배포, 장애에 약하다. |
| Redis session | 인스턴스 독립성이 높다 | Redis 장애와 TTL, memory 운영이 필요하다. |
| JWT access token | 매 요청 저장소 조회를 줄인다 | revoke, role change, token leak 대응이 어렵다. |
| JWT + refresh store | 성능과 통제의 균형 | token rotation, blacklist, device 관리가 필요하다. |
Stateless라는 단어만 보고 JWT를 선택하면 위험하다.
서비스가 요구하는 logout 강도와 권한 변경 반영 시간을 먼저 봐야 한다.

## 장애 시나리오
Redis session store가 느려지면 인증 경로 전체가 느려진다.
이때 API 서버 CPU는 남아 있어도 사용자 요청은 timeout으로 실패할 수 있다.
관측 지표는 다음을 포함해야 한다.
| 지표 | 이유 |
| --- | --- |
| session_read_latency_p95 | 인증 경로의 추가 latency를 본다. |
| session_write_error_rate | login, logout, renewal 실패를 본다. |
| active_session_count | memory 추정과 TTL 정책을 검증한다. |
| redis_evicted_keys | 세션 유실 위험을 본다. |
| unauthorized_rate_by_reason | 만료, revoke, 장애를 구분한다. |

## 개인 프로젝트 기준
- 단일 인스턴스라도 세션을 어디에 저장하는지 문서에 적는다.
- scale out할 계획이 있으면 서버 메모리 세션의 전환 조건을 남긴다.
- 세션에 큰 객체를 넣지 않고 사용자 id와 최소 권한 정보만 둔다.
- logout과 만료 응답을 API 계약으로 정한다.
- Redis를 쓰지 않는다면 장애와 배포 때 로그아웃이 허용되는지 명시한다.

## 기업 운영 기준
- session store는 인증 경로의 핵심 의존성으로 SLO와 alert를 둔다.
- rolling deploy 중 세션 serialization 호환성을 검증한다.
- 권한 변경, 강제 로그아웃, 계정 정지 반영 시간을 정책으로 둔다.
- Redis memory, eviction, replication lag, failover 시간을 capacity review에 포함한다.
- 인증 장애 때 공개 API, 로그인 API, 결제 API를 어떻게 분리할지 runbook에 둔다.

## 위험 신호
- `stateless`라고 말하지만 `HttpSession`에 큰 객체를 저장한다.
- sticky session으로 문제를 덮고 Pod 장애 때 사용자 영향 범위를 계산하지 않는다.
- JWT를 쓰면 logout과 권한 변경 문제가 자동 해결된다고 설명한다.
- 세션 TTL과 Redis eviction 정책이 없다.
- 세션 역직렬화 실패를 배포 위험으로 보지 않는다.
- session store 장애가 모든 API 장애로 번지는지 확인하지 않는다.

## 확인 질문
- 확인 질문: Stateless 서버는 어떤 상태를 갖지 않아야 하는가?
	- 답변: 요청 사이에 유지되어야 하고 다른 인스턴스에서도 일관되게 보여야 하는 사용자 상태를 로컬 메모리에 갖지 않아야 한다.
- 확인 질문: 세션을 Redis로 옮기면 무엇이 좋아지고 무엇이 나빠지는가?
	- 답변: 수평 확장과 failover는 쉬워지지만 Redis latency, memory, TTL, 장애 대응이라는 운영 복잡도가 생긴다.
- 확인 질문: JWT가 항상 session store보다 좋은 선택인가?
	- 답변: 아니다. 즉시 logout, 권한 변경 반영, 탈취 대응이 강하게 필요하면 별도 상태 저장이 필요할 수 있다.
