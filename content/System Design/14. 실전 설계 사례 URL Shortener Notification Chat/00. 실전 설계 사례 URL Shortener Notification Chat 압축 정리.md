# 실전 설계 사례 URL Shortener Notification Chat

### 3줄 요약
- 실전 설계 사례 URL Shortener Notification Chat의 핵심은 대표 서비스를 요구사항, 트래픽, 저장소, 캐시, queue, 일관성으로 풀어내는 흐름이다.
- 백엔드 개발자는 요구사항을 API, 트래픽, 상태, 캐시, queue, 일관성, 장애 격리, 운영 지표로 바꿔 설명해야 한다.
- 이 챕터는 기술 이름을 외우는 문서가 아니라 선택지별 trade-off와 실패 비용을 판단하는 문서다.

### 핵심 정리
- 기준 상황은 `URL 단축, 알림, 채팅, 피드 설계 리뷰`이다.
- 설계 입력은 기능 범위, 피크 트래픽, 데이터 보존 기간, 읽기/쓰기 비율, 장애 허용 범위, 운영 수준이다.
- 설계 출력은 API 계약, 컴포넌트 배치, 상태 저장 위치, 캐시/queue 사용 여부, 일관성 보장, 장애 격리, 관측 지표다.
- 대표 지표는 `redirect latency, delivery success, fanout latency`이다.
- 개인 프로젝트에서는 선택 이유, timeout, 로그, 재현 가능한 장애 시나리오를 남긴다.
- 기업 운영에서는 SLO, owner, alert, rollback, migration, 비용 영향까지 설계 문서에 포함한다.

### 헷갈리는 지점
- System Design을 아키텍처 그림 그리기로 오해하기 쉽다. 컴포넌트가 많으면 설계가 성숙해 보이기 때문이다.
	- 핵심은 컴포넌트가 어떤 요구사항 때문에 필요했고, 없으면 무엇이 깨지는지 설명하는 것이다.
	- 그림은 결론이 아니라 트래픽, 상태, 장애 경계를 검토하는 도구다.
- 성능 개선 선택이 항상 좋은 선택이라고 생각하기 쉽다. p95가 낮아지면 성공처럼 보이기 때문이다.
	- 핵심은 성능 개선이 정합성 약화, 복구 난이도, 운영 비용 증가로 바뀔 수 있다는 점이다.
	- 캐시, queue, replica, shard는 도입 후 생기는 실패 모드까지 같이 설계해야 한다.
- 개인 프로젝트에는 운영 기준이 과하다고 느끼기 쉽다. 트래픽이 작으면 장애 가능성도 작아 보이기 때문이다.
	- 핵심은 작은 서비스도 timeout, idempotency, backup, 로그가 없으면 문제를 설명하고 복구하기 어렵다는 점이다.

### 확인 질문
- 확인 질문: 이 챕터의 설계 선택은 무엇을 바꾸는가?
	- 답변: 대표 서비스를 요구사항, 트래픽, 저장소, 캐시, queue, 일관성으로 풀어내는 흐름이므로 성능, 정합성, 장애 격리, 운영 복잡도 중 어떤 축이 바뀌는지 지표와 함께 설명해야 한다.
- 확인 질문: 설계 문서에서 기술 이름만 쓰면 부족한 이유는 무엇인가?
	- 답변: 기술이 해결하는 요구사항, 새로 만드는 실패 비용, 운영자가 볼 지표가 드러나지 않기 때문이다.
- 확인 질문: 개인 프로젝트와 기업 운영 기준은 왜 나누어야 하는가?
	- 답변: 같은 구조라도 필요한 관측, 복구, 배포, 책임 분리 수준이 다르기 때문이다.
