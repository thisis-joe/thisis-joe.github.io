## 개요

이 문서의 주제는 `Java IO NIO와 서버 처리 모델`이다. Java IO, NIO, Servlet container, Netty 처리 모델의 차이를 백엔드 관점으로 정리한다.

먼저 붙잡을 기준은 다음 문장이다. I/O API 선택은 thread 모델 선택이다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: I/O API 선택은 thread 모델 선택이다.
- Blocking은 현재 thread가 결과를 기다리는 동안 다른 작업을 처리하지 못하는 실행 방식이다.
- Non-blocking은 대기 중인 I/O를 OS나 event loop에 맡기고 thread 점유를 줄이는 방식이지만 CPU 작업 자체가 사라지지는 않는다.
- Async는 호출자와 실행자를 분리한다. 실행자가 부족하거나 queue가 무제한이면 병목 위치만 바뀐다.
- Event loop는 적은 thread로 많은 연결을 다루지만 loop 안에서 blocking 호출이나 긴 CPU 작업을 하면 연결 전체가 지연된다.
- 실전 선택은 유행보다 외부 I/O 시간, 동시 연결 수, 팀의 디버깅 능력, backpressure 설계에 따라 달라진다.

## 문서별 핵심 구분

- Java IO는 thread-per-blocking 작업 모델로 이해하기 쉽다.
- NIO는 readiness와 selector를 통해 thread 점유를 줄인다.
- 서버 처리 모델은 코드 스타일보다 thread와 queue 위치를 바꾼다.

## 원리

Java classic IO는 `read()`나 `write()` 호출에서 thread가 기다리는 모델로 이해하기 쉽다. 코드 흐름은 단순하지만 연결 수와 대기 시간이 늘면 thread 요구량도 같이 커진다.

Java NIO는 channel, buffer, selector를 통해 "지금 읽거나 쓸 준비가 된 연결"을 골라 처리한다. 적은 thread로 많은 연결 상태를 관리할 수 있지만 상태 전이와 buffer 관리가 복잡해진다.

Servlet container와 Netty는 이 차이를 서버 처리 모델로 드러낸다. Spring MVC/Tomcat 동기 요청은 worker thread가 요청을 끝까지 들고 가는 쪽에 가깝고, Netty/WebFlux는 event loop와 callback 흐름을 중심으로 한다.

`Java IO NIO와 서버 처리 모델` 관점에서 중요한 점은 API 이름보다 thread와 queue 위치를 보는 것이다. 같은 endpoint라도 MVC, Servlet async, WebFlux, Netty 중 무엇을 쓰는지에 따라 병목이 worker thread, event loop, 별도 executor, socket queue 중 다른 위치에 생긴다.

## Java/Spring 연결

- Spring MVC blocking 모델은 단순하고 thread dump로 읽기 쉽지만 동시 blocking I/O가 많으면 worker thread가 빠르게 찬다.
- WebFlux나 Netty 기반 처리는 event loop를 막지 않는다는 전제가 깨지면 MVC보다 더 넓게 지연이 번질 수 있다.
- `CompletableFuture.supplyAsync`는 호출을 비동기로 만들지만, 내부가 blocking이면 결국 executor thread를 점유한다.
- DB JDBC driver는 일반적으로 blocking I/O이므로 reactive Controller를 써도 DB 구간에서 별도 전략이 필요하다.
- Timeout, queue size, bulkhead, retry backoff가 없으면 async 구조는 장애를 흡수하지 못하고 증폭할 수 있다.

## 코드와 설정 예시

```text
Blocking IO
  worker thread -> read/write 대기 -> 처리 완료

NIO/Event loop
  selector -> ready channel 확인 -> 짧은 handler 실행 -> 다음 event
```

예시는 IO API 선택이 thread 모델 선택으로 이어진다는 점을 보기 위한 것이다. 장애 중에는 어떤 thread가 socket read/write를 기다리는지, event loop가 막혔는지, 별도 executor queue가 쌓였는지를 나눠 본다.

## 관찰 명령

```bash
ss -tanp | grep java | head
jcmd <pid> Thread.print
lsof -p <pid> | head
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| Tomcat busy thread가 max 근처 | blocking I/O 또는 긴 요청 처리 | thread dump와 endpoint별 latency |
| executor queue가 계속 증가 | worker 부족 또는 downstream 지연 | active/queued/rejected 지표 |
| event loop thread CPU가 높음 | loop 안 CPU 작업 또는 blocking 호출 | JFR, thread name, stack trace |
| timeout 후 retry 급증 | backpressure 실패 | retry 로그와 downstream error rate |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 요청 thread가 어디서 멈췄는지 thread dump로 본다.
2. 외부 API, DB, file I/O 호출 시간이 전체 latency에서 차지하는 비율을 분리한다.
3. Executor active, queue, rejected 지표를 확인한다.
4. Async 작업이 같은 pool에 다시 작업을 제출하며 기다리는 구조가 있는지 찾는다.
5. 비필수 작업은 rate limit, circuit breaker, 기능 차단으로 먼저 줄인다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- MVC, Servlet async, WebFlux, Netty 중 실제 runtime 모델을 먼저 확인한다.
- thread dump에서 `http-nio`, `reactor-http`, `Netty`, custom executor 이름을 분리한다.
- JDBC나 legacy client가 blocking이면 reactive wrapper만으로 non-blocking이 되지 않는다.
- buffer 크기와 backpressure 설정은 memory 사용량과 같이 본다.
- 서버 처리 모델을 바꾸면 테스트도 latency 평균이 아니라 p95/p99와 saturation 기준으로 본다.

## 주니어 팁

- `Java IO NIO와 서버 처리 모델`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Java IO NIO와 서버 처리 모델`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- WebFlux를 쓰지만 내부 DB/client 호출은 전부 blocking이다.
- event loop와 worker executor의 지표를 따로 보지 않는다.
- socket 수는 늘었는데 file descriptor limit을 확인하지 않는다.
- buffer 누적으로 heap이나 direct memory가 압박받는다.
- 처리 모델을 바꿨는데 운영팀이 볼 thread name과 metric이 없다.

## 확인 질문

- `Java IO NIO와 서버 처리 모델`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
