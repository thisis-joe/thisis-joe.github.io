## 개요

이 문서의 주제는 `Listen Backlog와 Accept Queue`이다. 서버가 연결을 받는 과정에서 backlog와 accept queue가 만드는 병목을 정리한다.

먼저 붙잡을 기준은 다음 문장이다. 요청은 Controller 이전에도 줄을 선다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 요청은 Controller 이전에도 줄을 선다.
- Socket은 OS가 관리하는 통신 객체이고 Linux에서는 file descriptor로 다뤄진다.
- Port는 endpoint 식별자이고 socket은 상태를 가진 연결 또는 수신 대기 객체다.
- 연결은 SYN queue, accept queue, WAS connector, worker thread를 지나 Controller로 들어온다.
- TIME_WAIT은 TCP 정상 종료 과정의 일부이지만 과도한 connection churn, short timeout, keep-alive 불일치의 신호가 될 수 있다.
- `ss`와 `lsof`는 socket state, local/remote address, process 매핑을 연결하는 기본 도구다.

## 문서별 핵심 구분

- 요청은 Controller 전에 SYN queue와 accept queue에서 대기할 수 있다.
- acceptCount와 backlog는 Java thread 이전의 완충 지점이다.
- queue drop은 애플리케이션 로그 없이 client timeout으로 보일 수 있다.

## 원리

Socket은 OS가 관리하는 통신 객체이고 Linux에서는 file descriptor로 다뤄진다.

Port는 endpoint 식별자이고 socket은 상태를 가진 연결 또는 수신 대기 객체다.

연결은 SYN queue, accept queue, WAS connector, worker thread를 지나 Controller로 들어온다.

`Listen Backlog와 Accept Queue` 관점에서 중요한 점은 지표 하나로 원인을 확정하지 않는 것이다. thread dump는 Java 코드 위치를 보여 주지만 CPU 사용량이나 I/O 대기 시간은 OS 지표로 확인해야 한다. 반대로 OS 지표만 보면 어떤 Java 코드 경로가 문제인지 알기 어렵다.

## Java/Spring 연결

- Tomcat connector의 `maxThreads`, `acceptCount`, `connectionTimeout`, keep-alive 설정은 OS socket queue와 Java worker thread 사이의 경계다.
- Controller 로그가 없는데 client timeout이 나면 요청이 Spring에 도달하기 전 socket queue나 LB 구간에서 막혔을 수 있다.
- WebClient, RestTemplate, DB driver는 모두 socket과 FD를 사용하므로 outbound connection leak도 inbound 장애처럼 보일 수 있다.
- Actuator `tomcat.connections.*`, `tomcat.threads.*`와 `ss` 출력은 같은 시간대에 비교해야 의미가 있다.
- 서버를 늘리면 inbound는 분산될 수 있지만 downstream으로 나가는 connection 수는 오히려 증가할 수 있다.

## 코드와 설정 예시

```properties
server.tomcat.threads.max=200
server.tomcat.accept-count=100
server.connection-timeout=5s
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 코드가 thread를 오래 점유하는지, heap에 객체를 남기는지, socket이나 file descriptor를 여는지, GC나 context switch를 늘리는지 질문해야 한다.

## 관찰 명령

```bash
ss -ltnp
ss -tan state syn-recv
cat /proc/net/netstat | grep -E 'Listen|TCP'
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| SYN-RECV 증가 | handshake 지연, backlog 압박 | ss state syn-recv, LB 로그 |
| ESTABLISHED 과다 | keep-alive, client 폭주, connection leak | ss, lsof, tomcat connections |
| TIME_WAIT 급증 | 짧은 연결 반복, keep-alive 미사용 | client/server connection reuse |
| accept queue drop | 애플리케이션 accept 지연 | netstat counters, Tomcat busy thread |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. `ss -s`로 전체 socket 상태 분포를 본다.
2. Listen port가 어떤 process에 붙어 있는지 확인한다.
3. SYN, ESTABLISHED, TIME_WAIT 중 어느 상태가 비정상적으로 많은지 나눈다.
4. Tomcat busy thread와 accept/backlog 지표를 같이 본다.
5. Inbound와 outbound connection을 remote address 기준으로 분리한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 요청은 Controller 전에 SYN queue와 accept queue에서 대기할 수 있다. 이 기준을 실제 지표와 연결해 확인한다.
- acceptCount와 backlog는 Java thread 이전의 완충 지점이다. 정상 상태의 값을 먼저 남겨 장애 상태와 비교한다.
- queue drop은 애플리케이션 로그 없이 client timeout으로 보일 수 있다. 관련 명령은 한 번이 아니라 시간 간격을 두고 반복 수집한다.
- `Listen Backlog와 Accept Queue` 문제는 코드 수정, 설정 변경, capacity 조정 중 어디에 속하는지 분리한다.
- 장애 회고에는 확인한 후보와 배제한 후보를 같이 남긴다.

## 주니어 팁

- `Listen Backlog와 Accept Queue`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Listen Backlog와 Accept Queue`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- 요청은 Controller 전에 SYN queue와 accept queue에서 대기할 수 있다. 이 차이를 무시하고 한 가지 지표로 결론을 낸다.
- acceptCount와 backlog는 Java thread 이전의 완충 지점이다. 관련 정상 기준선 없이 현재 값만 보고 판단한다.
- queue drop은 애플리케이션 로그 없이 client timeout으로 보일 수 있다. 증거를 남기지 않고 재시작이나 설정 변경부터 한다.
- `Listen Backlog와 Accept Queue` 문제를 다른 계층의 문제와 구분하지 못한다.
- 완화 조치가 성공했다는 이유로 근본 원인 기록을 생략한다.

## 확인 질문

- `Listen Backlog와 Accept Queue`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
