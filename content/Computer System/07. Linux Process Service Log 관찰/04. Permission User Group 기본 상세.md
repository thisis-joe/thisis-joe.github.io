## 개요

이 문서의 주제는 `Permission User Group 기본`이다. Linux permission, user, group이 Java 서버 파일 접근과 운영 명령에 미치는 영향을 설명한다.

먼저 붙잡을 기준은 다음 문장이다. 권한은 런타임 계약이다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 권한은 런타임 계약이다.
- Linux에서 Java 서버는 process로 실행되고, 운영 환경에서는 대개 systemd service가 생명주기와 로그, limit을 관리한다.
- `ps`, `top`, `journalctl`, `systemctl`은 장애 중 가장 먼저 사용할 수 있는 낮은 비용의 관찰 도구다.
- Service 파일에는 실행 user, working directory, environment, restart policy, file descriptor limit 같은 운영 계약이 들어 있다.
- Permission 문제는 파일 읽기 실패, 로그 쓰기 실패, dump 생성 실패, 낮은 port binding 실패로 나타난다.
- 운영 명령은 관찰도 부하를 만들 수 있으므로 범위, 시간, 출력량을 제한해야 한다.

## 문서별 핵심 구분

- 운영 process는 특정 user/group 권한으로 파일과 port에 접근한다.
- permission denied는 설정 문제가 아니라 런타임 계약 위반이다.
- dump, log, upload path는 service user 권한으로 검증해야 한다.

## 원리

Linux에서 Java 서버는 process로 실행되고, 운영 환경에서는 대개 systemd service가 생명주기와 로그, limit을 관리한다.

`ps`, `top`, `journalctl`, `systemctl`은 장애 중 가장 먼저 사용할 수 있는 낮은 비용의 관찰 도구다.

Service 파일에는 실행 user, working directory, environment, restart policy, file descriptor limit 같은 운영 계약이 들어 있다.

`Permission User Group 기본` 관점에서 중요한 점은 지표 하나로 원인을 확정하지 않는 것이다. thread dump는 Java 코드 위치를 보여 주지만 CPU 사용량이나 I/O 대기 시간은 OS 지표로 확인해야 한다. 반대로 OS 지표만 보면 어떤 Java 코드 경로가 문제인지 알기 어렵다.

## Java/Spring 연결

- Spring Boot jar는 단순히 `java -jar`가 아니라 JVM option, profile, environment, working directory에 영향을 받는다.
- Actuator health가 실패하더라도 process는 살아 있을 수 있고, process가 살아 있어도 service dependency는 실패할 수 있다.
- journalctl timestamp와 애플리케이션 log timestamp가 timezone과 format에서 어긋나면 장애 타임라인이 흔들린다.
- Heap dump나 GC log 파일을 만들 권한이 없으면 장애 중 필요한 증거를 남기지 못한다.
- systemd restart policy는 장애 완화에는 유용하지만 crash loop를 숨길 수 있다.

## 코드와 설정 예시

```bash
systemctl status my-app
journalctl -u my-app --since "10 min ago" -o short-iso
ps -o pid,ppid,user,stat,pcpu,pmem,etime,args -p <pid>
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 코드가 thread를 오래 점유하는지, heap에 객체를 남기는지, socket이나 file descriptor를 여는지, GC나 context switch를 늘리는지 질문해야 한다.

## 관찰 명령

```bash
id myapp
ls -l /var/log/my-app
namei -l /var/log/my-app/app.log
cat /proc/<pid>/status | grep -E 'Uid|Gid'
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| process는 살아 있으나 health 실패 | 앱 내부 dependency 실패 | Actuator health detail, logs |
| service restart 반복 | crash loop, OOM kill, config error | journalctl, systemctl status |
| permission denied | user/group/path 권한 문제 | id, ls -l, namei |
| dump/log 파일 생성 실패 | working directory, disk, 권한 | service user와 target path |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 현재 실행 중인 PID와 command line을 확인한다.
2. systemd service 정의와 실제 실행 user, limit을 확인한다.
3. journalctl에서 장애 시간대의 warning/error를 본다.
4. 애플리케이션 로그와 OS/service 로그 timestamp를 맞춘다.
5. 변경 명령 전에는 읽기 전용 증거를 먼저 남긴다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 운영 process는 특정 user/group 권한으로 파일과 port에 접근한다. 이 기준을 실제 지표와 연결해 확인한다.
- permission denied는 설정 문제가 아니라 런타임 계약 위반이다. 정상 상태의 값을 먼저 남겨 장애 상태와 비교한다.
- dump, log, upload path는 service user 권한으로 검증해야 한다. 관련 명령은 한 번이 아니라 시간 간격을 두고 반복 수집한다.
- `Permission User Group 기본` 문제는 코드 수정, 설정 변경, capacity 조정 중 어디에 속하는지 분리한다.
- 장애 회고에는 확인한 후보와 배제한 후보를 같이 남긴다.

## 주니어 팁

- `Permission User Group 기본`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Permission User Group 기본`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- 운영 process는 특정 user/group 권한으로 파일과 port에 접근한다. 이 차이를 무시하고 한 가지 지표로 결론을 낸다.
- permission denied는 설정 문제가 아니라 런타임 계약 위반이다. 관련 정상 기준선 없이 현재 값만 보고 판단한다.
- dump, log, upload path는 service user 권한으로 검증해야 한다. 증거를 남기지 않고 재시작이나 설정 변경부터 한다.
- `Permission User Group 기본` 문제를 다른 계층의 문제와 구분하지 못한다.
- 완화 조치가 성공했다는 이유로 근본 원인 기록을 생략한다.

## 확인 질문

- `Permission User Group 기본`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
