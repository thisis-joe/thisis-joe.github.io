## 개요

이 문서의 주제는 `운영 중 안전한 명령 사용`이다. 장애 중 명령 사용의 안전 기준과 증거 확보 순서를 정리한다.

먼저 붙잡을 기준은 다음 문장이다. 명령도 운영 변경이다. `jcmd`, `lsof`, `tail`, `grep`, `kill`, `systemctl restart`는 모두 증거를 만들거나 지우고, 때로는 CPU/I/O 부하를 추가한다. 장애 중 명령은 읽기 전용, 범위 제한, 시간 제한, 기록 가능성을 기준으로 선택해야 한다.

## 핵심 모델

- 판단 기준: 명령도 운영 변경이다.
- 안전한 운영 명령은 대상 PID, 범위, 예상 부하, 저장 위치, 중단 조건이 명확하다.
- `ps`, `uptime`, 제한된 `journalctl`은 낮은 비용의 1차 증거 수집에 적합하다.
- Thread dump, heap dump, JFR, 대량 `lsof`는 유용하지만 CPU/I/O/stop-the-world/파일 크기 영향을 고려해야 한다.
- `kill`, `restart`, 설정 변경은 증거를 없앨 수 있으므로 완화 목적과 rollback 조건을 먼저 적어야 한다.
- 명령 결과에는 시각, host, PID, 실행자, 필터 조건을 남겨야 회고에서 재사용할 수 있다.

## 문서별 핵심 구분

- 관찰 명령도 CPU, I/O, lock 부하를 만들 수 있다.
- 장애 중에는 읽기 전용, 범위 제한, 시간 제한을 우선한다.
- 변경 명령 전에는 증거와 rollback 조건을 남긴다.

## 원리

운영 중 명령은 관찰과 변경 사이의 스펙트럼에 있다. `date`, `ps`, `uptime`은 읽기 비용이 낮고, heap dump나 JFR은 관찰이지만 파일 I/O와 런타임 부담을 만든다. `restart`와 `kill`은 명백한 변경이다.

장애 중에는 먼저 낮은 비용의 snapshot으로 대상과 시간대를 고정한다. PID, host, service, 최근 로그, thread 수, CPU/RSS 같은 기본 증거가 없으면 이후 dump나 재시작 결과를 해석하기 어렵다.

부하가 큰 명령은 범위를 줄인다. `journalctl --since`, `tail -n`, `lsof -p <pid>`, JFR duration, dump 저장 경로처럼 제한을 걸어야 장애 대응이 추가 장애가 되지 않는다.

변경 명령은 완화가 목적일 때만 실행하고, 실행 전후 기대 효과와 rollback 조건을 남긴다. 재시작은 증상을 없앨 수 있지만 원인 증거도 함께 없앨 수 있다.

## Java/Spring 연결

- Spring Boot 장애 대응에서는 Actuator metric, thread dump, heap dump, JFR, journal 로그가 서로 다른 비용과 위험을 가진다.
- `/actuator/metrics` 조회는 낮은 비용이지만 heap dump나 JFR은 duration, 파일 크기, 저장 위치를 통제해야 한다.
- `jcmd Thread.print`는 원인 보존에 유용하지만 대상 PID를 틀리면 전혀 다른 process 증거가 된다.
- `systemctl restart`는 빠른 완화 수단이지만 Spring runtime 상태, thread stack, memory 증거를 없앨 수 있다.
- Runbook은 어떤 명령을 먼저 실행하고 어떤 조건에서 변경 명령으로 넘어갈지 Spring 운영 지표와 함께 정의해야 한다.
- Spring 코드 리뷰에서는 `운영 중 안전한 명령 사용` 판단 기준이 어떤 thread, pool, timeout, resource 설정으로 드러나는지 확인한다.

## 코드와 설정 예시

```bash
date -Is
ps -o pid,stat,pcpu,pmem,etime,args -p <pid>
jcmd <pid> Thread.print > /tmp/thread-$(date +%s).txt
```

예시는 먼저 시각과 process snapshot을 남긴 뒤 thread dump를 파일로 저장하는 흐름이다. stdout에 긴 dump를 그대로 뿌리기보다 파일 경로, 크기, 보관 위치를 통제한다.

## 관찰 명령

```bash
date -Is
uptime
ps -o pid,stat,pcpu,pmem,args -p <pid>
jcmd <pid> Thread.print > /tmp/thread-$(date +%s).txt
```

`운영 중 안전한 명령 사용` 관찰 명령은 결론이 아니라 가설 확인 도구다. 운영 중에는 반복 간격, 대상 PID, 수집 시각을 함께 남기고 출력이 큰 명령은 범위를 제한한다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| 명령 출력이 너무 큼 | 범위 제한 부족 | `--since`, `head`, `tail -n`, PID filter |
| dump 파일 생성 실패 | 권한, disk, 경로 문제 | target path, service user |
| dump 후 latency 악화 | 수집 명령 부하 | duration, 파일 크기, 반복 횟수 |
| 재시작 후 증거 사라짐 | 변경 명령 선실행 | dump/log/metric 선수집 여부 |

`운영 중 안전한 명령 사용`에서는 핵심 신호와 보조 지표를 같은 시간축에서 맞춘다. 먼저 변한 신호와 뒤따라 포화된 신호를 분리해야 원인과 결과를 구분할 수 있다.

## 장애 상황에서 보는 순서

1. 명령 대상 host, PID, service, 시간대를 먼저 기록한다.
2. 낮은 비용의 읽기 전용 명령으로 현재 상태를 남긴다.
3. Dump/JFR/lsof처럼 비용 있는 명령은 범위, duration, 저장 위치를 정한다.
4. 변경 명령은 기대 효과, 영향 범위, rollback 조건을 적은 뒤 실행한다.
5. 실행 후 같은 관찰 명령을 다시 수행해 실제 완화 여부를 확인한다.

이 순서는 `운영 중 안전한 명령 사용` 후보를 빠르게 좁히기 위한 기본 루틴이다. 결론을 내리기 전에는 애플리케이션 증거와 JVM/OS 증거를 최소 한 번 이상 맞춘다.

## 실전 팁

- 긴 로그 출력은 `--since`, `--until`, `tail -n`으로 제한한다.
- Thread dump는 보통 여러 번 짧게 수집하되, 파일명에 시각과 PID를 포함한다.
- Heap dump는 disk 여유, 민감 정보, stop-the-world 가능성을 확인한 뒤 실행한다.
- 재시작 전에는 최소한 PID, command line, thread dump, 주요 metric, 최근 로그를 남긴다.
- 장애 회고에는 실행한 명령뿐 아니라 실행하지 않기로 한 명령과 이유도 남긴다.

## 주니어 팁

- 명령을 치기 전에 "읽기인가 변경인가"를 먼저 구분한다.
- `grep`, `tail`, `journalctl`도 범위를 제한하지 않으면 운영 부하가 될 수 있다.
- 재시작은 빠른 해결처럼 보이지만 증거를 지우는 명령이라는 점을 기억한다.

## 시니어 팁

- Runbook에는 명령, 예상 비용, 출력 위치, 해석 기준, 금지 조건을 같이 적는다.
- Heap dump/JFR/thread dump는 운영 보안 정책과 보관/삭제 정책까지 포함해 표준화한다.
- 변경 명령은 승인 기준, 실행자, rollback 조건, 사후 검증 명령을 한 묶음으로 관리한다.

## Guru급 팁

- `운영 중 안전한 명령 사용` 주제는 단일 snapshot보다 변화 방향이 중요하다. 같은 명령을 간격을 두고 실행해 상태가 증가, 유지, 회복 중 어디인지 본다.
- 고급 도구는 `운영 중 안전한 명령 사용` 가설을 좁힐 때만 사용하고 기본 지표와 모순되는지 먼저 확인한다.
- `운영 중 안전한 명령 사용` 조치 후에는 CPU, memory, socket, disk, pool 중 다음 포화 지점이 어디로 이동했는지 확인한다.

## 위험 신호!

- `lsof`, `journalctl`, `grep`을 전체 범위로 실행해 출력과 부하를 키운다.
- Heap dump 저장 위치와 disk 여유를 확인하지 않는다.
- Thread dump를 한 번만 찍고 순간 상태로 결론을 낸다.
- 재시작 전 증거를 남기지 않아 원인 후보를 모두 잃는다.
- 변경 후 같은 관찰 명령을 다시 실행하지 않아 완화 여부를 증명하지 못한다.

## 확인 질문

- 운영 명령을 실행하기 전에 반드시 정해야 할 것은 무엇인가?
	- 대상 host/PID, 읽기/변경 여부, 범위, 예상 부하, 저장 위치, 중단 조건을 정해야 한다.
- 재시작 전에 최소한 어떤 증거를 남겨야 하는가?
	- PID와 command line, 최근 로그, 핵심 metric, thread dump, 필요 시 heap/JFR 수집 가능 여부를 남겨야 한다.
- 명령 실행 후 같은 관찰 명령을 반복해야 하는 이유는 무엇인가?
	- 변경이 실제로 장애를 완화했는지, 또는 부하를 다른 계층으로 옮겼는지 증명해야 하기 때문이다.
