## 개요

이 문서의 주제는 `Java File IO와 Resource 관리`이다. Java File I/O, stream close, try-with-resources, temp file, multipart 처리를 다룬다.

먼저 붙잡을 기준은 다음 문장이다. close는 기능이 아니라 안정성이다. 이 문서는 이 기준을 Java/Spring 실행 흐름, JVM/OS 관찰 지표, 장애 판단 순서로 연결한다.

## 핵심 모델

- 판단 기준: Java I/O 객체는 OS 자원을 감싼다.
- `InputStream`, `OutputStream`, `Channel`은 닫히기 전까지 FD를 붙잡을 수 있다.
- GC에 close를 맡기는 설계는 고부하에서 FD 고갈로 먼저 드러날 수 있다.
- Classpath resource와 filesystem path는 운영 배포 방식에 따라 의미가 달라진다.
- Temp file은 생성보다 cleanup 정책이 운영 안정성을 결정한다.

## 문서별 핵심 구분

- stream close는 기능이 아니라 OS 자원 반환이다.
- try-with-resources는 FD 누수를 막는 기본 방어선이다.
- temp file과 upload directory는 운영 disk 정책과 연결된다.

## 원리

Java File I/O에서 `InputStream`, `OutputStream`, `Channel`은 Java 객체이면서 OS 자원을 감싼다. 객체 참조가 사라지는 것과 FD가 제때 반환되는 것은 같은 말이 아니다.

try-with-resources는 예외가 발생해도 close를 보장하는 기본 방어선이다. close 누락은 낮은 트래픽에서는 숨지만 고부하와 오류 경로에서 FD leak으로 드러난다.

`readAllBytes()`나 전체 파일 메모리 적재는 코드가 짧지만 파일 크기만큼 heap을 사용한다. 큰 파일 다운로드, 업로드, export는 streaming과 backpressure를 먼저 검토해야 한다.

`Java File IO와 Resource 관리` 관점에서 중요한 점은 파일 작업을 기능 코드가 아니라 자원 생명주기로 보는 것이다. open, read/write, flush, close, temp cleanup, permission, disk quota가 모두 운영 계약이다.

## Java/Spring 연결

- `MultipartFile`, `Resource`, `InputStreamResource`는 memory threshold와 temp directory 정책을 확인해야 한다.
- `readAllBytes()`는 구현은 간단하지만 큰 파일에서 heap과 GC 부담을 키운다.
- try-with-resources가 없는 파일/stream 코드는 FD leak 후보로 본다.
- Spring resource abstraction은 classpath와 file path 차이를 숨기므로 운영 권한을 확인한다.
- Download/export API는 streaming, range, timeout, client disconnect 처리를 함께 설계한다.

## 코드와 설정 예시

```java
try (InputStream in = Files.newInputStream(path)) {
    return in.readAllBytes();
}
```

예시는 try-with-resources가 FD 반환을 보장한다는 점을 보기 위한 것이다. 다만 `readAllBytes()`는 큰 파일에서 heap을 크게 쓰므로 실제 다운로드나 export에서는 streaming이 더 안전할 수 있다.

## 관찰 명령

```bash
lsof -p <pid> | wc -l
find /tmp -maxdepth 1 -type f | wc -l
jcmd <pid> Thread.print
```

`Java File IO와 Resource 관리` 관찰 명령은 결론이 아니라 가설 확인 도구다. 운영 중에는 반복 간격, 대상 PID, 수집 시각을 함께 남기고 출력이 큰 명령은 범위를 제한한다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| open files가 limit에 근접 | FD leak 또는 connection 폭주 | lsof, `/proc/<pid>/fd` |
| iowait 증가와 latency 상승 | disk 병목, flush 지연 | iostat, vmstat |
| 로그량 급증 후 API 지연 | 동기 로그 또는 log collector 지연 | log rate, appender queue |
| tmp 사용량 증가 | upload/export/temp cleanup 실패 | tmp directory, lsof deleted |

`Java File IO와 Resource 관리`에서는 핵심 신호와 보조 지표를 같은 시간축에서 맞춘다. 먼저 변한 신호와 뒤따라 포화된 신호를 분리해야 원인과 결과를 구분할 수 있다.

## 장애 상황에서 보는 순서

1. 파일 API stack이 많은지 thread dump에서 확인한다.
2. FD 수와 open file 경로를 `lsof`로 본다.
3. temp directory 사용량과 deleted-open file을 확인한다.
4. 큰 파일을 heap에 올리는 코드가 있는지 찾는다.
5. close, timeout, client disconnect, cleanup 경로를 테스트한다.

이 순서는 Java I/O 코드와 OS resource 회수를 연결하기 위한 루틴이다.

- 큰 파일은 `readAllBytes()` 대신 streaming, range, 비동기 export를 검토한다.
- multipart temp directory와 max file size는 disk 용량 정책과 함께 둔다.

## 위험 신호!

- finally나 try-with-resources 없이 stream을 연다.
- 오류가 난 업로드 temp file을 정리하지 않는다.
- 큰 파일을 `readAllBytes()`로 heap에 통째로 올린다.
- 파일 경로를 상대 경로로 두고 systemd working directory를 확인하지 않는다.
- permission denied를 코드 버그로만 보고 실행 user/group을 확인하지 않는다.
