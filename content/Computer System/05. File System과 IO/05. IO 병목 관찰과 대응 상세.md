>- `IO 병목 관찰과 대응` 관점에서 어떤 실행 비용을 봐야 하는가?
>- 장애 상황에서 어떤 OS/JVM 지표를 먼저 확인하는가?
>- Java/Spring 코드와 운영 지표를 어떻게 연결하는가?

## 개요

이 문서의 주제는 `IO 병목 관찰과 대응`이다. I/O 병목을 CPU, memory, thread 상태와 구분하고 완화하는 루틴을 정리한다.

먼저 붙잡을 기준은 다음 문장이다. iowait와 latency를 함께 본다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: iowait와 latency를 함께 본다.
- File descriptor는 파일뿐 아니라 socket, pipe, eventfd 같은 OS 자원을 가리킨다. 고갈되면 파일 오류와 네트워크 오류가 같이 나타날 수 있다.
- Disk I/O는 page cache, buffer, flush, fsync, storage latency를 거치므로 코드의 `write` 한 줄과 실제 디스크 반영 시점은 다를 수 있다.
- 로그는 문자열 출력이 아니라 CPU, lock, buffer, disk, rotation, 수집 agent를 통과하는 운영 트래픽이다.
- Java stream과 channel은 close가 안정성의 일부다. GC에 맡기면 고부하에서 FD가 먼저 고갈될 수 있다.
- I/O 병목은 thread dump만으로 애매하게 보일 수 있어 `iostat`, `vmstat`, `lsof` 같은 OS 관찰이 필요하다.

## 문서별 핵심 구분

- I/O 병목은 CPU가 낮아도 latency를 크게 만든다.
- iowait, disk await, queue depth를 함께 본다.
- 로그, dump, upload, swap이 같은 disk를 압박할 수 있다.

## 원리

I/O 병목은 CPU 계산이 아니라 storage나 kernel I/O 경로를 기다리는 병목이다. CPU 사용률이 낮아도 요청 latency와 load average가 올라갈 수 있다.

관찰은 `iowait` 하나로 끝나지 않는다. device await, util, queue, dirty/writeback page, FD 수, 로그량, upload/export 작업, swap 여부를 같은 시간대에 맞춰야 한다.

Java thread dump에서는 I/O 대기가 `RUNNABLE` 또는 native method 근처로 보일 수 있다. 그래서 thread state만 보고 CPU bound로 단정하면 안 된다.

`IO 병목 관찰과 대응` 관점에서 중요한 점은 증상 완화와 원인 수정을 분리하는 것이다. 임시로 유입을 줄이거나 로그를 낮추더라도, 근본 원인이 disk capacity인지, 코드의 대량 I/O인지, 수집 agent 지연인지 다시 좁혀야 한다.

## Java/Spring 연결

- Multipart upload는 memory threshold, temp directory, file size limit, cleanup 정책을 함께 가진다.
- Logback/Log4j async appender는 요청 thread를 줄일 수 있지만 queue overflow와 flush 손실 정책을 확인해야 한다.
- 정적 파일 다운로드나 report export가 요청 thread 안에서 오래 실행되면 thread와 FD를 동시에 점유한다.
- Spring resource 로딩은 classpath와 filesystem 경계를 숨기므로 운영 경로와 권한을 확인해야 한다.
- Heap dump, GC log, access log 위치가 같은 disk에 몰리면 장애 중 관찰 작업이 장애를 키울 수 있다.

## 코드와 설정 예시

```text
latency 상승
  CPU 낮음 또는 load 상승
  iostat await/util 증가
  thread dump native I/O 또는 file write 주변 반복
  로그, dump, upload, swap 시간대 대조
```

예시는 I/O 병목을 확인하는 증거 연결 순서다. 애플리케이션 latency, OS disk 지표, thread dump, 같은 시간대의 로그·dump·upload 작업을 맞춰야 원인 후보를 줄일 수 있다.

## 관찰 명령

```bash
iostat -xz 1 5
vmstat 1 5
top -H -p <pid>
jcmd <pid> Thread.print
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| open files가 limit에 근접 | FD leak 또는 connection 폭주 | lsof, `/proc/<pid>/fd` |
| iowait 증가와 latency 상승 | disk 병목, flush 지연 | iostat, vmstat |
| 로그량 급증 후 API 지연 | 동기 로그 또는 log collector 지연 | log rate, appender queue |
| tmp 사용량 증가 | upload/export/temp cleanup 실패 | tmp directory, lsof deleted |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. FD 수와 limit을 먼저 비교한다.
2. `lsof`로 file, socket, deleted file이 어떤 종류로 많은지 나눈다.
3. Disk latency와 iowait를 확인해 파일 시스템 병목인지 본다.
4. 로그량과 rotation, 압축, 수집 agent 상태를 시간대별로 맞춘다.
5. 코드에서는 stream close, try-with-resources, temp file cleanup을 확인한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- `iostat`, `vmstat`, thread dump를 같은 시각에 남긴다.
- 로그 폭주, heap dump, upload/export, backup이 같은 disk를 쓰는지 확인한다.
- 임시 완화는 로그 레벨 조정, 비필수 batch 중지, upload 제한, dump 중지부터 검토한다.
- 근본 해결은 storage 성능, 작업 분리, streaming, 비동기 export, retention 정책으로 나눈다.
- I/O 병목 후에는 새 병목이 CPU, DB, network 중 어디로 이동했는지 다시 본다.

## 주니어 팁

- `IO 병목 관찰과 대응`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `IO 병목 관찰과 대응`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- CPU가 낮으니 서버는 여유 있다고 판단한다.
- iowait만 보고 device await, util, queue를 보지 않는다.
- 장애 중 heap dump를 같은 disk에 남겨 I/O 병목을 키운다.
- 로그량을 줄여 장애가 완화됐는데 원래 로그 폭주 원인을 추적하지 않는다.
- storage capacity와 application I/O 패턴을 서로 다른 팀 문제로 분리해 버린다.

## 확인 질문

- `IO 병목 관찰과 대응`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
