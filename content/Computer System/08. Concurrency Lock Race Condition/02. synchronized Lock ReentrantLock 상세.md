## 개요

이 문서의 주제는 `synchronized Lock ReentrantLock`이다. `synchronized`, `Lock`, `ReentrantLock`의 차이와 Spring 서버에서의 사용 기준을 정리한다.

먼저 붙잡을 기준은 다음 문장이다. lock은 보호 범위와 대기 정책이다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: lock은 보호 범위와 대기 정책이다.
- Race condition은 여러 thread의 실행 순서에 따라 결과가 달라지는 버그다.
- Critical section은 동시에 실행되면 안 되는 공유 상태 접근 구간이다.
- Lock은 안전성을 주지만 대기, contention, deadlock, starvation 비용을 만든다.
- `volatile`, Atomic, concurrent collection은 각각 가시성, 원자성, 자료구조 안전성의 범위가 다르다.
- Thread-safe 설계는 lock을 더 많이 거는 것이 아니라 공유 상태를 줄이고 소유권을 명확히 하는 것이다.

## 문서별 핵심 구분

- `synchronized`는 monitor 기반 mutual exclusion을 제공한다.
- `ReentrantLock`은 timeout, interrupt, fairness 같은 선택지를 제공한다.
- lock 선택보다 lock 범위와 외부 I/O 포함 여부가 더 중요할 때가 많다.

## 원리

Race condition은 여러 thread의 실행 순서에 따라 결과가 달라지는 버그다.

Critical section은 동시에 실행되면 안 되는 공유 상태 접근 구간이다.

Lock은 안전성을 주지만 대기, contention, deadlock, starvation 비용을 만든다.

`synchronized Lock ReentrantLock` 관점에서 중요한 점은 지표 하나로 원인을 확정하지 않는 것이다. thread dump는 Java 코드 위치를 보여 주지만 CPU 사용량이나 I/O 대기 시간은 OS 지표로 확인해야 한다. 반대로 OS 지표만 보면 어떤 Java 코드 경로가 문제인지 알기 어렵다.

## Java/Spring 연결

- Spring singleton bean은 여러 요청 thread가 동시에 접근하므로 mutable field를 두면 공유 상태가 된다.
- `@Transactional`은 DB 정합성 도구이지 Java 객체의 memory race를 자동으로 막지 않는다.
- 분산 환경에서는 JVM lock이 인스턴스 내부에서만 유효하다. 여러 서버가 같은 DB row나 Redis key를 다루면 별도 전략이 필요하다.
- Cache, counter, in-memory map은 작은 서비스에서 시작해 운영 장애의 hot spot이 되기 쉽다.
- Thread dump의 BLOCKED, parking, lock owner 정보는 코드 리뷰보다 빠르게 실제 경합 위치를 보여 준다.

## 코드와 설정 예시

```java
private final ReentrantLock lock = new ReentrantLock();

public void change() {
    lock.lock();
    try {
        updateSharedState();
    } finally {
        lock.unlock();
    }
}
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 코드가 thread를 오래 점유하는지, heap에 객체를 남기는지, socket이나 file descriptor를 여는지, GC나 context switch를 늘리는지 질문해야 한다.

## 관찰 명령

```bash
jcmd <pid> Thread.print | grep -A5 BLOCKED
top -H -p <pid>
jcmd <pid> JFR.start name=lock duration=60s filename=lock.jfr
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| BLOCKED thread 증가 | monitor lock 경합 | lock owner stack |
| CPU는 낮고 요청 정체 | lock wait 또는 condition wait | thread dump 반복 샘플 |
| 데이터 값이 간헐적으로 틀림 | race condition | 공유 mutable state와 복합 연산 |
| 특정 작업만 계속 밀림 | starvation 또는 unfair lock | queue 정책과 lock 사용 구간 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 문제 데이터가 공유 memory인지 DB 상태인지 먼저 나눈다.
2. Thread dump에서 BLOCKED, WAITING, parking stack을 찾는다.
3. Lock을 잡은 상태에서 외부 I/O나 DB 호출을 하는지 확인한다.
4. 공유 컬렉션, static field, singleton bean mutable field를 찾는다.
5. 단일 JVM에서 해결되는 문제인지 다중 인스턴스 문제인지 분리한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- `synchronized`는 monitor 기반 mutual exclusion을 제공한다. 이 기준을 실제 지표와 연결해 확인한다.
- `ReentrantLock`은 timeout, interrupt, fairness 같은 선택지를 제공한다. 정상 상태의 값을 먼저 남겨 장애 상태와 비교한다.
- lock 선택보다 lock 범위와 외부 I/O 포함 여부가 더 중요할 때가 많다. 관련 명령은 한 번이 아니라 시간 간격을 두고 반복 수집한다.
- `synchronized Lock ReentrantLock` 문제는 코드 수정, 설정 변경, capacity 조정 중 어디에 속하는지 분리한다.
- 장애 회고에는 확인한 후보와 배제한 후보를 같이 남긴다.

## 주니어 팁

- `synchronized Lock ReentrantLock`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `synchronized Lock ReentrantLock`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- `synchronized`는 monitor 기반 mutual exclusion을 제공한다. 이 차이를 무시하고 한 가지 지표로 결론을 낸다.
- `ReentrantLock`은 timeout, interrupt, fairness 같은 선택지를 제공한다. 관련 정상 기준선 없이 현재 값만 보고 판단한다.
- lock 선택보다 lock 범위와 외부 I/O 포함 여부가 더 중요할 때가 많다. 증거를 남기지 않고 재시작이나 설정 변경부터 한다.
- `synchronized Lock ReentrantLock` 문제를 다른 계층의 문제와 구분하지 못한다.
- 완화 조치가 성공했다는 이유로 근본 원인 기록을 생략한다.

## 확인 질문

- `synchronized Lock ReentrantLock`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
