## 개요

이 문서의 주제는 `개인 프로젝트와 기업 운영 수준 비교`이다. 규모별로 필요한 관찰, 알림, 복구, 변경 통제의 수준 차이를 정리한다.

먼저 붙잡을 기준은 다음 문장이다. 같은 원리라도 운영 장치의 깊이가 달라진다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 같은 원리라도 운영 장치의 깊이가 달라진다.
- 개인 프로젝트의 최소 기준은 health 확인, 로그 위치, 재시작 방법, timeout, dump 저장 위치를 혼자 재현할 수 있는 상태다.
- 기업 운영의 기준은 SLO, alert, capacity, runbook, 변경 승인, 장애 기록, 책임 경계가 팀 단위로 반복 가능한 상태다.
- 같은 `journalctl`, `top`, `jcmd` 명령도 기업 환경에서는 권한, 감사 로그, 부하, 개인정보 노출, 작업 승인 범위까지 고려해야 한다.
- 작은 서비스에서는 빠른 복구가 중요하지만, 기업 환경에서는 증거 보존과 재발 방지까지 운영 계약에 포함된다.
- 운영 수준은 도구 개수가 아니라 장애가 났을 때 누구나 같은 증거로 같은 판단을 반복할 수 있는지로 판단한다.

## 문서별 핵심 구분

- 개인 프로젝트의 목표는 최소한 원인 추적이 가능한 상태를 만드는 것이다.
- 기업 운영의 목표는 장애를 SLO, 알림, 변경 통제, runbook으로 관리하는 것이다.
- 규모가 달라도 timeout, log, health, backup, dump 확보는 공통 기본값이다.

## 원리

개인 프로젝트에서는 "내가 지금 고칠 수 있는가"가 판단의 중심이 되기 쉽다. 그래서 SSH 접속, 로그 확인, 재시작, 간단한 백업만 있어도 운영처럼 느껴진다. 그러나 이 상태는 담당자가 바뀌거나 장애가 새벽에 나면 바로 취약해진다.

기업 운영에서는 "누가 보아도 같은 절차로 판단할 수 있는가"가 중요하다. health check, alert, dashboard, runbook, incident timeline, 변경 이력, rollback 기준이 필요하다. 기술은 같아도 증거를 남기는 방식과 변경을 통제하는 깊이가 달라진다.

Java/Spring 서버 관점에서는 규모와 무관하게 기본값이 있다. timeout을 정하고, log와 metric을 남기고, heap/thread dump를 확보할 권한과 경로를 준비하고, OS limit과 JVM option을 기록해야 한다.

`개인 프로젝트와 기업 운영 수준 비교` 관점에서 중요한 점은 운영 성숙도를 기능 수로 보지 않는 것이다. 같은 장애를 다시 만났을 때 더 빨리 찾고, 더 안전하게 완화하고, 더 적은 추측으로 근본 원인에 접근할 수 있으면 운영 수준이 올라간 것이다.

## Java/Spring 연결

- Spring Boot jar는 단순히 `java -jar`가 아니라 JVM option, profile, environment, working directory에 영향을 받는다.
- Actuator health가 실패하더라도 process는 살아 있을 수 있고, process가 살아 있어도 service dependency는 실패할 수 있다.
- journalctl timestamp와 애플리케이션 log timestamp가 timezone과 format에서 어긋나면 장애 타임라인이 흔들린다.
- Heap dump나 GC log 파일을 만들 권한이 없으면 장애 중 필요한 증거를 남기지 못한다.
- systemd restart policy는 장애 완화에는 유용하지만 crash loop를 숨길 수 있다.

## 코드와 설정 예시

```bash
systemctl status my-app
journalctl -u my-app --since "10 min ago" -o short-iso
ps -o pid,ppid,user,stat,pcpu,pmem,etime,args -p <pid>
```

예시는 특정 명령을 외우기 위한 것이 아니라 개인 프로젝트에서도 최소 증거를 남기는 순서를 보여 준다. 기업 환경에서는 여기에 승인된 접근 경로, 작업자, 수집 시각, 변경 여부를 함께 기록해야 한다.

## 관찰 명령

```bash
systemctl status my-app
journalctl -u my-app --since today
curl -s localhost:8080/actuator/health
curl -s localhost:8080/actuator/metrics
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| process는 살아 있으나 health 실패 | 앱 내부 dependency 실패 | Actuator health detail, logs |
| service restart 반복 | crash loop, OOM kill, config error | journalctl, systemctl status |
| permission denied | user/group/path 권한 문제 | id, ls -l, namei |
| dump/log 파일 생성 실패 | working directory, disk, 권한 | service user와 target path |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 현재 실행 중인 PID와 command line을 확인한다.
2. systemd service 정의와 실제 실행 user, limit을 확인한다.
3. journalctl에서 장애 시간대의 warning/error를 본다.
4. 애플리케이션 로그와 OS/service 로그 timestamp를 맞춘다.
5. 변경 명령 전에는 읽기 전용 증거를 먼저 남긴다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 개인 프로젝트라도 health check와 로그 위치는 문서화한다.
- 운영 전에는 재시작 방법보다 증거 수집 방법을 먼저 정한다.
- 기업 환경에서는 인프라팀이 보는 지표 이름을 같이 적는다.
- 장애 기준은 감정이 아니라 latency, error rate, saturation으로 둔다.
- 운영 성숙도는 기능 수가 아니라 복구 가능성으로 판단한다.

## 주니어 팁

- `개인 프로젝트와 기업 운영 수준 비교`를 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `개인 프로젝트와 기업 운영 수준 비교`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- 작은 서비스라서 timeout과 로그 보관을 생략한다.
- 기업 환경에서 개인 서버처럼 직접 수정하고 기록을 남기지 않는다.
- 장애 알림이 사용자 신고보다 늦게 온다.
- 재시작 권한은 있는데 dump 수집 권한이 없다.
- 운영 문서가 배포 절차만 있고 관찰 절차가 없다.

## 확인 질문

- `개인 프로젝트와 기업 운영 수준 비교`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
