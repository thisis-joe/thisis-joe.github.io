>- `백엔드 요청과 실행 환경 전체 흐름` 관점에서 어떤 실행 비용을 봐야 하는가?
>- 장애 상황에서 어떤 OS/JVM 지표를 먼저 확인하는가?
>- Java/Spring 코드와 운영 지표를 어떻게 연결하는가?

## 개요

이 문서의 주제는 `백엔드 요청과 실행 환경 전체 흐름`이다. HTTP 요청이 OS socket, WAS connector, Spring handler, JVM heap, scheduler를 지나 응답으로 돌아오는 전체 경로를 다룬다.

먼저 붙잡을 기준은 다음 문장이다. 요청 흐름을 자원 점유 흐름으로 바꿔 읽는다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 요청 흐름을 자원 점유 흐름으로 바꿔 읽는다.
- 요청 흐름은 Controller에서 시작하지 않는다. 클라이언트 연결이 OS socket에 도착하고, WAS connector가 thread나 event loop로 넘긴 뒤에야 Spring handler가 실행된다.
- Application, JVM, OS의 경계를 나누면 같은 지연도 코드 실행, GC, scheduling, socket queue, disk I/O 중 어디서 생겼는지 좁힐 수 있다.
- CPU, memory, I/O, network 지표는 따로 읽지 않는다. 같은 시간대의 latency, error, thread state, resource saturation을 맞춰 읽어야 한다.
- 개인 프로젝트에서는 최소한 health, log, dump, timeout을 준비하고, 기업 운영에서는 alert, SLO, capacity, runbook까지 연결한다.
- 학습 순서는 개념 암기가 아니라 장애 상황에서 어떤 증거를 먼저 볼지 정하는 순서로 잡는다.

## 문서별 핵심 구분

- 요청이 Spring Controller에 들어오기 전에도 OS socket, accept queue, WAS connector 대기가 존재한다.
- Controller 이후에는 Java call stack, DB/client I/O, GC, scheduler 대기가 하나의 latency로 합쳐진다.
- trace id가 있으면 Application 로그와 thread dump, access log를 같은 요청 단위로 묶을 수 있다.

## 원리

요청 흐름은 Controller에서 시작하지 않는다. 클라이언트 연결이 OS socket에 도착하고, WAS connector가 thread나 event loop로 넘긴 뒤에야 Spring handler가 실행된다.

Application, JVM, OS의 경계를 나누면 같은 지연도 코드 실행, GC, scheduling, socket queue, disk I/O 중 어디서 생겼는지 좁힐 수 있다.

CPU, memory, I/O, network 지표는 따로 읽지 않는다. 같은 시간대의 latency, error, thread state, resource saturation을 맞춰 읽어야 한다.

`백엔드 요청과 실행 환경 전체 흐름` 관점에서 중요한 점은 latency를 한 계층의 시간으로만 보지 않는 것이다. Controller 로그는 Spring 이후 경로를 보여 주지만 accept queue, Tomcat worker 대기, DB connection acquire, socket I/O, GC pause가 같은 응답 시간 안에 합쳐질 수 있다.

## Java/Spring 연결

- Spring MVC 요청은 대개 Tomcat worker thread 위에서 실행되므로 요청 지연은 thread 점유 시간과 직접 연결된다.
- Actuator의 `http.server.requests`, `jvm.*`, `tomcat.*` 지표는 애플리케이션과 JVM 경계를 이어 주는 최소 관찰점이다.
- Repository 호출이 느려도 원인은 DB SQL만이 아니라 connection pool 대기, socket 대기, GC pause, CPU 포화일 수 있다.
- 로그의 trace id와 thread name을 남기면 OS thread 관찰 결과와 애플리케이션 로그를 맞추기 쉽다.
- 운영 설정은 Spring property 하나가 아니라 OS limit, JVM option, WAS connector 설정과 함께 읽어야 한다.

## 코드와 설정 예시

```text
Client
  OS socket
    Tomcat connector
      worker thread
        Spring MVC handler
          Service / Repository
            DB or external I/O
      JVM heap / GC / scheduler
  Response
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 흐름도에서는 요청이 어느 시점에 worker thread를 점유하고, 어느 구간에서 socket, file descriptor, heap을 쓰며, 어떤 구간이 GC나 scheduler 대기의 영향을 받는지 질문해야 한다.

## 관찰 명령

```bash
ps -o pid,ppid,stat,pcpu,pmem,args -p <pid>
top -H -p <pid>
jcmd <pid> Thread.print
ss -tanp | head
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| 요청 latency가 전체적으로 상승 | 공통 하위 자원 포화 | Tomcat busy thread, GC pause, CPU, DB pool |
| 특정 endpoint만 느림 | 코드 경로 또는 하위 의존성 문제 | trace, SQL, 외부 API 시간 |
| 서버 재시작 후 잠시 정상 | 누수, queue 누적, warm-up, connection churn | heap/RSS 추세와 thread 수 |
| 지표는 정상인데 사용자는 느림 | 네트워크 앞단, LB, TLS, client timeout | edge/gateway 로그와 서버 수신 시각 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 영향 endpoint와 시간대를 먼저 고정한다.
2. 애플리케이션 로그에서 요청이 서버에 도착했는지 확인한다.
3. Tomcat thread, executor, DB pool 지표로 대기 위치를 본다.
4. CPU, memory, socket, disk 지표를 같은 시간대에 맞춘다.
5. 최근 배포, 설정 변경, batch, 트래픽 증가를 타임라인에 올린다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 요청 경로를 `client -> socket -> connector -> thread -> handler -> dependency -> response`로 적어 둔다.
- 느린 API는 코드 시간, queue 시간, I/O 시간을 분리해서 본다.
- Controller 로그가 없으면 Spring 이전 구간을 먼저 의심한다.
- 요청별 trace id와 thread name을 로그에 남긴다.
- 전체 흐름 문서는 장애 회고의 공통 그림으로 재사용한다.

## 주니어 팁

- `백엔드 요청과 실행 환경 전체 흐름`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `백엔드 요청과 실행 환경 전체 흐름`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- Controller 코드만 보고 전체 요청 시간을 설명하려 한다.
- LB나 socket queue에서 밀린 요청을 애플리케이션 로직 문제로 오해한다.
- DB 호출 시간과 connection acquire 시간을 구분하지 않는다.
- 요청이 서버에 도착했는지 확인하지 않고 JVM만 본다.
- latency를 평균값 하나로만 본다.

## 확인 질문

- `백엔드 요청과 실행 환경 전체 흐름`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
