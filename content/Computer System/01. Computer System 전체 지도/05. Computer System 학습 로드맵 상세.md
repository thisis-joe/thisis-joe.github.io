>- Java/Spring 코드와 운영 지표를 어떻게 연결하는가?

## 개요

이 문서의 주제는 `Computer System 학습 로드맵`이다. OS와 JVM 개념을 장애 분석에 필요한 순서로 학습하는 경로를 제시한다.

먼저 붙잡을 기준은 다음 문장이다. 학습 순서는 장애 원인 격리 순서와 맞춘다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 학습 순서는 장애 원인 격리 순서와 맞춘다.
- 먼저 하나의 요청이 socket, connector, thread, Spring handler, dependency I/O, JVM, OS scheduler를 지나는 그림을 잡는다.
- 그 다음 CPU/process/thread, blocking, memory, file/socket, Linux 관찰, concurrency, JVM, 병목 분석, 플레이북 순서로 좁혀 간다.
- 각 장은 개념 하나와 관찰 명령 하나를 반드시 짝지어 학습한다. 명령 없이 외운 개념은 장애 중 사용할 수 없다.
- Java/Spring 코드는 항상 thread 점유, heap 사용, socket/file descriptor 사용, timeout 전파와 연결해서 읽는다.
- 로드맵의 끝은 지식 목록이 아니라 장애 상황에서 증거를 모으고 원인을 격리하는 반복 루틴이다.

## 문서별 핵심 구분

- 학습 순서는 OS 이론 순서가 아니라 백엔드 장애에서 자주 만나는 원인 순서로 잡는다.
- thread, memory, socket, file descriptor, GC를 각각 독립 과목이 아니라 요청 실행의 일부로 연결한다.
- 각 주제는 반드시 관찰 명령과 함께 학습해야 운영 지식이 된다.

## 원리

학습 순서는 운영에서 질문이 생기는 순서와 맞아야 한다. 느린 API를 보면 먼저 요청 흐름을 그리고, thread가 어디에서 점유되는지 본 뒤, CPU와 scheduler, blocking I/O, memory/GC, file/socket, OS service 상태를 차례로 좁힌다.

OS 교과서 순서대로 모든 개념을 깊게 파고드는 방식은 백엔드 장애 대응과 거리가 멀 수 있다. 처음에는 process, thread, file descriptor, socket, memory, scheduling처럼 Java 서버 관찰에 바로 필요한 단어부터 잡는 편이 낫다.

각 주제는 "정상 상태에서 어떤 명령으로 보이는가"와 함께 학습해야 한다. 정상 기준선이 없으면 장애 중 숫자가 큰지 작은지, 새로 생긴 현상인지 원래 있던 현상인지 판단하기 어렵다.

`Computer System 학습 로드맵` 관점에서 중요한 점은 개념을 독립 과목으로 쌓지 않는 것이다. thread 학습은 ExecutorService와 thread dump로, memory 학습은 heap/RSS/GC log로, socket 학습은 Tomcat connector와 `ss`로 연결되어야 한다.

## Java/Spring 연결

- Spring MVC 요청은 대개 Tomcat worker thread 위에서 실행되므로 요청 지연은 thread 점유 시간과 직접 연결된다.
- Actuator의 `http.server.requests`, `jvm.*`, `tomcat.*` 지표는 애플리케이션과 JVM 경계를 이어 주는 최소 관찰점이다.
- Repository 호출이 느려도 원인은 DB SQL만이 아니라 connection pool 대기, socket 대기, GC pause, CPU 포화일 수 있다.
- 로그의 trace id와 thread name을 남기면 OS thread 관찰 결과와 애플리케이션 로그를 맞추기 쉽다.
- 운영 설정은 Spring property 하나가 아니라 OS limit, JVM option, WAS connector 설정과 함께 읽어야 한다.

## 코드와 설정 예시

```text
요청 지연
  CPU와 run queue 확인
  thread dump에서 대기 위치 확인
  GC와 heap 추세 확인
  socket, file descriptor, disk I/O 확인
```

예시는 공부 순서를 장애 원인 격리 순서로 바꾼 것이다. 느린 요청을 만났을 때 어떤 장을 다시 열어야 하는지 떠올릴 수 있어야 로드맵이 실제 운영 지식이 된다.

## 관찰 명령

```bash
man ps
man top
jcmd <pid> help
jcmd <pid> Thread.print
jcmd <pid> JFR.start help
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| 요청 latency가 전체적으로 상승 | 공통 하위 자원 포화 | Tomcat busy thread, GC pause, CPU, DB pool |
| 특정 endpoint만 느림 | 코드 경로 또는 하위 의존성 문제 | trace, SQL, 외부 API 시간 |
| 서버 재시작 후 잠시 정상 | 누수, queue 누적, warm-up, connection churn | heap/RSS 추세와 thread 수 |
| 지표는 정상인데 사용자는 느림 | 네트워크 앞단, LB, TLS, client timeout | edge/gateway 로그와 서버 수신 시각 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 영향 endpoint와 시간대를 먼저 고정한다.
2. 애플리케이션 로그에서 요청이 서버에 도착했는지 확인한다.
3. Tomcat thread, executor, DB pool 지표로 대기 위치를 본다.
4. CPU, memory, socket, disk 지표를 같은 시간대에 맞춘다.
5. 최근 배포, 설정 변경, batch, 트래픽 증가를 타임라인에 올린다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 처음에는 `ps`, `top`, `ss`, `jcmd` 네 가지 도구만 반복해도 충분하다.
- 각 장을 읽은 뒤 정상 서버에서 같은 명령을 실행해 기준선을 만든다.
- 개념을 외운 뒤에는 반드시 느린 요청 시나리오에 대입한다.
- thread dump와 heap dump는 샘플 파일을 열어 보는 연습이 필요하다.
- 로드맵은 한 번에 끝내지 말고 장애 회고 때 보강한다.

## 주니어 팁

- `Computer System 학습 로드맵`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Computer System 학습 로드맵`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- 운영체제 용어만 외우고 Java/Spring 요청 흐름과 연결하지 않는다.
- 고급 profiling 도구부터 시작해 기본 지표를 놓친다.
- 정상 상태 관찰 없이 장애 상태만 보려 한다.
- 각 장을 독립적으로 읽어 병목 전파를 이해하지 못한다.
- 명령 사용 권한과 운영 부하를 고려하지 않는다.

## 확인 질문

- `Computer System 학습 로드맵`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
