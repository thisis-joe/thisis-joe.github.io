>- Java/Spring 코드와 운영 지표를 어떻게 연결하는가?

## 개요

이 문서의 주제는 `IO Wait와 Disk 병목`이다. iowait, disk queue, latency를 보고 로그와 파일 I/O 병목을 판단하는 방법을 정리한다.

먼저 붙잡을 기준은 다음 문장이다. disk 병목은 응답 지연으로 번진다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: disk 병목은 응답 지연으로 번진다.
- 성능 병목 분석은 증상을 하나의 계층에 빨리 귀속시키는 일이 아니라 원인 후보를 지워 가는 일이다.
- CPU bound, memory pressure, disk I/O, socket queue, thread pool, connection pool은 서로 원인과 결과가 될 수 있다.
- Load average는 CPU 사용률만이 아니라 runnable task와 uninterruptible I/O 대기 영향을 함께 받는다.
- Pool 고갈은 원인일 수도 있고 downstream 지연의 결과일 수도 있다.
- 장애 대응은 증거 확보, 유입 완화, 원인 격리, 근본 수정, 회고로 나눈다.

## 문서별 핵심 구분

- iowait는 CPU가 I/O 완료를 기다리는 시간이다.
- disk await와 queue depth는 latency 원인을 좁히는 지표다.
- 로그, dump, DB, upload가 같은 disk를 공유하면 병목이 겹친다.

## 원리

성능 병목 분석은 증상을 하나의 계층에 빨리 귀속시키는 일이 아니라 원인 후보를 지워 가는 일이다.

CPU bound, memory pressure, disk I/O, socket queue, thread pool, connection pool은 서로 원인과 결과가 될 수 있다.

Load average는 CPU 사용률만이 아니라 runnable task와 uninterruptible I/O 대기 영향을 함께 받는다.

`IO Wait와 Disk 병목` 관점에서 중요한 점은 지표 하나로 원인을 확정하지 않는 것이다. thread dump는 Java 코드 위치를 보여 주지만 CPU 사용량이나 I/O 대기 시간은 OS 지표로 확인해야 한다. 반대로 OS 지표만 보면 어떤 Java 코드 경로가 문제인지 알기 어렵다.

## Java/Spring 연결

- Spring Actuator와 Micrometer 지표는 JVM/애플리케이션 관찰의 시작점이지만 OS 지표 없이 병목을 확정하기 어렵다.
- Tomcat thread, executor, HikariCP, Redis/client pool은 각각 다른 queue와 timeout을 가진다.
- 느린 API 하나가 thread pool과 connection pool을 점유하면 정상 API까지 지연될 수 있다.
- Retry, timeout, circuit breaker 설정은 장애 전파 경로를 만들거나 끊는다.
- 운영 대시보드는 평균보다 saturation, queue, pending, p95/p99 중심으로 구성해야 한다.

## 코드와 설정 예시

```bash
date -Is
uptime
top -H -p <pid>
jcmd <pid> Thread.print
jcmd <pid> GC.heap_info
ss -s
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 코드가 thread를 오래 점유하는지, heap에 객체를 남기는지, socket이나 file descriptor를 여는지, GC나 context switch를 늘리는지 질문해야 한다.

## 관찰 명령

```bash
iostat -xz 1 5
vmstat 1 5
pidstat -d -p <pid> 1 5
jcmd <pid> Thread.print
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| CPU 사용률 높음 | CPU bound, GC, busy loop | top -H, JFR, thread dump |
| load 높고 iowait 높음 | disk 또는 swap 병목 | iostat, vmstat, thread stack |
| pool pending 증가 | 하위 시스템 지연 또는 pool 부족 | pool active/idle/pending |
| memory pressure | heap leak, native, container limit | GC, RSS, OOM log |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 증상 시간을 분 단위로 고정한다.
2. CPU, memory, disk, socket, JVM, pool 지표를 같은 시간대에 모은다.
3. 가장 포화된 자원과 가장 먼저 변한 지표를 구분한다.
4. 임시 완화는 유입 제한, 비필수 작업 중지, timeout 정렬부터 검토한다.
5. 근본 해결은 코드, 설정, capacity, 운영 절차 중 어디인지 나눈다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- iowait는 CPU가 I/O 완료를 기다리는 시간이다. 이 기준을 실제 지표와 연결해 확인한다.
- disk await와 queue depth는 latency 원인을 좁히는 지표다. 정상 상태의 값을 먼저 남겨 장애 상태와 비교한다.
- 로그, dump, DB, upload가 같은 disk를 공유하면 병목이 겹친다. 관련 명령은 한 번이 아니라 시간 간격을 두고 반복 수집한다.
- `IO Wait와 Disk 병목` 문제는 코드 수정, 설정 변경, capacity 조정 중 어디에 속하는지 분리한다.
- 장애 회고에는 확인한 후보와 배제한 후보를 같이 남긴다.

## 주니어 팁

- `IO Wait와 Disk 병목`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `IO Wait와 Disk 병목`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- iowait는 CPU가 I/O 완료를 기다리는 시간이다. 이 차이를 무시하고 한 가지 지표로 결론을 낸다.
- disk await와 queue depth는 latency 원인을 좁히는 지표다. 관련 정상 기준선 없이 현재 값만 보고 판단한다.
- 로그, dump, DB, upload가 같은 disk를 공유하면 병목이 겹친다. 증거를 남기지 않고 재시작이나 설정 변경부터 한다.
- `IO Wait와 Disk 병목` 문제를 다른 계층의 문제와 구분하지 못한다.
- 완화 조치가 성공했다는 이유로 근본 원인 기록을 생략한다.

ze만 늘린다.
- Load average를 CPU 사용률과 같은 의미로 해석한다.
- 장애 중 수집한 지표의 시각이 서로 맞지 않는다.
- 증상 완화와 근본 원인 수정을 구분하지 않는다.

## 확인 질문

- `IO Wait와 Disk 병목`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
