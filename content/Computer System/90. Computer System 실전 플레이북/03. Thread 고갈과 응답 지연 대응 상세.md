>- Java/Spring 코드와 운영 지표를 어떻게 연결하는가?

## 개요

이 문서의 주제는 `Thread 고갈과 응답 지연 대응`이다. Thread 고갈, pool starvation, blocking I/O로 인한 응답 지연 대응 절차를 정리한다.

먼저 붙잡을 기준은 다음 문장이다. 느린 요청은 thread 위치로 좁힌다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 느린 요청은 thread 위치로 좁힌다.
- 플레이북은 장애 중 생각을 줄이기 위한 최소 절차다. 모든 상황을 맞히는 문서가 아니라 첫 증거를 놓치지 않게 해 준다.
- CPU, memory, thread, FD/socket 장애는 서로 겹쳐 나타나므로 한 루틴에서 다른 루틴으로 넘어갈 수 있어야 한다.
- 장애 중 수집할 증거는 짧고 반복 가능해야 한다. 긴 분석은 서비스 안정화 뒤에 진행한다.
- 완화 조치와 원인 분석은 다른 작업이다. 재시작은 완화일 수 있지만 원인을 설명하지 않는다.
- 보고서는 결론보다 판단 근거, 타임라인, 남은 리스크를 명확히 남겨야 한다.

## 문서별 핵심 구분

- thread 고갈은 busy thread, executor queue, downstream 대기를 같이 봐야 한다.
- CPU가 낮아도 모든 worker가 blocking 중이면 응답은 멈춘다.
- thread dump 반복 샘플로 대기 위치를 고정한다.

## 원리

플레이북은 장애 중 생각을 줄이기 위한 최소 절차다. 모든 상황을 맞히는 문서가 아니라 첫 증거를 놓치지 않게 해 준다.

CPU, memory, thread, FD/socket 장애는 서로 겹쳐 나타나므로 한 루틴에서 다른 루틴으로 넘어갈 수 있어야 한다.

장애 중 수집할 증거는 짧고 반복 가능해야 한다. 긴 분석은 서비스 안정화 뒤에 진행한다.

`Thread 고갈과 응답 지연 대응` 관점에서 중요한 점은 지표 하나로 원인을 확정하지 않는 것이다. thread dump는 Java 코드 위치를 보여 주지만 CPU 사용량이나 I/O 대기 시간은 OS 지표로 확인해야 한다. 반대로 OS 지표만 보면 어떤 Java 코드 경로가 문제인지 알기 어렵다.

## Java/Spring 연결

- Spring Boot 운영에서는 Actuator, application log, GC log, thread dump, OS command output을 하나의 incident bundle로 묶는 것이 좋다.
- CPU 급등은 endpoint traffic, JSON 직렬화, 암호화, compression, GC, busy loop 등 애플리케이션 코드와 JVM 모두에서 생긴다.
- Thread 고갈은 Tomcat, async executor, scheduler, DB pool 대기로 나누어 봐야 한다.
- FD/socket 고갈은 inbound 연결뿐 아니라 outbound client, DB connection, 로그 파일, temp file까지 포함한다.
- 장애 보고서에는 Spring 설정 변경만이 아니라 OS limit과 JVM option도 함께 적는다.

## 코드와 설정 예시

```bash
mkdir -p /tmp/incident-$(date +%Y%m%d-%H%M%S)
jcmd <pid> Thread.print > /tmp/thread-dump.txt
jcmd <pid> GC.heap_info > /tmp/gc-heap.txt
ss -s > /tmp/socket-summary.txt
```

예시는 특정 문법을 외우기 위한 것이 아니라 실행 위치를 보기 위한 것이다. 이 코드가 thread를 오래 점유하는지, heap에 객체를 남기는지, socket이나 file descriptor를 여는지, GC나 context switch를 늘리는지 질문해야 한다.

## 관찰 명령

```bash
jcmd <pid> Thread.print > thread.txt
curl -s localhost:8080/actuator/metrics/tomcat.threads.busy
curl -s localhost:8080/actuator/metrics/executor.queued
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| CPU 급등 | hot thread, GC, traffic spike | top -H, JFR, thread dump |
| OOM 또는 재시작 | heap/native/container limit | GC info, dump, dmesg |
| 응답 지연 | thread/pool/downstream 대기 | thread dump, pool metrics |
| 새 연결 실패 | FD/socket/backlog 고갈 | lsof, ss, limits |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. 사용자 영향과 시작 시각을 먼저 기록한다.
2. 재시작 전 가능한 최소 dump와 OS 지표를 확보한다.
3. 유입 제한, 비필수 batch 중지, 기능 차단으로 증상을 완화한다.
4. 원인 후보를 CPU, memory, thread, I/O, socket, downstream으로 나눈다.
5. 보고서에 타임라인, 근거, 완화, 근본 수정, 미확인 리스크를 남긴다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- thread 고갈은 busy thread, executor queue, downstream 대기를 같이 봐야 한다. 이 기준을 실제 지표와 연결해 확인한다.
- CPU가 낮아도 모든 worker가 blocking 중이면 응답은 멈춘다. 정상 상태의 값을 먼저 남겨 장애 상태와 비교한다.
- thread dump 반복 샘플로 대기 위치를 고정한다. 관련 명령은 한 번이 아니라 시간 간격을 두고 반복 수집한다.
- `Thread 고갈과 응답 지연 대응` 문제는 코드 수정, 설정 변경, capacity 조정 중 어디에 속하는지 분리한다.
- 장애 회고에는 확인한 후보와 배제한 후보를 같이 남긴다.

## 주니어 팁

- `Thread 고갈과 응답 지연 대응`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Thread 고갈과 응답 지연 대응`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- thread 고갈은 busy thread, executor queue, downstream 대기를 같이 봐야 한다. 이 차이를 무시하고 한 가지 지표로 결론을 낸다.
- CPU가 낮아도 모든 worker가 blocking 중이면 응답은 멈춘다. 관련 정상 기준선 없이 현재 값만 보고 판단한다.
- thread dump 반복 샘플로 대기 위치를 고정한다. 증거를 남기지 않고 재시작이나 설정 변경부터 한다.
- `Thread 고갈과 응답 지연 대응` 문제를 다른 계층의 문제와 구분하지 못한다.
- 완화 조치가 성공했다는 이유로 근본 원인 기록을 생략한다.

## 확인 질문

- `Thread 고갈과 응답 지연 대응`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
