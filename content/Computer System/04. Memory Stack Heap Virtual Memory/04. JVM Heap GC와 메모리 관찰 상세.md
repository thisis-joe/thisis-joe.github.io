## 개요

이 문서의 주제는 `JVM Heap GC와 메모리 관찰`이다. Heap 구조, GC pause, GC log, actuator metric으로 memory를 관찰하는 방법을 다룬다.

먼저 붙잡을 기준은 다음 문장이다. heap 사용량은 GC 이후 추세로 본다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: heap 사용량은 GC 이후 추세로 본다.
- Java memory는 heap만이 아니다. stack, metaspace, direct buffer, code cache, native library, OS page cache까지 process memory에 영향을 준다.
- GC는 도달 불가능한 heap 객체를 회수한다. 계속 참조되는 객체, native memory, file descriptor는 GC만으로 해결되지 않는다.
- Virtual memory는 process가 보는 주소 공간이고 RSS는 실제 물리 memory에 올라온 부분이다. 둘을 같은 값으로 보면 안 된다.
- Memory leak은 사용 후 참조가 끊기지 않아 시간이 지날수록 baseline이 올라가는 패턴으로 확인한다.
- Heap dump는 가장 강한 증거지만 크고 민감한 데이터를 담을 수 있어 수집 위치, 권한, 보관 기간을 정해야 한다.

## 문서별 핵심 구분

- GC는 heap 회수를 담당하지만 pause와 CPU 비용을 만든다.
- heap used는 GC 전보다 GC 후 추세가 중요하다.
- allocation rate가 높으면 leak이 없어도 GC 압박이 커질 수 있다.

## 원리

JVM heap은 Java 객체가 할당되는 주요 영역이고 GC는 더 이상 도달할 수 없는 객체를 회수한다. 관찰할 때는 "현재 heap used"보다 GC 이후 old 영역이 어느 수준으로 돌아오는지를 본다.

GC pause는 애플리케이션 thread가 멈추는 시간으로 사용자 latency에 직접 영향을 줄 수 있다. pause가 짧아도 allocation rate가 높으면 CPU 비용과 tail latency가 커질 수 있다.

Heap 관찰은 Actuator metric, GC log, `jcmd GC.heap_info`, JFR을 함께 사용한다. metric은 추세를 보여 주고, GC log는 collector 동작과 pause 원인을 더 자세히 보여 준다.

`JVM Heap GC와 메모리 관찰` 관점에서 중요한 점은 leak과 allocation pressure를 구분하는 것이다. GC 후 바닥선이 올라가면 보관 객체를 의심하고, 바닥선은 안정적인데 GC 빈도와 CPU가 높으면 할당량이 많은 코드 경로를 의심한다.

## Java/Spring 연결

- Spring singleton bean의 cache, static map, listener 등록, scheduler 누락은 heap leak의 흔한 출발점이다.
- ThreadLocal은 thread pool과 만나면 요청이 끝나도 값이 남을 수 있다.
- Multipart upload, WebClient buffer, direct buffer, Netty memory는 heap 밖 memory 압박으로 나타날 수 있다.
- Actuator `jvm.memory.used`, `jvm.gc.pause`, process RSS를 함께 봐야 heap 문제와 native 문제를 나눌 수 있다.
- OOM 후 자동 재시작만 있으면 서비스는 살아나도 leak 원인은 계속 남는다.

## 코드와 설정 예시

```java
public OrderDto getOrder(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    return mapper.toDto(order); // 대량 호출 시 allocation rate를 만든다.
}
```

예시는 leak이 없어도 객체 생성량이 많으면 GC 압박이 생긴다는 점을 보기 위한 것이다. DTO 변환, JSON 직렬화, 대량 조회, 문자열 조합은 allocation rate를 높일 수 있다.

## 관찰 명령

```bash
jcmd <pid> GC.heap_info
jcmd <pid> VM.flags
curl -s localhost:8080/actuator/metrics/jvm.gc.pause
curl -s localhost:8080/actuator/metrics/jvm.memory.used
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| GC 후 heap used가 계속 상승 | heap leak 또는 cache 증가 | class histogram, heap dump |
| heap은 안정적인데 RSS 상승 | native/direct memory, thread stack | NMT, `/proc/<pid>/status` |
| Full GC와 pause 증가 | allocation pressure 또는 old gen 압박 | GC log, allocation hot spot |
| Swap in/out 발생 | OS memory pressure | vmstat, container limit, OOM kill log |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. OOM 메시지가 `Java heap space`, `Metaspace`, `Direct buffer memory`, OS kill 중 무엇인지 확인한다.
2. heap used after GC 추세와 RSS 추세를 분리한다.
3. thread 수 증가로 stack memory가 늘었는지 확인한다.
4. 운영에서 가능하면 class histogram을 먼저 남기고 heap dump는 부하와 용량을 보고 결정한다.
5. 최근 배포에서 cache, batch, 대량 조회, buffering 변경이 있었는지 확인한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- `jvm.gc.pause`는 평균보다 p95/p99와 최대값을 본다.
- GC 후 old 영역 바닥선이 올라가는지 별도 그래프로 본다.
- allocation rate가 높은 endpoint는 trace, profiler, JFR로 코드 경로를 좁힌다.
- GC log는 장애 전후 collector 동작을 비교할 수 있게 보관한다.
- heap size 변경 전에는 CPU, pause 목표, container limit을 함께 확인한다.

## 주니어 팁

- `JVM Heap GC와 메모리 관찰`을 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `JVM Heap GC와 메모리 관찰`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- heap used 순간값만 보고 GC 문제를 판단한다.
- GC pause p99를 보지 않고 평균만 본다.
- allocation rate를 보지 않고 heap size만 키운다.
- GC log 없이 collector 튜닝을 시도한다.
- container memory limit보다 큰 heap 목표를 잡는다.

## 확인 질문

- `JVM Heap GC와 메모리 관찰`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
