## 개요

이 문서의 주제는 `Thread Dump로 병목 읽기`이다. Thread state, stack trace, lock owner, 반복 샘플을 읽어 병목을 판단하는 방법을 다룬다.

먼저 붙잡을 기준은 다음 문장이다. thread state와 stack trace는 시간축으로 읽는다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: thread state와 stack trace는 시간축으로 읽는다.
- Thread dump는 Java thread의 이름, state, stack trace, lock 대기 관계를 보여 주는 snapshot이다.
- `RUNNABLE`은 항상 CPU를 태우는 상태가 아니며 socket read 같은 native I/O 대기까지 포함할 수 있다.
- `BLOCKED`는 monitor lock 획득 대기이고, `WAITING/TIMED_WAITING`은 park, sleep, queue, condition, I/O wrapper 등 여러 원인을 가질 수 있다.
- 병목 증거는 한 장의 dump보다 10초 간격 2~3장에서 같은 stack이 반복될 때 강해진다.
- CPU hot thread를 찾을 때는 OS native thread id와 dump의 `nid`를 맞춰야 한다.

## 문서별 핵심 구분

- thread dump는 Java thread의 state와 stack trace snapshot이다.
- 한 장보다 여러 장에서 반복되는 stack이 병목 증거로 강하다.
- BLOCKED, WAITING, RUNNABLE은 OS CPU 사용량과 함께 해석해야 한다.

## 원리

Thread dump는 "어떤 Java 코드 위치에 thread가 머물러 있는가"를 보여 준다. 그래서 CPU 사용률, latency, pool 지표와 연결할 때 강력하다. 하지만 dump 자체는 CPU 사용량, disk wait, network retransmit을 직접 측정하지 않는다.

먼저 thread name 분포를 본다. `http-nio-*`, `task-*`, `scheduler-*`, `HikariPool-*`, `reactor-*`처럼 이름이 나뉘면 어느 executor나 처리 모델에 thread가 몰렸는지 빠르게 좁힐 수 있다.

다음으로 state보다 stack의 반복을 본다. 많은 thread가 같은 DB 호출, 같은 lock, 같은 외부 API client, 같은 queue wait에 머물면 그 위치가 병목 후보가 된다.

`Thread Dump로 병목 읽기` 관점에서 중요한 점은 dump를 시간축으로 읽는 것이다. 단일 snapshot은 우연일 수 있으므로 여러 번 수집하고, 같은 시각의 `top -H`, GC log, pool metric과 맞춘다.

## Java/Spring 연결

- Spring MVC의 동기 요청은 worker thread 하나가 Controller, Service, Repository 호출을 끝까지 수행하는 모델로 이해하면 된다.
- `@Async`, scheduler, batch, 외부 API client가 별도 executor를 쓰면 요청 thread와 worker thread의 병목 위치가 달라진다.
- Tomcat `threads.max`를 늘리면 더 많은 요청을 동시에 받지만, CPU와 DB connection이 따라오지 않으면 대기열만 커진다.
- Thread name을 executor별로 명명하면 dump에서 `http-nio`, `task-`, `scheduler-`, `HikariPool`을 빠르게 구분할 수 있다.
- ThreadLocal, MDC, SecurityContext는 thread 재사용 환경에서 정리 누락이 장애와 정보 누출로 이어질 수 있다.

## 코드와 설정 예시

```text
"http-nio-8080-exec-42" #142 daemon prio=5 os_prio=0 tid=0x... nid=0x7f03 BLOCKED
   java.lang.Thread.State: BLOCKED (on object monitor)
    - waiting to lock <0x00000007123> owned by "http-nio-8080-exec-17"
    at com.example.OrderService.placeOrder(OrderService.java:42)
```

예시는 dump에서 읽어야 할 핵심 단서다. thread name, `nid`, state, lock owner, application stack frame을 보고 어떤 요청 처리 경로가 어떤 자원에서 멈췄는지 추적한다.

## 관찰 명령

```bash
jcmd <pid> Thread.print > dump1.txt
sleep 10; jcmd <pid> Thread.print > dump2.txt
grep -E 'BLOCKED|WAITING|RUNNABLE' dump1.txt | head
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| RUNNABLE thread가 core보다 많음 | CPU 경합 또는 native I/O 대기 | `top -H`, stack trace, load average |
| BLOCKED가 특정 lock에 몰림 | synchronized/monitor 경합 | lock owner와 기다리는 thread |
| WAITING/TIMED_WAITING이 pool에 몰림 | queue 대기, connection 대기, sleep/retry | executor, Hikari, timeout 지표 |
| thread 수가 계속 증가 | unbounded executor 또는 thread leak | thread name 분포와 생성 위치 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. `top -H -p <pid>`로 CPU를 쓰는 native thread를 찾는다.
2. 같은 시각에 `jcmd <pid> Thread.print`를 남긴다.
3. native thread id와 Java thread dump의 `nid`를 맞춘다.
4. state별 개수보다 같은 stack에 몰린 thread를 먼저 본다.
5. 10초 간격으로 2~3회 반복해 계속 같은 위치인지 확인한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- 10초 간격으로 2~3회 dump를 남긴다.
- 같은 stack에 몰린 thread 수를 먼저 본다.
- lock owner와 waiting thread를 같이 찾는다.
- CPU hot thread는 native id를 변환해 dump와 맞춘다.
- dump 파일명에 시각, host, pid를 넣는다.

## 주니어 팁

- `Thread Dump로 병목 읽기`를 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Thread Dump로 병목 읽기`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- thread dump 한 장으로 결론을 확정한다.
- RUNNABLE을 모두 CPU bound로 해석한다.
- WAITING thread가 많다는 이유만으로 장애라고 판단한다.
- dump 수집 전에 재시작한다.
- thread name이 없어 executor를 구분하지 못한다.

## 확인 질문

- `Thread Dump로 병목 읽기`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
