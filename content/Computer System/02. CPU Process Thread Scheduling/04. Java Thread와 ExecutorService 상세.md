## 개요

이 문서의 주제는 `Java Thread와 ExecutorService`이다. Java Thread와 ExecutorService가 요청 처리량, queue, rejection, shutdown에 미치는 영향을 정리한다.

먼저 붙잡을 기준은 다음 문장이다. thread pool은 실행 정책과 대기 정책의 조합이다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: thread pool은 실행 정책과 대기 정책의 조합이다.
- `ExecutorService`는 thread를 만드는 도구가 아니라 작업 제출, queue, worker 수, rejection, shutdown을 묶은 실행 경계다.
- `Executors.newFixedThreadPool`은 worker 수는 고정하지만 내부 queue가 커질 수 있어 지연을 memory와 대기열 안에 숨길 수 있다.
- Pool size는 CPU core 수만으로 정하지 않는다. CPU 작업인지 blocking I/O 작업인지, downstream capacity가 얼마인지, timeout이 어디에 있는지 같이 봐야 한다.
- 작업 제출이 성공했다는 사실은 처리 완료를 뜻하지 않는다. queue에서 오래 기다리면 사용자는 이미 느린 응답을 경험한다.
- 종료 정책이 없으면 배포, 장애, scale-in 중 작업 유실이나 오래 매달린 thread가 생긴다.

## 문서별 핵심 구분

- ExecutorService는 thread 수, queue, rejection, lifecycle 정책의 묶음이다.
- 작업 제출이 성공해도 queue에서 오래 기다리면 사용자는 느리게 느낀다.
- shutdown 정책이 없으면 배포 종료나 장애 중 작업이 유실될 수 있다.

## 원리

Java `Thread`는 실행 흐름이고 `ExecutorService`는 그 실행 흐름을 재사용하는 정책이다. 직접 thread를 계속 만들면 생성 비용, stack memory, shutdown 관리가 문제가 되므로 서버 코드는 보통 executor를 통해 작업을 제출한다.

Executor의 핵심은 worker 수보다 queue와 rejection이다. worker가 모두 바쁘면 새 작업은 queue에 들어가거나 거절된다. queue가 무제한이면 장애가 즉시 드러나지 않고 latency와 memory 사용량이 뒤에서 커진다.

Blocking I/O 작업과 CPU 작업을 같은 executor에 섞으면 튜닝 기준이 흔들린다. CPU 작업은 core 수가 상한이고, blocking I/O 작업은 대기 시간이 길수록 worker를 더 오래 붙잡는다. 같은 pool을 공유하면 한 종류의 작업이 다른 작업을 굶길 수 있다.

`Java Thread와 ExecutorService` 관점에서 중요한 점은 "동시에 실행할 수 있는 수"와 "대기시킬 수 있는 수"를 분리하는 것이다. 장애 중에는 active, queued, completed, rejected, thread name 분포를 함께 봐야 한다.

## Java/Spring 연결

- Spring MVC의 동기 요청은 worker thread 하나가 Controller, Service, Repository 호출을 끝까지 수행하는 모델로 이해하면 된다.
- `@Async`, scheduler, batch, 외부 API client가 별도 executor를 쓰면 요청 thread와 worker thread의 병목 위치가 달라진다.
- Tomcat `threads.max`를 늘리면 더 많은 요청을 동시에 받지만, CPU와 DB connection이 따라오지 않으면 대기열만 커진다.
- Thread name을 executor별로 명명하면 dump에서 `http-nio`, `task-`, `scheduler-`, `HikariPool`을 빠르게 구분할 수 있다.
- ThreadLocal, MDC, SecurityContext는 thread 재사용 환경에서 정리 누락이 장애와 정보 누출로 이어질 수 있다.

## 코드와 설정 예시

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    20, 20,
    30, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

예시는 executor의 운영 계약을 드러내기 위한 것이다. worker 20개, queue 100개, rejection 정책이 함께 있어야 장애 중 새 작업을 계속 받을지, 호출자에게 backpressure를 걸지 판단할 수 있다.

## 관찰 명령

```bash
jcmd <pid> Thread.print
curl -s localhost:8080/actuator/metrics/executor.active
curl -s localhost:8080/actuator/metrics/jvm.threads.live
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| RUNNABLE thread가 core보다 많음 | CPU 경합 또는 native I/O 대기 | `top -H`, stack trace, load average |
| BLOCKED가 특정 lock에 몰림 | synchronized/monitor 경합 | lock owner와 기다리는 thread |
| WAITING/TIMED_WAITING이 pool에 몰림 | queue 대기, connection 대기, sleep/retry | executor, Hikari, timeout 지표 |
| thread 수가 계속 증가 | unbounded executor 또는 thread leak | thread name 분포와 생성 위치 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. `top -H -p <pid>`로 CPU를 쓰는 native thread를 찾는다.
2. 같은 시각에 `jcmd <pid> Thread.print`를 남긴다.
3. native thread id와 Java thread dump의 `nid`를 맞춘다.
4. state별 개수보다 같은 stack에 몰린 thread를 먼저 본다.
5. 10초 간격으로 2~3회 반복해 계속 같은 위치인지 확인한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- executor별 thread name prefix를 명확히 둔다.
- queue는 무제한보다 업무별 상한과 rejection 정책을 둔다.
- blocking 작업과 CPU 작업은 같은 executor에 섞지 않는다.
- Actuator executor metric을 endpoint latency와 함께 본다.
- 장애 중에는 active, queued, rejected를 동시에 확인한다.

## 주니어 팁

- `Java Thread와 ExecutorService`를 단어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Java Thread와 ExecutorService`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- 무제한 queue로 backpressure를 memory 문제로 바꾼다.
- 공용 executor에 batch와 사용자 요청 후속 작업을 같이 넣는다.
- Future 결과를 같은 pool thread에서 기다려 starvation을 만든다.
- shutdownNow를 안전한 종료로 오해한다.
- executor metric 없이 thread 수만 설정한다.

## 확인 질문

- `Java Thread와 ExecutorService`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
