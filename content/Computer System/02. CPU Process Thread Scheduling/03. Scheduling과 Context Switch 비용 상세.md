## 개요

이 문서의 주제는 `Scheduling과 Context Switch 비용`이다. OS scheduler가 runnable thread를 CPU에 올리는 방식과 context switch 비용을 다룬다.

먼저 붙잡을 기준은 다음 문장이다. 전환 비용은 thread가 많아질수록 숨은 지연이 된다. 코드가 정상적으로 보여도 실제 실행 환경에서는 CPU, thread, heap, file descriptor, socket, disk, GC 같은 자원이 함께 움직인다. 따라서 이 문서는 개념 설명에서 멈추지 않고 관찰 명령과 장애 판단 기준까지 연결한다.

## 핵심 모델

- 판단 기준: 전환 비용은 thread가 많아질수록 숨은 지연이 된다.
- CPU core는 실제 실행 자원이고 thread는 실행 후보이다. runnable thread가 core보다 많으면 scheduler 대기와 context switch가 생긴다.
- Process는 주소 공간과 file descriptor table을 갖고, thread는 같은 process 안에서 heap과 열린 자원을 공유한다.
- Java platform thread는 운영체제 thread와 연결되므로 thread 수 증가는 stack memory, scheduling 비용, dump 분석 비용을 함께 늘린다.
- ExecutorService는 thread 생성기가 아니라 작업 제출, queue, worker 수, rejection, shutdown 정책을 가진 실행 경계다.
- Thread dump는 한 시점의 snapshot이다. 병목은 보통 여러 번의 dump에서 같은 stack이 반복될 때 더 강하게 드러난다.

## 문서별 핵심 구분

- scheduler는 runnable thread를 CPU core에 배치한다.
- context switch는 작업 전환 비용이며 thread가 많을수록 무시하기 어렵다.
- blocking과 wake-up이 잦으면 CPU를 많이 쓰지 않아도 지연이 커질 수 있다.

## 원리

Scheduler는 runnable thread를 CPU core에 배치한다. runnable thread가 core보다 많으면 모든 thread가 동시에 실행되는 것이 아니라 짧은 시간 조각을 나눠 받는다.

Context switch는 실행 중인 thread를 멈추고 다른 thread의 register, stack, scheduler 상태로 바꾸는 비용이다. 한 번의 비용은 작아 보여도 thread가 많고 blocking/wake-up이 잦으면 latency와 CPU overhead로 누적된다.

Java 서버에서는 blocking I/O, 짧은 timeout, 즉시 retry, 너무 큰 worker pool, 과도한 logging이 wake-up을 늘릴 수 있다. CPU 사용률이 높지 않아도 runnable queue와 context switch가 늘면 요청 지연이 커진다.

`Scheduling과 Context Switch 비용` 관점에서 중요한 점은 thread 수 증가를 처리량 증가로 바로 해석하지 않는 것이다. core 수, runnable 개수, voluntary/non-voluntary context switch, load average, thread dump를 함께 봐야 한다.

## Java/Spring 연결

- Spring MVC의 동기 요청은 worker thread 하나가 Controller, Service, Repository 호출을 끝까지 수행하는 모델로 이해하면 된다.
- `@Async`, scheduler, batch, 외부 API client가 별도 executor를 쓰면 요청 thread와 worker thread의 병목 위치가 달라진다.
- Tomcat `threads.max`를 늘리면 더 많은 요청을 동시에 받지만, CPU와 DB connection이 따라오지 않으면 대기열만 커진다.
- Thread name을 executor별로 명명하면 dump에서 `http-nio`, `task-`, `scheduler-`, `HikariPool`을 빠르게 구분할 수 있다.
- ThreadLocal, MDC, SecurityContext는 thread 재사용 환경에서 정리 누락이 장애와 정보 누출로 이어질 수 있다.

## 코드와 설정 예시

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    200, 200,
    0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>()
);
```

예시는 큰 thread pool이 항상 빠른 처리를 의미하지 않는다는 점을 보기 위한 것이다. core 수보다 훨씬 많은 worker가 runnable 상태로 깨어나면 scheduler 대기와 context switch가 늘고, queue가 무제한이면 지연이 안쪽에 쌓일 수 있다.

## 관찰 명령

```bash
vmstat 1 5
pidstat -w -p <pid> 1 5
top -H -p <pid>
cat /proc/<pid>/sched | head
```

운영 환경에서는 명령도 부하가 될 수 있다. dump, JFR, 대량 `lsof`, 긴 로그 출력은 범위와 시간을 제한하고, 수집 시각과 대상 PID를 함께 남긴다.

## 지표 해석

| 신호 | 먼저 의심할 것 | 다음 확인 |
| --- | --- | --- |
| RUNNABLE thread가 core보다 많음 | CPU 경합 또는 native I/O 대기 | `top -H`, stack trace, load average |
| BLOCKED가 특정 lock에 몰림 | synchronized/monitor 경합 | lock owner와 기다리는 thread |
| WAITING/TIMED_WAITING이 pool에 몰림 | queue 대기, connection 대기, sleep/retry | executor, Hikari, timeout 지표 |
| thread 수가 계속 증가 | unbounded executor 또는 thread leak | thread name 분포와 생성 위치 |

지표는 같은 시간축에서 비교해야 한다. 예를 들어 API latency가 먼저 올랐는지, GC pause가 먼저 늘었는지, pool pending이 먼저 증가했는지에 따라 원인과 결과가 달라진다.

## 장애 상황에서 보는 순서

1. `top -H -p <pid>`로 CPU를 쓰는 native thread를 찾는다.
2. 같은 시각에 `jcmd <pid> Thread.print`를 남긴다.
3. native thread id와 Java thread dump의 `nid`를 맞춘다.
4. state별 개수보다 같은 stack에 몰린 thread를 먼저 본다.
5. 10초 간격으로 2~3회 반복해 계속 같은 위치인지 확인한다.

이 순서는 절대 규칙이 아니다. 이미 명확한 증거가 있다면 해당 계층부터 보되, 결론을 내리기 전에는 Application, JVM, OS 중 최소 두 계층의 증거를 맞춘다.

## 실전 팁

- `vmstat`의 context switch와 run queue를 함께 본다.
- worker thread 수를 늘릴 때 context switch 변화를 확인한다.
- 짧은 작업을 너무 잘게 쪼개면 scheduling 비용이 커질 수 있다.
- CPU 사용률과 load average를 같이 해석한다.
- GC, logging, retry 폭주가 scheduling 압박을 만들 수 있다.

## 주니어 팁

- `Scheduling과 Context Switch 비용`을 용어로만 외우지 말고, 정상 상태와 장애 상태에서 같은 명령을 실행해 차이를 비교한다.
- 처음에는 `top`, `ps`, `ss`, `jcmd Thread.print`, Actuator metric처럼 재현 가능한 기본 도구부터 익힌다.
- 숫자가 크거나 작다는 판단보다 평소 기준선에서 얼마나 벗어났는지를 먼저 본다.

## 시니어 팁

- `Scheduling과 Context Switch 비용`에서 생긴 병목이 다른 pool, queue, retry, timeout으로 어떻게 전파되는지 설계 단계에서 확인한다.
- 장애 대응 runbook에는 명령뿐 아니라 해석 기준과 금지할 대응도 같이 적는다.
- 단일 인스턴스 기준의 해결책이 다중 인스턴스, container, LB 환경에서도 유효한지 확인한다.

## Guru급 팁

- snapshot 하나보다 여러 시점의 샘플이 강하다. thread dump, CPU, memory, socket 상태를 같은 간격으로 2~3회 수집하면 상태 전이가 보인다.
- JFR, async-profiler, eBPF, perf 같은 도구는 결론을 장식하는 도구가 아니라 가설을 검증하는 도구다.
- 병목을 제거하면 병목은 사라지는 것이 아니라 다른 자원으로 이동할 수 있다. 수정 후 새로운 saturation 지점을 다시 확인한다.

## 위험 신호!

- context switch 비용을 0으로 가정한다.
- thread pool을 크게 잡고 queue 대기만 줄었다고 성공으로 판단한다.
- load average를 CPU 사용률과 같은 뜻으로 본다.
- 짧은 timeout과 즉시 retry가 wake-up 폭주를 만드는 점을 놓친다.
- scheduler 지표 없이 thread 수만 튜닝한다.

## 확인 질문

- `Scheduling과 Context Switch 비용`에서 Application 로그만 보면 부족한 이유는 무엇인가?
	- Application 로그는 증상과 코드 경로를 보여 주지만 CPU, memory, socket, disk, scheduler 같은 하위 자원의 포화 여부를 직접 설명하지 못하기 때문이다.
- 장애 중 설정값을 바로 키우기 전에 확인해야 할 것은 무엇인가?
	- 어떤 자원이 먼저 포화됐는지, 하위 시스템 capacity가 남아 있는지, 변경이 장애를 완화하는지 증폭하는지 확인해야 한다.
- 같은 증상이 재발하지 않게 하려면 무엇을 남겨야 하는가?
	- 발생 시간, 영향 범위, 사용한 명령, 핵심 지표, 원인 판단, 완화 조치, 근본 수정, 남은 리스크를 남겨야 한다.
